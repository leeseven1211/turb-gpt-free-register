# Oracle 独立协议实例

## 已确认的部署范围

本机和 Oracle 使用同一 Git 仓库的 `main`，分别部署、分别保存 PostgreSQL 数据与运行配置，不同步账号、任务、邮箱库存或凭证。Oracle 从空业务库开始，只初始化必要配置，再单独导入邮箱。

Oracle 使用 `https://turb.leeseven.com`，复用主机现有 PostgreSQL 16、Nginx 和 HTTPS。应用采用 Python 3.12、Node 22 和 systemd，监听 `127.0.0.1:8000`。Roxy 保留在本机，Oracle 只运行协议功能。

## 部署能力设计

新增启动项 `TURB_BROWSER_ENABLED`，缺省为 `true`，Oracle 明确设置为 `false`。它属于每个部署的启动配置，不写入共享代码默认值或运行配置数据库。禁止浏览器的实例保留浏览器功能入口并置灰，显示“当前部署未启用浏览器”。

后端按实际选用的驱动和操作，在创建任务或领取邮箱之前校验能力，覆盖注册创建与重跑、CLI、Codex 显式驱动、查活与刷新 AT、账号配置和原生任务重试。协议任务保持原有重跑能力。配置保存不得重新开启该部署不支持的浏览器驱动或兜底。

用户已明确确认注册创建、重跑和 CLI 的准入方案；不修改驱动内部的步骤、请求参数、调用顺序、状态流转、重试、超时或运行中的兜底。能力不足时在开始之前明确拒绝，不在注册中途跳过步骤或切换驱动。

## 外部依赖准备

- 711Proxy 的 IP 白名单必须包含 Oracle 直连公网 IPv4；本机已有的白名单不会自动覆盖新服务器。提取 API 返回 HTTP 400、正文为 `IP Whitelist Check Failed` 时，应先在当前套餐加入服务器出口 IP，再验证代理领取，不修改注册步骤或反复新建注册任务。
- Email Butler 连接可以复用，但必须为新实例设置独立消费者身份，并从未归属的候选库存单独导入邮箱。

## 数据与回滚边界

使用现有 PostgreSQL 实例的新角色与新库，不新增 PostgreSQL 容器、不修改已有数据卷。本机与 Oracle 使用不同 `TURB_MAIL_CONSUMER_ID`，由 Butler 区分邮箱永久交接归属。Oracle 独立生成主密钥；配置迁入新库时用新密钥加密，不复制本机历史收件 profile 或凭据版本引用。

新库初始化、配置导入与正式生产进程属于部署操作；测试使用独立测试数据库及 `test_` schema，不能借生产放行项运行测试。备份同时保存数据库与匹配的启动配置/主密钥，日志按实例保留。新服务失败时停止该实例，恢复其代码、配置和数据库；本机继续独立运行。

## 服务与备份模板

- [应用服务](../../deploy/systemd/turb-gpt-free-register.service)直接运行 `web.py`，加载该实例 `.env`，避免遗漏 worker 初始化。
- [Nginx 站点](../../deploy/nginx/turb.leeseven.com.conf)使用独立域名与证书，保留服务器现有 Cloudflare 来源限制，不改其他站点。
- [备份脚本](../../tools/maintenance/backup_oracle.sh)先复制 `.env`，从该副本的 `DATABASE_URL` 确定数据库，并核对本机回环地址、端口与指定 PostgreSQL 容器的实际映射；核验后固定容器 ID 执行 `pg_dump`。同目录保存启动配置与代码提交，校验备份目录后才生成 `COMPLETE` 标志；失败目录不作为可恢复备份使用。`TURB_BACKUP_DATABASE` 仅可显式确认同一个库，不允许覆盖成其他库；不支持远端数据库、连接 service 或 hostaddr 间接寻址。
- [备份服务](../../deploy/systemd/turb-backup.service)及[定时器](../../deploy/systemd/turb-backup.timer)每天北京时间 03:30 运行。备份位于 `/srv/backups/turb-gpt-free-register`，不自动删除旧备份，需按磁盘容量定期管理。

恢复时先停止该实例，将完整备份恢复到新的独立库核验，核对匹配的主密钥和消费者身份，再切换数据库连接；不要直接覆盖仍在运行的数据库。配置历史、固定收件版本及邮箱归属一起保留。
