一句话结论：这不是「不好看」的问题，是没有单一事实来源的问题。18 个 CSS 变量只被引用了 103 次，而硬编码色值出现了 1,045 次——设计系统名存实亡。每加一个功能就新调一次颜色、字号和圆角，界面在按功能分叉而不是按系统收敛。

三 · 密度、滚动与列表

滑动 / 列表 —— 这是日常使用中最耗神的部分

严重

嵌套滚动容器 + overscroll-behavior: contain

L2433

表格外层 .accounts-table-v2-wrap 被限高为 min(720px, 100vh − 236px) 并 overflow:auto，同时页面本身也可纵向滚动。于是出现双层纵向滚动条：鼠标在表格上滚动表格，滚到底之后由于 overscroll-behavior: contain，滚动链被切断，页面不会继续滚——必须把鼠标移出表格区域才能继续。

叠加密度问题：行高 52px，每页 20 条，即 1,040px 内容塞进约 660px 视口 —— 每一页都必须在内层容器里滚动，无一例外。

二选一。① 让表格随页面自然流动（去掉 wrap 限高），表头用 position:sticky; top: 顶栏高度 吸附到视口；② 保留内层滚动，但把工具栏 + 分页也纳入同一个固定框架，做成真正的「全高数据面板」（表格区域 = 100vh − chrome），并去掉 overscroll-behavior: contain。

低

13 列无冻结列（实测后降级）

L3176–3197

实机复核后此条已降级。原判断「必然横向滚动、邮箱列滚出视野导致误操作」不成立——table[data-resizable-table]{min-width:100%!important} 覆盖了 min-width:1280px，1440px 下横向仅溢出 9px。

但代价转移到了截断：13 列平分 1130px，每列均宽 87px，导致 32% 单元格和 11/12 列头被省略号截断（见第零节）。冻结列仍值得加，因为用户会手动拉宽列（已有列宽持久化机制），拉宽后横滚就会变成真问题。

优先级低于「减列数」。先做列显隐开关，再考虑冻结前三列。

严重

复选框被 !important 锁死在 16×16px

L563 / 1053 / 1462 / 1728 / 1895

五处表格各用 6 条 !important 把复选框钉死在 16px（width/height/min-/max- 全锁）。WCAG 2.5.8 的最小目标尺寸是 24×24px，移动端建议 44px。而复选框正是所有批量操作（查活、刷新 AT、提链、删除）的入口。因为用了 !important，连响应式断点都无法放大它。

复选框本体保持 16px 视觉尺寸，但用 padding 或伪元素把点击热区撑到 ≥24px，并移除全部 !important。整行可点选中会更好。

四 · 交互与反馈

这是「感觉不够专业」的主要来源

严重

35 处原生 confirm() 承担全部高危确认

JS 全域

包括删除账号、批量删除、停止任务、提链（消耗 CDK）、补跑 Codex（消耗接码费用）。原生 confirm 的问题：① 阻塞主线程；② 显示为「127.0.0.1:5000 显示」，观感廉价；③ 无法排版——现在靠 \n\n 拼多行文本；④ 浏览器在连续弹出后会提供「阻止此页面创建更多对话框」，用户一旦勾选，后续所有确认会静默返回 false，操作会「点了没反应」。批量操作场景极易触发。

做一个统一的确认弹层组件：标题 + 影响范围（列出受影响账号）+ 成本预估（「将消耗 12 次 CDK / 约 $1.56」）+ 危险操作需输入数量确认。这一项对「专业感」的提升最大。

严重

没有任何加载态

JS 全域

全文 skeleton / spinner / loading 各 0 处，只有 6 处纯文本「加载中…」。表格数据在切换筛选、翻页、切 tab 时是直接跳变的——旧数据停留，然后突然被替换，用户无法判断「是在加载还是没数据」。

表格加 skeleton 行（保持行高，避免布局跳动）；按钮点击后进入 pending 态并禁用；配合 aria-busy。

五 · 任务执行：两套并行的任务体系

你提的问题——为什么只有注册有步骤和耗时

先说结论：不是账号任务缺数据，是缺「步骤模型」。注册任务有一份预先声明的有序步骤表，账号任务只有事后追加的流水事件。前者能画进度条，后者只能打日志。

注册任务 有步骤

  • db.JOB_PROGRESS_STAGES 声明 11 个有序步骤（key + 中文 label）
  • progress_steps 存 {stage: {state, started_at, completed_at, detail}}
  • 状态机含 pending/running/success/failed/skipped/stopped
  • 切换到 running 时自动结算前序步骤
  • 前端渲染横向步骤轨 + 每步耗时

账号任务 无步骤

  • 无步骤声明，不知道总共有几步
  • account_action_events 只有 created_at，无 started/finished
  • duration_ms 只在任务级，没有分步耗时
  • stage 命名不统一：network_route（查活/查套餐）vs network（Codex）
  • token_refresh_service 一个事件都不发
  • 前端把 detail 直接 JSON.stringify 铺在深色日志里

当前各服务实际发出的 stage

任务类型已发出的 stage数量问题

建议：给每种任务声明步骤表

完全复用注册那套模式，在 account_task_store.py 里加一份 ACCOUNT_TASK_STAGES: dict[action_type, tuple[(key, label)]]：

任务类型建议步骤序列
查活排队 → 选择线路 → 验证 Token → 判定结果
刷新AT排队 → 选择线路 → 收取邮箱 OTP → 重新登录 → 获取新 AT → 写入
查套餐排队 → 选择线路 → 请求套餐接口 → 试用资格判定 → 写入
Codex 补跑排队 → 启动驱动 → 选择线路 → OAuth 授权 → 回调校验 → 写入凭证
查封号邮件排队 → 定位邮箱通道 → 扫描信号 → 判定

再加一个 set_stage(task_id, stage, state, detail=None)——同时写步骤状态表和追加事件。这样每个 service 只需把现有的 append_event(...) 改成 set_stage(...)，一行换一行，就同时获得了进度轨和分步耗时。分支步骤（roxy_fallback 线路回退、reauth OTP 重登）标记为 skipped 或条件插入即可。

额外收益：有了分步耗时，「哪一步最慢」就成了可量化的问题。上面这个例子里「收取 OTP 18.6s」一眼可见是瓶颈——现在这个信息埋在事件时间戳里，没人会去手工做差。

更上层的问题：两套任务系统应该合并

现在有两个「任务」概念，分属两个模块、两套数据模型、两套 UI、两个轮询循环、两个分页器：

注册 › 任务记录账号 › 任务实例
存储JSON 文件（db.py）SQLite（account_task_store）
进度步骤表 + 分步耗时流水事件
日志独立日志文件 + 轮询事件表
批次批次进度面板batch 表但无 UI
重试单个 / 批量 / 批次级单个

用户视角里这两者都是「我发起的一个后台操作」。建议中期收敛成统一的任务中心：一个列表、一套状态机、一套步骤模型、一个详情抽屉。注册只是 action_type 的一种。account_action_batches 表已经存在但前端没用——批量操作的批次视图可以直接复用注册那套批次进度面板。

六 · 优化方案

按「投入产出比」排序，每阶段可独立交付

1

止血：可读性与安全

纯 CSS + 少量 JS · 低风险

不动结构，只改值。改完立刻能感知，且几乎不可能改坏。

  1. 轮询加 document.hidden 判断——十几行代码，立刻砍掉大部分无效请求（当前 30 次/分）
  2. 创建时间列改相对时间（2小时前），完整值放 tooltip——单这一项就消掉最严重的截断
  3. ID 列改等宽数字 + 右对齐，宽度给足 5 位
  4. 四张主表表头颜色提到 ≥5:1，字号 11 → 12px

  10. 删掉 L252–324 的旧侧边栏死代码

建立单一事实来源

机械替换 · 中等工作量

这是所有后续工作的地基。建议先把 <style> 拆到 static/app.css，否则 2,827 行内联 CSS 无法维护，也拿不到浏览器缓存。

  1. 定义 --brand-50…900、--gray-50…900 两套色阶 + 语义色（success/warn/danger/info）
  2. 25 种蓝 → 一套色阶；134 种灰 → 一套灰阶

  6. 顺带即可支持暗色模式（token 化之后只需重定义变量）

滚动与列表模型

需要设计决策 · 中高风险

先定「整页滚动」还是「全高面板」，再动手——这两条路的实现完全不同。

  1. 消除双层纵向滚动，去掉 overscroll-behavior: contain
  2. 冻结账号表前三列（勾选 / ID / 邮箱）
  3. 加列显隐开关，默认只显示 6 列，配置持久化到 localStorage（复用已有的列宽持久化机制）
  4. 顶栏 76 → 56px，子导航与命令甲板合并
  5. 行高 52 → 44px，并提供「紧凑 / 舒适」密度切换
  6. 移动端：13 列表格降级为卡片列表

反馈系统

新组件 · 独立可交付
  1. 统一确认弹层：影响范围 + 成本预估 + 危险操作二次输入，替换全部 35 处 confirm()
  2. Toast 分级：错误不自动消失、可复制、可堆叠、带 role

  4. 弹层改用原生 <dialog>

  6. 账号工具栏 17 按钮按对象重组

任务中心

前后端联动 · 最大工作量
  1. ACCOUNT_TASK_STAGES 步骤表 + set_stage() 写入器
  2. 五个 service 把 append_event 换成 set_stage，统一 stage 命名
  3. token_refresh_service 补齐可观测性
