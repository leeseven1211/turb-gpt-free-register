# 批量执行与任务提交性能分析

日期：2026-10-29（Asia/Shanghai）
状态：只读调查与优化建议，尚未实施优化。

## 1. 结论

当前最有现场证据的瓶颈是**代理池多个维护 worker 争抢全局容量锁，同时占用通用数据库连接**。它能同时拖慢后台任务、任务提交和页面查询。其他主要开销是同步逐项提交、反复汇总批次/历史任务、轮询请求重复携带大字段。

建议按“代理池锁与连接争用 → 批量提交 → 列表与轮询 → 批次/事件增量投影”的顺序分批处理。先消除等待和重复工作，再评估是否需要提高并发；目前没有证据支持直接增加数据库连接数或任务线程数。

## 2. 调查范围与证据边界

- 阅读当前代码，三个子 agent 分别审查提交/调度、存储、页面刷新，主 agent 核对调用链及运行态。
- 通过既有 Chrome 页面读取状态和已发生请求的 Performance 数据；没有点击执行、重试、支付或取消操作。
- 对现有服务执行少量、串行的 GET 请求，记录耗时、响应字节数和计数；没有提交新业务任务或执行压力测试。
- PostgreSQL 观察连接仅连接管理库 `postgres`，启用 `default_transaction_read_only=on` 和查询超时；读取 `pg_stat_activity`、`pg_locks`、`pg_blocking_pids()`，没有连接 `turb_console` 业务库、执行迁移或读取业务表。
- 没有改动业务代码、配置、现有任务或生产数据，没有重启服务。本文是新增分析文档。

当前工作区为 `main`，HEAD 为 `853a222`，调查开始时相对 `self/main` 领先 79 个提交。已有代码改动和未跟踪数据予以保留。运行服务 PID 为 `62142`，工作目录为本仓库，监听 `127.0.0.1:8000`；`/healthz`、`/readyz`、`/login` 返回 200。进程未提供构建指纹，因此这些信息不能证明它加载了当前工作区的每一处改动。

## 4. 关键瓶颈与拟优化位置

### P0：代理池全局维护锁挤占数据库连接，现场已确认

连续四次业务数据库活动快照分别有 **11、10、9、11 个连接等待 advisory lock**，单条锁等待语句的已运行时间最高约 4.16 秒。进一步采样发现等待者都在同一锁键上；数据库计算 `hashtextextended('proxy-pool-capacity', 0)` 与该锁完全匹配。

持锁连接执行的 `proxy_pool_resources` 终态查询、按 `resource_id` 获取行锁，精确对应 [proxy_pool_store.py](../../core/proxy_pool_store.py#L418) 的 `maintenance()`。因此现场主等待锁是代理池容量锁，不能把它归为任务批次汇总锁。

具体放大链路：

1. [proxy_pool.py](../../core/proxy_pool.py#L768) 的 20 个 worker 都执行 `maintain_once()`；每轮首先运行同一套全局维护（第 655–668 行），供给与复检角色均如此。
2. `maintenance()` 先借数据库连接，再等待 `proxy-pool-capacity`，持锁期间读取全部 live/cooldown/quarantine 资源，读取终态候选，再逐条 `FOR UPDATE` 并处理 anchor/children。当前非终态就有 513 条。
3. 闲置 ready 资源处理还会按每条资源重新读取同 profile 的可用集合。历史清理虽然最多返回 200 条，SQL 在缺少合适索引时仍可能扫描/排序大量终态历史；当前历史约 3.9 万条。查询实际扫描量尚需执行计划确认。
4. `reserve_refill_slots()` 也竞争同一容量锁。通用连接池在 [postgres_store.py](../../core/postgres_store.py#L131) 默认每池最大 12 条，按连接参数分别建池；现场见到大量业务连接被锁等待占用，甚至有样本出现 11 个等待者和 1 个持锁者。活动视图没有池身份，不能仅从跨池连接总数断言某一个池耗尽；尚需应用内连接池等待指标确定其占比。

**建议设计：** 将全局维护的并发与供应商网络检查的并发拆开。全局维护采用可跳过的单执行者协调，重复维护请求合并，等待尽量发生在借用通用连接之前；容量预留继续使用短事务进行原子检查。历史清理独立为有界维护，不放在每个供给/复检 worker 的容量锁内。针对终态清理和 children 查询，在隔离库确认执行计划后补充必要索引，消除逐行重复查询。

**必须保持：** 全局容量、资源所有权、出口隔离、活跃子租约、释放时序、过期规则及重启恢复。可跳过/合并仅适用于重复维护，容量预留仍须原子协调；冷却转 ready、资源过期等活动状态变化也必须保留短事务保护，不能把整个维护函数简单移出容量锁。不要通过改变注册领取、重试或超时策略掩盖争用。记录持锁时长、锁前等待、连接池等待，区分事务总耗时和真正持锁耗时。

### P1：大批量提交同步逐项落库，请求要等待整批处理

[extract_link_service.py](../../core/extract_link_service.py#L2476) 的 `create_workbench_batch()` 虽按 500 条切片，但切片内仍逐个调用 `create_workbench_tasks()`；当前 HTTP 请求直到全部循环及 `finish_submission()` 完成才返回。每项包括读取账号、检查资格/未决支付、占用账号、捕获配置、创建 Task/Run/Event、写账号排队状态。

[operation.py](../../core/storage/operation.py#L4091) 创建任务还包括账号行锁、多条 INSERT/UPDATE、批次序号查询；[同文件](../../core/storage/operation.py#L4031) 的 `_insert_runtime_run()` 在数据库事务内同步写日志文件。工作量和数据库往返次数随批量数量增加，且会叠加 P0 的连接等待。本轮没有新提交批次，因此不声称测得千条提交耗时。

另一个更强的锁影响在 [account_inspections.py](../../core/storage/account_inspections.py#L37)：整批巡检在同一事务里锁定全部匹配账号，再逐账号创建子任务；大批次提交期间可能阻塞这些账号的完成回写。这是代码风险，现场未证明正在发生。

**建议设计：** 先做批量账号预取、一次获取批次配置、批量预分配序号和分块写入，减少数据库往返。若提交仍超过交互预算，再引入持久化的批次提交进度：先保存请求身份和完整目标快照，再由可恢复 worker 分块入队，接口快速返回批次 ID。后者属于单独的架构改动，需要明确中断恢复和部分成功语义。

**必须保持：** `submission_id` 幂等、账号去重/占用检查、逐项结果、当前重跑能力、未知远端结果处理、配置快照语义和重启续建。巡检改变事务边界还必须保证目标快照、忙碌判断和账号 fence，不可仅去掉行锁。

注册提交的逐项写入和 `_executor_lock` 长临界区、Codex 批量补跑重复读取账号也存在同类问题，分别见 [registration_service.py](../../core/registration_service.py#L2638) 与 [codex_operation_service.py](../../core/codex_operation_service.py#L578)。涉及注册任务创建、调度或执行时序的修改须另给具体方案确认，不能作为本次普通性能修补直接实施。

### P1：统计与列表轮询重复计算大集合

- 全站可见时每 10 秒调用 `/api/summary`；总览页还每 15 秒调用 `/api/dashboard`，见 [bootstrap.js](../../webui/static/js/modern/bootstrap.js#L15)。两者都调用库存汇总。
- [local_email_inventory.py](../../core/local_email_inventory.py#L136) 每次串行汇总五个邮箱池；available 条件包含跨表占用、跨来源去重、收件 profile 和有效期检查。这部分确有重复工作，但 4–5 秒概览耗时还包括连接等待，不能全部算作扫描耗时。
- [operation.py](../../core/storage/operation.py#L2901) 统一任务列表执行 COUNT、分页和 5 组 facet 查询；当前 Run 的选择和运行次数派生会涉及执行历史。账号任务页由 5 秒定时器驱动刷新；请求未完成时记录待刷新，结束后可能立即续拉，见 [accounts.js](../../webui/static/js/modern/accounts.js#L532)。其物理扫描范围需结合计划，不能仅凭 SQL 就断言每次全表扫描。
- 注册任务表同样由 5 秒定时器驱动，表格模式持续轮询；相同查询正在进行时会合并请求，见 [jobs.js](../../webui/static/js/modern/jobs.js#L729)。当前测得的 6,975 ms 长响应意味着交互已明显受影响，但不代表每 5 秒都并发发起一份相同查询。
- 提链页每个成功轮次完成后等 5 秒再刷新，总周期还要加本轮请求和处理耗时。通常先读 20 个批次汇总，再读 10 条任务及整批计数；所选批次不在当前批次页内时另读详情，见 [extract-workbench.js](../../webui/static/js/modern/extract-workbench.js#L657)。批次下拉与任务列表重复汇总当前批次，后端见 [extract_link_batches.py](../../core/storage/extract_link_batches.py#L298)、[extract_link_jobs.py](../../core/storage/extract_link_jobs.py#L744)。

**建议设计：** 重复聚合先做短时缓存及并发请求合并，批次下拉/facets 低频或按变更版本更新；当前页任务状态按需刷新。统一任务当前 Run 与运行次数在确认查询计划后选择针对性查询或投影，避免一开始再造完整任务系统。库存缓存仅用于展示，领取仍执行权威条件；缓存必须处理绝对过期时间，并标明统计更新时间。

### P1：轮询响应携带详情，固定少量行也有大响应

10 条账号状态响应为 111,049 B，其中 `plan_check_country_results` 约 75,760 B、`account_promotions` 约 15,433 B。它不是前端一次加载全部账号，而是单行详情过重，见 [admin_repository.py](../../core/admin_repository.py#L434)。

20 条统一任务响应约 122 KB，其中任务 items 约 27.7 KB，额外附带的 50 个 batches 约 90.4 KB。`list_batches()` 返回整条批次及 `data`，每次列表刷新再次传输，见 [operations.py](../../webui/routes/operations.py#L242)、[operation.py](../../core/storage/operation.py#L2745)。

**建议设计：** 轮询只返回展示所需状态和 revision；国家详情、优惠明细及批次详情改为按需读取，保留已有详情功能。批次选择器使用明确字段白名单，变化时再刷新。前端根据 revision/行版本更新，避免内容未变仍整页重建。验收包含详情可用性和状态清空，不能因为增量合并留下旧状态。

### P2：批次完成逐项重算整批，任务越多总工作量越大

[operation.py](../../core/storage/operation.py#L6588) 的原生 `finish_run()` 同步刷新批次；[批次刷新](../../core/storage/operation.py#L1933) 在批次锁内计算所有逻辑根任务及重试子任务的有效状态。N 个任务逐个结束时，会触发 N 次整批统计，逻辑处理输入可达近似 N²。实际开销还受索引、缓存和完成分布影响；本轮现场主要等待的是代理池锁，而不是该锁。

**建议设计：** 合并批次摘要刷新；先核实已有投影队列的职责，再复用其去重机制或建立轻量摘要刷新队列。现队列还执行注册事实事件投影和终态修复，不能直接接入原生完成路径而增加额外工作。必要时才维护幂等增量计数。任务/Run 终态、依赖通知和账号回写保持原同步语义，仅展示汇总允许有界延迟，保留定期校正与重启补算。必须验证父子重试、部分成功、取消与重复完成的计数语义。

### P2：旧账号任务事件桥重复重放历史事件

[legacy_task_store.py](../../core/operations/legacy_task_store.py#L337) 每追加一个事件后同步任务；[operation.py](../../core/storage/operation.py#L2681) 同步时重新读取该任务全部旧事件，并逐个 upsert 到统一模型。E 个事件累计处理约 E(E+1)/2 次事件。它适用于旧账号任务桥，不应泛化到所有原生提链任务。

**建议设计：** 按源事件 ID/游标增量投影，任务摘要与事件分别同步，保留幂等全量校正工具。先确认活跃任务类型和调用频率再决定投入顺序。

### P3：暂不优先处理的候选

Codex 兼容导出仍会在去抖窗口后重写全量凭证文件，但当前只有 89 条凭证，且账号/注册任务已不做旧式全量导出，证据不足以列为本次首要瓶颈。模糊搜索 `%keyword%` 与 JSON 文本匹配可能需要专用索引，但应先以常用查询计划确认。暂不把磁盘容量、机器性能、上游网络或普通连接池大小认定为根因。

## 5. 实施选项与推荐顺序

| 选项 | 收益与限制 | 建议 |
|---|---|---|
| 针对性缩短锁、合并维护、批量数据库操作、精简读接口 | 直接对应现场证据；能分批上线和回滚 | 推荐 |
| 先调 worker/连接池参数 | 可用于受控对照；无法消除重复维护，扩大池还可能扩大锁队列 | 仅作为后续验证变量，本轮未调整 |
| 全面重构队列、引入新中间件或分库 | 成本和行为影响大，目前没有必要性证据 | 暂不推进 |

### 阶段 A：代理池争用治理

范围：`core/proxy_pool.py`、`core/proxy_pool_store.py`、必要的 `core/record_store.py` 索引；按需要增加最小诊断指标。

先用隔离库构造 500 左右非终态资源（包含约 409 条 cooldown）、4 万终态历史，以及 2/10/20 个 worker 的基线；区分维护次数、锁等待、持锁时间和普通查询延迟。随后将全局维护合并、终态历史整理移出容量锁的长临界区，优化集合查询。供给/复检网络并发与全局维护并发分别管理，避免后台锁等待持续挤占通用连接；跨进程协调仍可能占用连接，需单独测量。

验收：无容量超发、无活跃租约误回收、晚到结果不能覆盖新所有者；重启恢复通过；同等负载下不再持续出现通用池大多数连接等待同一容量锁。因代理池被所有注册驱动使用，任何改变领取行为、等待/重试/超时策略的部分都要单列方案确认。

### 阶段 B：提交性能与可恢复性

先优化提链和账号操作的预取、配置捕获及分块落库，测 10/100/500/1,000 项提交曲线；对巡检单独测账号行锁影响。若需要后台分块入队，另外设计 submission 状态、目标清单、分块游标、幂等重入、失败原因及启动恢复，再实施。

验收：持久接受后的接口响应目标 P95 < 1 秒仅适用于采用后台入队的方案；整批入队另报吞吐与完成时间，不能用快速 202 隐藏慢建任务。相同请求不得重复建任务，重启不漏项，批量任务重跑规则保持原样。

### 阶段 C：页面与统计减负

范围：`webui/static/js/modern/`、相关只读 routes、`core/admin_repository.py`、列表/汇总查询。

精简轮询字段、批次选项和详情按需读取；合并重复统计；缓存附带更新时间与失效规则。建议验收目标：同等任务负载下普通列表 P95 < 500 ms、展示统计 P95 < 1 秒；10 行状态响应 < 20 KB、20 行任务列表 < 50 KB。以上为拟定目标，需要隔离环境基线和真实浏览器复核后调整。

### 阶段 D：写入投影与批次汇总

针对仍有测量证据的热点，依次处理批次聚合合并和旧事件增量投影。先做查询/写入次数断言，再测扩大任务数后的曲线；不能仅用“测试通过”或小数据平均耗时证明性能改善。

本轮完成的是定位与方案，不包含业务优化、代码提交、远端推送、服务重启或优化后的流程验收。
