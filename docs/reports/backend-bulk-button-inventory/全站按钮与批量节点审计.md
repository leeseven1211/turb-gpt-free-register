# 全站按钮与批量节点审计

审计日期：2026-11-24（Asia/Shanghai）  
仓库：`/Users/lihongwei/code/personal/gpt/turb-gpt-free-register`  
范围：全站现代 Vue 页面、旧壳模板、动态 JS 按钮、公共交互组件、可见业务 API 及对应后端路由/存储/批量执行层。

本轮只做静态源码盘点和归类，没有修改仓库业务代码，没有提交、推送、部署、重启服务，也没有调用业务写接口。工作区在审计开始前已经存在用户未提交修改，审计保留原状。

## 先看结论

1. 全站已有“批量”按钮大多满足“一次点击、一次数组 HTTP”，但大量后端仍按目标逐条读取、校验、建任务、开事务、写状态或唤醒调度器。一次 HTTP 不等于批量节点。
2. 现有可复用的持久批量平台是 `selection → batch → round → target → Run`，另有 control、lease、outbox、投影和报告能力；当前没有独立通用 `node` 实体，原生目录只覆盖 6 类账号操作：`plan_check`、`token_refresh`、`password_setup`、`twofa_setup`、`codex_retry`、`account_completion`。
3. 最明确的公共缺口是任务中心 `/api/operations/bulk`：它在一次请求内逐条调用单条动作；managed 任务批量重跑时，同一原批次的 N 个目标会形成 N 个单目标 round。
4. 账号域的查活、查套餐、刷新 AT、提链、查封号邮件、补密码/2FA/修改/补全、C2A、Sub2API、注册重跑等，虽有数组 API 或旧批次，仍未统一到公共批量节点。邮箱换绑、Codex 重授权、巡检有各自批次，但任务创建/取消仍存在逐目标路径。
5. 邮箱状态批量、邮箱删除批量、Codex 归档/删除/导出、提链同步原单、支付入口读取等是后续应优先处理的“接口已批量、内部仍逐条”对象；其中同步读取和复制/导出不必默认变成长任务，应按结果恢复和耗时决定是否持久化节点。
6. 注册主流程仍需单独保护。任何后续把注册创建、注册重跑、停止或协议执行迁入节点的方案，都必须保持 Roxy、proto2 和其他驱动的步骤、请求顺序、定位、重试/超时、状态流转及邮箱租约语义；本轮没有触碰这些行为。

## “批量节点”统一判定口径

| 层次 | 需要满足的证据 | 当前常见误判 |
|---|---|---|
| 用户意图/API | 一次请求提交冻结后的 ID 集合或查询描述，带幂等身份；前端不循环调用单条写 API | `Promise.all(ids.map(singleAction))` 仍是 N 个单条请求 |
| 持久控制节点 | 保存本次动作、参数/配置快照、目标集合、受理状态、逐目标结果、重试/取消/恢复边界 | `batch_id`、`operation_batches`、`account_action_batches` 只表示分组，未必是统一节点 |
| 集合存储/调度 | 集合预取、集合资格判定、分块集合建 Task/Run/状态写；事务/SQL 随块增长 | 一个事务内 `for` N 次 UPDATE 或 N 次单条 submit 仍是逐条处理 |
| 外部目标执行 | 认证、邮箱 OTP、浏览器、远端凭证上传、单线路代理检测等仍可按目标执行，但必须受同一节点并发、取消、回执和恢复控制 | 为了“无循环”强行合并不同账号的外部会话 |

## 重点问题总表

| 优先级 | 按钮/区域 | 当前状态 | 需要讨论的节点化方向 |
|---|---|---|---|
| P0 | 任务中心批量重跑/取消/终止 | `/api/operations/bulk` 内逐条读取和调用单条服务；managed retry 一目标一 round | 按来源 batch/动作/参数聚合目标，统一创建一轮和控制命令；保留每 Run 的状态竞争、停止清理和错误回执 |
| P0 | Codex OAuth Token 刷新、Sub2API 手动上传 | 刷新使用旧字符串 UUID 分组；上传逐凭证建 durable task，无 batch | 增加独立 action，集合固定凭证/账号、集合准入和建任务，worker 仍按凭证执行远端请求 |
| P0 | 账号补密码/2FA/修改/补全、C2A、Codex 重授权 | 一次数组 POST，路由/服务逐账号建任务；部分使用旧 operation batch | 统一批量节点/目标回执；单条入口传一个目标复用同一契约 |
| P0 | 邮箱批量状态、删除批量 | 一次 bulk POST，后端逐邮箱独立事务或逐项删除；删除中途异常可能前面已提交但整体失败 | 持久批量回执、分块事务、逐目标跳过/失败/异步退租结果；保留邮箱租约安全边界 |
| P1 | 注册创建、注册任务批量重跑、批次停止 | 一次请求后逐 job；注册 batch 字符串分组，不是公共节点 | 先做不改注册主流程的提交层设计；方案确认后再实施，不能直接套新 worker 改执行顺序 |
| P1 | 提链创建/同步原单/复制支付入口 | 创建已有批量工作台但每账号一个 Task/Run；同步原单、支付入口前端 `for-await` 逐条 POST | 创建继续复用批次/round；同步状态改集合读取/回执；支付入口可一次聚合读取已存产物，不触发支付 |
| P1 | Codex 归档/删除/本地导出/CPA 导出 | 一次数组 POST，但逐凭证读库、更新计数或串行下载 | 集合读取/写回、manifest、受控外部下载；无需把纯本地复制强制变成长任务 |
| P1 | 账号查活/查套餐/刷新 AT/提链/封号邮件 | 兼容 `account_action_batches` UUID，常无法接 native numeric batch；目标仍逐条 enqueue | 对齐公共 batch/target；保留 HME 多别名共享扫描这种真实聚合能力 |
| P2 | 代理池与代理流量页面 | 现代页面均只读，没有用户批量检测/回收按钮；配置页检测固定 1 个 IP | 若未来暴露批量测试，外层建节点，逐出口检测和释放仍按目标执行；后台维护暂不伪装成页面按钮 |
| P2 | 复制、下载、归档、邮箱标记等同步数据动作 | 部分已是集合 SQL，部分只是数组包装；不需要默认创建 N 个 Task/Run | 统一集合服务与逐项结果清单；只有耗时、外部副作用或需恢复时才持久化节点 |

## 后续方案讨论顺序

1. 先确定公共节点模型：现有 batch/round/target/Run 是否作为节点内部执行结构，还是新增 `node` 层；明确单操作节点、多节点依赖、输入快照、状态、控制、回执和错误分类。
2. 优先处理任务中心批量控制和 managed retry 的碎轮次，再处理 Codex refresh/upload、账号补全类和邮箱资源批量写入；这些边界已能用当前源码复现和定位。
3. 对每个域区分“集合读写/任务编排/逐目标外部执行”。外部每账号执行可以保留，但请求线程逐条预取、逐条建任务、逐条独立事务和重复调度唤醒应迁入节点内的分块处理。
4. 注册、邮箱租约、支付/提链等涉及状态安全和外部副作用的动作，先单独提交方案和验证边界；不要把统一批量节点当成修改主流程或放宽重跑门槛的授权。
5. 实施前按当前工作区独立工作区、隔离测试数据库和相关测试验证；本轮没有创建工作区、没有改代码，因此没有测试结论。
