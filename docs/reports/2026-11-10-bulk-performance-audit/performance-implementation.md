# 既有性能热点实施记录

日期：2026-11-10。工作分支：`codex/bulk-task-platform`。本篇记录既有功能热点的实际改造；新批量平台的性能由独立验收记录说明。

## 1. 已实施的改造

### 1.1 凭证定位

- `core/storage/codex/__init__.py` 提供按唯一 filename、显式 filename 集合、规范邮箱的元数据查询。
- Codex Token 刷新提交、刷新后 sub2 同步、sub2 手动上传不再为每个目标调用全库 `list_codex_accounts()`。
- 邮箱匹配沿用原大小写/空白与最新元数据时间、ID排序；表达式索引支持规范邮箱定位。
- worker 仍按原凭证 ID、代次、邮箱身份及账号状态核验；上传提交期间仍重新读取原引用，不能把同名新凭证当作旧目标。
- 周期扫描仍需发现全体到期凭证，这类全范围生产者保留集合读取；单目标路径不再重复全库读取。

### 1.2 任务中心列表

普通列表先按任务筛选和原排序取当前页 ID，再为该页读取有效当前 Run 和运行次数。原生任务排序保持任务创建时间；注册兼容链和旧账号任务继续读取其有效 Run 来源时间。

当前 Run 仍按“有效活跃状态优先，再 run_no/id 倒序”选择，不能直接使用 `last_run_id`。当前页次数使用一次集合查询，原始事件和完整运行结果不参与全局派生。

状态、阶段、结果、搜索、运行次数等依赖 Run 的筛选仍用原集合派生路径；准确的全局 facets 仍按全部匹配任务计算。五列 facets 合并成一条 UNION 查询，共用一次窄字段当前 Run 和次数物化；各列自排除筛选语义不变，不搜索结果时不物化结果 JSON。这些请求保留其数据量成本，未被描述为常数时间。

实施选择与原详细设计的区别：本次优先采用已经验证等价的查询分阶段方案，没有新增尚未完全接通兼容状态更新的持久 current-Run 读模型。读请求不产生新后台修复或隐藏写入。后续如 Run 相关筛选仍成为瓶颈，可继续引入有完整事实更新覆盖的读模型。

曾测试“所有任务逐项 LATERAL 读取”的直接替换，在大规模单 Run 任务下比原集合查询更慢，因此最终仅在当前页和兼容排序所需候选上使用索引读取。失败试验未保留为实现。

### 1.3 满载调度

同一轮每个业务线程池只读取一次容量提示，再扣除本轮已接受数量；最终数据库许可和 `try_submit` 仍作实时裁决。候选顺序、持久公平游标和领域执行步骤不变。

该改造消除 64 个候选导致同池重复 65 次读取容量配置的问题。刚释放的线程名额最迟在下一轮发现；完成事件仍唤醒调度器。

满载等待原因改为一次集合观察：同事务仅读一次容量策略、活动许可和既有等待请求，供应商配置与新批次限额各自集合读取。64 个候选的观察 SQL 总数有固定上限，不再执行64次观察事务。

相同 scopes/原因的连续观察不写数据库；原因或配置变化时合并一次写入。为保留活跃等待展示，每15秒最多一次集合续期。观察记录保持 `observed_only=true`，不改公平游标，不覆盖其他进程真正准入请求及其账号占用原因；单项观察也委托同一实现。

### 1.4 旧任务账号关联

`get_accounts_for_jobs()` 将显式账号 ID 与邮箱回退候选合成一次 SQL；内存中仍先使用显式 ID，只有该邮箱未通过显式 ID 命中才使用邮箱候选，保留重复邮箱与注册归属核验规则。

### 1.5 固定名单与预检

固定名单仍在一个数据库快照中保存，后续预检按最多 5,000 个目标一块处理，内存占用有界。查询套餐及 Codex 预检只读取资格所需列，不加载账号会话或凭据；注册占用查询只取账号和邮箱身份。执行阶段仍重新读取完整业务材料并核验，预检不替代实际准入。

10,000 个目标的客户端 SQL 数从 509 条降至 19 条。冻结后身份与证据保护改为 `AFTER UPDATE FOR EACH STATEMENT`，用 OLD/NEW transition tables 一次集合验证，消除预检更新中逐行查选择状态的内部查询。触发器拒绝冻结证据变更时整条语句回滚；主键重新生成同样被拒绝。初始化会替换同名旧行级触发器，二次初始化不重复重建。客户端 SQL 计数本身不包含数据库函数内部查询，因此耗时复测与数据库约束测试共同作为证据。

## 2. 验证

使用独立 `turb_test` 数据库和随机 `test_` schema。未连接生产库、启动真实业务或调用账号网络接口。

- Codex Token 刷新、持久边界和 sub2 手动上传相关 57 项及 10 个子用例通过。
- 任务列表有效活跃优先、兼容来源时间排序、Run次数/各列筛选、旧任务列表固定查询次数及账号元数据相关定向回归通过。
- 现有满载观察及周边并发 12 项通过，另增加“8个候选仅读取一次线程池容量”的回归。
- 集合观察新增64/8候选SQL数相同（首次观察≤12条，后续不变观察零写入）、策略读取一次、周期续期保留原身份与managed批次限额回归。
- 10组混合筛选对照旧全集合参考SQL，当前页ID/Run/状态/次数/阶段、总数及所有facets一致；6项显式Attempt归属和重复邮箱隔离回归通过。
- 已修改性能代码通过 Ruff 和 Python 语法检查。
- 固定目标触发器真实 PostgreSQL 回归覆盖旧行级触发器迁移、二次初始化、整句多行回滚、主键重新生成拦截及合法投影字段更新；预检资格与执行资格等价、预检分块回执完整性同时通过。

完整性能基准由[批量基准脚本](../../../tools/benchmarks/benchmark_bulk.py)与[任务读取基准脚本](../../../tools/benchmarks/benchmark_operation_reads.py)执行；必须显式传非生产 `DATABASE_URL`，自动创建并清理独立 schema。统计至少 30 次样本才用作 p95 报告。

### 2.1 新批量平台最终规模测量

10万合成账号、100万 Task 与同量 Run，每项30样本，无外部请求。以下为数据库与本地提交流程用时，预览包含固定名单与纯数据库预检；不包含实际网络、代理、邮箱或远端认证时间。[原始汇总](benchmark-bulk-final.json)记录同次测量和 schema 清理确认。

| 测量项 | p50 毫秒 | p95 毫秒 | 客户端 SQL |
|---|---:|---:|---:|
| 500目标固定名单及预检 | 140.6 | 441.6 | 14 |
| 500目标批次受理 | 11.2 | 15.8 | 8 |
| 10,000目标固定名单及预检 | 2,095.2 | 3,373.5 | 19 |
| 10,000目标批次受理 | 10.3 | 15.9 | 8 |
| 100目标集合提交 | 232.3 | 276.0 | 28 |
| 10,000目标批次汇总读取 | 10.1 | 13.5 | 4 |
| 同批50条明细读取 | 6.6 | 9.2 | 3 |

同规模早期版本的10,000目标固定及预检为509条客户端 SQL、p95 10,296毫秒；优化后为19条、p95 3,374毫秒。预检仍未达到最初2秒目标：后台准备1万目标约需数秒，不能宣称已达到2秒。它与快速受理、统计读取分离，页面持续显示准备状态并允许离开后恢复。进一步降低预检成本须另行定位目标写入、结果编码和数据库I/O的占比，不能靠扩大线程数或省略资格校验。

### 2.2 旧任务中心读取对照

同次随机独立schema、10万历史 Task 与同量 Run、1000个合成账号、50条/页；以测量时 `HEAD=5d51c54` 的 `store.py` 与工作区最终实现顺序执行（该文件与本任务起点 `4bccb4c` 相同），每个模式预热一次、测量30次。两版的当前页任务/Run身份、状态、运行次数一致后才输出对照。[原始汇总](benchmark-operation-reads-final.json)保留完整毫秒数据。

| 模式 | 改前 p50 / p95 毫秒 | 改后 p50 / p95 毫秒 |
|---|---:|---:|
| 普通列表，不带facets | 900.9 / 1,435.2 | 98.8 / 110.0 |
| 普通列表，完整facets | 1,356.9 / 1,521.5 | 797.0 / 865.7 |
| 状态筛选，不带facets | 1,080.8 / 1,309.3 | 887.3 / 1,103.7 |

普通列表 p95 约降低92%，完整facets约降低43%；Run状态筛选仍需读取全体候选事实，本次只约降低16%，不能作为恒定时间读取宣传。全局准确facets与状态等Run相关筛选仍随历史规模增长。深页、混合多Run、真实注册兼容来源与不同硬件负载需另测，这组10万数据不替代百万规模的任务中心读取基准。

更早的大规模联合验收曾遇到共享Docker/PostgreSQL服务退出，恢复原服务后已完成上述最终测量。没有证据把退出原因归于某条查询；该中断前的样本不混入最终对照。最终两组基准都清理了各自的随机测试schema。

## 3. 交付边界

本轮交付包含代码和隔离验证，不包含推送、重启或部署；Git 合并状态以实际交付回执为准。新批量平台已在100万历史Task/Run下完成30样本测量；旧任务中心列表本次对照为10万规模，不能互相替代。两端真实部署性能仍须分别验收。任务列表对全局准确 facets、Run相关筛选及深页保留原计算成本；集合观察的固定SQL预算不等于整个候选发现查询已固定成本，原队列多层排序仍须单独测量。
