# 统一批量任务管理与性能改造方案

日期：2026-11-10。状态：待评审设计，未实施业务改造。

本篇为总体方案；已进一步形成[实施级详细设计](detailed-design.md)，覆盖数据与事务、API与领域适配、界面与验收、性能与运行四个分篇。具体字段、排序、配置覆盖与迁移门槛以详细设计为准。

本文承接[性能调查](README.md)，并纳入用户新增需求：专门菜单创建和管理批次，选择查询套餐、补密码、补 2FA、补 Codex 等操作，复用现有列表列筛选，按批次展示进度、结果统计和失败处理。用户明确：日期与当前列表日期列一致，筛选条件应联动；架构不合理的部分允许在方案中调整。

## 1. 推荐方案与边界

新增一级菜单“批量任务”，由一个公共批次平台提供选择、受理、执行关联、统计、重跑和页面框架，各账号功能提供自己的参数、资格判断与结果适配。保留现有 PostgreSQL、任务/Run、领域服务和并发许可体系。

方案的三条主线：

1. **列表与批量选择同源。** 现有列筛选抽取为共享查询契约，预览与实际固定清单使用同一版本；不复制另一份前端条件或 SQL。
2. **批次是用户意图，Run 是执行事实。** 固定目标、执行轮次、单账号动作与功能结果分别建模；批次统计不会被账号后来变化或其他批次重跑污染。
3. **快速受理与高吞吐分别解决。** 快照预备、创建批次、分块建任务、实际执行、结果投影都有单独耗时预算，不能仅把慢请求藏到后台。

第一批交付必须完整覆盖查套餐、补密码、补 2FA、补 Codex，以及相关批次列表、详情、失败重跑。查套餐先作为纵向验证样本，不把只支持查套餐当成全部交付完成。组合补全沿用现有规划器，随后纳入同一验收。

本轮交付设计文档与示例原型，不修改注册或账号执行行为。注册重跑、注册并发调度、提链/支付执行规则若需调整，分别提供受保护边界的具体方案；不能用公共辅助层间接改变注册主流程。

## 2. 用户实际怎么使用

### 2.1 从批量任务新建

进入“批量任务 → 新建批次”，依次填写：

- 操作：“查询套餐”。
- 账号范围：沿用账号列表的归档范围、创建日期、套餐优惠等列筛选；例为 2026-10-01 至 2026-10-31、套餐优惠“无优惠”。不额外暗加用户未选的筛选。
- 执行设置：本批并发上限及已有服务允许覆盖的查询参数。当前查询国家取配置快照并只读展示；筛选历史优惠所属范围与本次查询国家分别表达。
- “预览并固定账号范围”：显示固定名单的数量、当前可执行/被占用/明确不符合项和少量分页样本。
- “创建并运行”：保存批次并立即进入详情；后台分块提交，页面关闭后继续运行。

列表当前“无优惠”可能保留上次成功查询的结论，即使最新一次查询失败。新菜单第一版完全复用当前列筛选语义；预览额外显示证据时间、最近查询状态，不静默排除或纳入其他集合。后续增加“最近查询状态”“上次成功时间”等字段时，两处共同提供。

查询套餐是主动刷新，即使原来查询成功仍然执行，不能套用组合补全“已有结果就无需补”的判定。

### 2.2 从账号列表进入

新增“按当前筛选创建批次”，将当前筛选对象、归档范围和固定排序带入；不传当前页全部账号 JSON。原查套餐、补密码等快捷按钮保留，选中账号时携带显式 ID 集合和对应操作。

必须区别：“本页勾选 50 个”“跨页已选 120 个”“当前筛选全部匹配 2,000 个”。显式 ID 与全筛选是互斥的目标来源；不能用当前页数据冒充全筛选。

从新菜单返回账号列表时可选择“查看相同筛选”；批次已固定的目标则通过“查看本批账号”查询快照，不能重新套原条件让处理过的账号消失。

### 2.3 重跑与重复使用

| 操作 | 范围 | 执行归属 | 历史表现 |
|---|---|---|---|
| 重跑失败/未完成 | 本批目标中选定状态的固定子集 | 同批新执行轮次，保留原 task 检查点 | 首轮和各重跑轮不变，当前结果另算 |
| 同一批账号再次执行 | 原固定清单，可从结果筛子集 | 新批次，标记来源批次 | 原批次不变 |
| 复制条件新建 | 重新查询现在符合条件的账号 | 新批次和新快照 | 人数可变化，清晰显示新固定时点 |

“重跑未成功”不要求逐账号人工核对。领域适配器根据原 Run 事实选择正常重跑、原身份恢复或回执确认；逐项返回接受、等待、无法执行及明确原因。不能因远端未返回就统一封锁重跑，也不能把已有活跃 Run 当作本轮新执行。

## 3. 页面与信息架构

### 3.1 与现有菜单的关系

| 菜单 | 主要职责 |
|---|---|
| 账号 | 查看账号当前状态、列筛选、快捷操作 |
| 批量任务（新增） | 管理用户批次、固定账号范围、执行轮次和结果统计 |
| 任务中心（现有） | 查看具体逻辑任务、Run、阶段、日志、资源和诊断 |
| 提链工作台（现有） | 平台材料、提链、支付与到账等业务专页；后续接统一批次概览 |

单账号执行与批次共用事实，不另起一套队列。任务中心增加所属批次链接，批次账号行打开现有 Run 详情。现有巡检默认全范围的规则保留，不能因为共享新页面就偷偷改为受账号筛选影响。

### 3.2 批次列表

主要列：名称/ID、功能、范围摘要、状态、已结束/目标数、成功/部分成功/失败/未执行数、创建时间、当前轮次。筛选：功能、批次状态、创建日期、名称/ID。

“已完成”只表示本轮不再有活动项，旁边显示“失败 12”等结果，不能把结束统一画成全部成功。默认 20 条/页，统计与响应只随当前页增长。

### 3.3 新建批次

使用完整子页面：桌面主表单与右侧范围摘要，手机顺序单列。公共部分只有操作、名称、目标来源、共享列筛选、预览和执行设置；选不同功能只更换专用参数和推荐显示的筛选项，其他合法列条件仍可使用。

筛选定义与列表一致：同列多选 OR、不同列 AND；第一版不做任意嵌套表达式编辑器。修改条件后旧预览失效，保存已填写的其他参数；选不同操作时保留合法共享条件，明显提示参数变化，不无声清空用户条件。

支持全部匹配或最多 N 个，限制时展示固定排序并用 ID 兜底。预览不启动业务、不占用账号，只保存选择快照及必要证据；“被占用”不是未匹配，仍保留在目标范围中。

### 3.4 批次详情

顶部：名称、功能、固定范围时间、条件摘要、并发设置、批次状态和执行轮次切换。主体：

1. 共用进度：目标、待提交、等待账号、排队、执行/等待外部结果、成功、部分成功、失败、未执行、取消、待确认。
2. 功能结果面板：查套餐显示套餐/优惠分布；补密码/2FA 显示确认结果；Codex 显示凭证确认；组合补全显示每能力达成情况。
3. 明细表：账号、执行状态、当前阶段、业务结果、错误分类、耗时与查看执行。功能扩展列控制在必要范围。
4. 条件/配置快照、轮次历史、日志按需打开。点击统计数字和错误分类筛选明细，维持分页、滚动位置和已选项。

进度是“已结束账号 / 本视图目标账号”，不是成功率。每轮显示本轮目标数；“批次当前结果”以固定批次目标数为分母，按每个账号最近被请求的轮次计算。重跑请求尚未建 Run 时，该账号即为本轮待提交，旧失败留在历史中，不能在主视图同时计入失败和排队。

手机端保留名称、进度、失败数及主要按钮；次要列折叠，失败全文可点击展开。支持刷新/后退/深链接恢复批次 ID、轮次和结果筛选，不能仅靠全局 JS 变量保存位置。

## 4. 共享筛选契约

### 4.1 抽取现有定义，不重写另一套规则

把现有 `accountListQueryParams()`、`admin_repository` 的列条件及搜索解析统一到版本化的 `AccountQuerySpec`。现有 URL 参数先由兼容适配器转成规范对象，列表、批量预览、固定清单和导出共用编译器。

建议对象示例（API 设计稿）：

```json
{
  "schema_version": 1,
  "entity": "account",
  "archived": "0",
  "date_from": "2026-10-01",
  "date_to": "2026-10-31",
  "filters": {"promotion": ["none"]},
  "q": "",
  "order": [{"field": "id", "direction": "desc"}],
  "limit": null
}
```

字段、运算符、排序与枚举全部白名单化并参数化查询，客户端不能提交 SQL。日期沿用列表的“创建 / 更新”列中创建日期口径，当前代码按 `created_at` 前十位日历日期比较，结束日包含在内。**不把它改叫已验证的远端注册时间，也不在新菜单独自做时区转换。** 若迁移为有类型的日期/时间列，先建立旧日历值到新列的对照，证明两处结果集合一致，再一同切换；历史无效/缺失日期明确保留。

搜索、归档范围、套餐/优惠、来源、注册驱动、Token、密码、2FA、风险、Codex、账号状态、邮箱状态等现有条件完整联动。跨账号与 Codex 凭证列表使用同一个字段框架，但保留实体差异，不能把凭证更新时间映射为账号创建日期。

### 4.2 筛选与可执行资格分离

现有密码列“有/无”表示本地是否有值；不能在批量页悄悄改成已确认。2FA 启用标记、完整可用材料、远端确认也不是同一个事实。保持列筛选原含义，预检单独返回：可提交、等待账号、功能不可用、材料不足、账号已废/已删除等。

需要更细筛选时新增共同字段，如“密码确认状态”“2FA 材料状态”“Codex 凭证状态”“最近查询状态”，两处同步可用。缺 AT 可能可由现有自动刷新恢复，不得仅凭字段为空就拒绝本来可执行的任务。

预检只作本地批量查询，不发认证、查套餐、邮箱或代理请求。创建/领取时继续做必要原子校验；预览可执行不保证稍后一定成功。目标身份固定，最新安全条件变化只能产生等待/未执行等明确结果，不能悄悄替换账号或扩大范围。

## 5. 功能扩展契约

建议目录放在 `core/bulk_operations/`，各领域模块注册 `BulkOperationDefinition`：

| 属性/适配器 | 责任 |
|---|---|
| key / version / target_kind | 用户功能标识与版本；账号或凭证等实体 |
| filter_profile / parameter_schema | 推荐共享筛选项、功能参数及约束 |
| capability / preflight_many | 当前部署是否可用、批量本地资格与原因 |
| prepare_many / submit_chunk | 读取必要字段、一次配置快照、分块持久提交；返回 owned task/run |
| result_adapter / result_schema | 从本轮具体 Run 与依赖生成结果、统计贡献与明细 |
| retry_adapter | 沿用领域恢复入口与检查点，核验是否真正生成新 Run |
| controls / result_columns | 可支持的控制动作与专用界面字段 |

目录与 `task_gateway` 的 handler 注册分层：目录编排用户批量意图，handler 仍负责真实动作。前端渲染固定组件和受控字段，不执行服务端下发任意代码；特殊结果面板可注册小组件，公共页面不堆积大量功能判断。

| 功能 | 原有筛选联动之外的可选扩展 | 执行与结果重点 |
|---|---|---|
| 查询套餐 | 最近查询状态、上次成功时间；后续可选国家/套餐证据 | 每次刷新；成功无优惠仍是成功；逐国成功/失败、Free/Plus/Go、Plus 优惠 |
| 补密码 | 密码候选/确认状态 | 保留现有补密码语义；与改密/重置分开；确认原密码和新补密码分别统计 |
| 补 2FA | 本地材料缺失/待确认/完整 | 使用既有确认结果；补与更换分开；不能仅看到启用标记就算本轮成功 |
| 补 Codex | 凭证缺失/已确认/需重授权；最近执行状态 | callback 回执与可用凭证分开；旧凭证仍可用和本轮失败可以同时成立 |
| 刷新 AT / 查活 | 到期、最近检查/刷新结果 | 复用原驱动；401 不等于废号，缺 Token 不一律不可运行 |
| 组合补全 | 缺失能力集合 | 复用现有规划器，不建立任意 DAG；账号总结果与每能力结果分别计数 |
| sub2 上传 / Codex Token 刷新 | 凭证和目标状态 | 按 ID/filename 批量定位，保留代际校验，不每项全表找凭证 |
| 提链/支付、换邮箱、导出 | 各领域自己的条件和参数 | 后续适配；付费、付款结果、Plus 到账、凭证导出分别保留业务语义 |

当前补密码、2FA、组合补全的部分领域协调位于 `webui/runtime.py`。必须先提取到 `core/accounts/`，WebUI 改为薄委托；保持已有步骤顺序、认证方式、配置、重试和错误规则。新 core 批量服务不得反向依赖 WebUIContext。

## 6. 固定范围与快速创建

推荐把固定范围放在预览阶段，使用可持久化的选择快照：

1. `POST /api/bulk/selections` 保存查询/显式 ID、定义版本、排序、数量上限，快速返回 selection ID 和 preparing 状态。
2. 后台在一次 MVCC 语句快照内执行 `INSERT ... SELECT`，只复制目标身份、排序和必要筛选/比较证据；不锁定全库账号，不创建业务任务。可用同一 SQL 的集合运算准备轻量预检材料。
3. 名单与状态在同一事务提交为 ready，记录实际 `selection_at`、总数、修订号与摘要。页面只在 ready 后显示可提交的最终数量。大范围准备较慢时真实显示准备中，不编造百分比。
4. 用户确认后 `POST /api/bulk/batches` 原子消费 ready selection 并保存操作参数、配置修订、并发上限、首轮和幂等键，返回 202/batch ID。此事务不复制 N 份任务，也不遍历全部目标。
5. 后台按索引取有界目标，每块先批量读取所需字段，再调用领域批量适配持久化 task/run、账号状态和精确关联，提交后统一唤醒。

只有一次语句/同一事务快照的集合查询能保证该次范围一致；不能用多个独立事务的 ID 分页查询却宣称同一冻结时点，也不能长期持有账号行锁获取“精确快照”。超大范围若需不同方案，必须明确一致性成本和语义，不能改变上述承诺。

首次预览到提交之间，名单保持不变；不再因原条件变化自动剔除目标。提交时明确预览固定时间，提供“重新预览”按钮。过期未使用快照不可提交，重新生成并显示新数量。已消费快照归批次持有，不按预览 TTL 清理。

取消、重启与回执丢失：准备事务失败则无半份 ready 清单；后台重试采用 owner/租约与代际；创建请求使用稳定幂等键+请求摘要，键相同内容不同返回明确冲突。同一请求重发返回原批次，用户主动新建/新轮使用新意图，不被永久去重。

### 6.1 分块提交与等待账号

建议初始块大小 100，按事务时间和锁等待调整，而不是固定越大越好。批量预取、配置归一化、明确序号、复用连接和集合写入优先；不要简单把当前 10 条 SQL/账号的循环搬到后台后就宣告完成。

固定全部目标后，只展开有界的待执行窗口，按不同批次公平轮转补充；不要一次生成十万个 queued Run 并抢占十万个账号唯一名额。窗口大小结合实际并发与准备速度定标，不成为用户目标总数上限。初始轮次明细尚未全部物化时，用固定总数减去已准备计数表达待提交数，不靠全表COUNT补齐，也不遗漏取消未物化目标的范围。

每个目标创建任务的幂等标识由批次、轮次、目标和动作组成；创建任务、账号 queued 状态、目标运行关联及展开进度必须在同一事务提交。逐项业务约束失败可通过保存点或集合校验记录原因；系统性 DB 故障回滚该块并恢复，不能伪报整块全部成功。

同账号被其他操作占用时保留 waiting_account，记录 blocker 引用、下次可尝试时间；不把另一批的活跃 Run 计成本批执行，也不跳过丢弃。释放信号加有界退避重检，不逐秒重扫所有等待项；长等待可提示并允许取消，不因任意固定等待时长自动丢任务。

## 7. 数据模型与事实归属

### 7.1 复用与新增

继续复用 `operation_batches` 的批次身份，`operation_tasks/runs/events/resources` 的执行事实与许可。现有 `operation_batch_items` 的 task_id/run_id 均为 NOT NULL，只适合已经生成 Run 的关联，不能塞入“已选但未建任务”的账号。

以下六种关系是总体职责分解；详细设计另外增加持久 `operation_projection_outbox` 和 `operation_batch_control_commands`，并给出确切字段、约束与锁序：

| 结构 | 关键内容与约束 |
|---|---|
| `operation_selections` | 条件/选择来源、版本、排序、状态、固定时点、总数、owner/租约、TTL；可被一个新批次消费 |
| `operation_selection_targets` | 固定目标 identity、ordinal、轻量匹配证据与比较基线；唯一(selection_id,target_kind,target_id)，唯一(selection_id,ordinal)。已消费目标可另带可重建的latest_requested_round投影，不能改动固定身份与证据 |
| `operation_batch_controls` | 1:1 batch_id、selection_id、功能/结果schema版本、参数/配置修订、控制状态、幂等键与请求摘要、控制修订 |
| `operation_batch_rounds` | batch_id、round_no、首轮/重跑、成员selection_id、目标数、受理键、状态、时间与结果修订；唯一(batch_id,round_no) |
| `operation_batch_target_rounds` | round_id、固定目标引用、本轮入队状态、等待原因、重跑来源、规范结果、贡献版本、已聚合贡献；唯一(round_id,target_ref) |
| `operation_batch_run_links` | target_round、task/run、step_key、relation、代次；唯一的拥有关系，区分本轮拥有的执行与外部阻塞引用 |

这是六种不同职责，不是六套任务存储：目标表固定选择，轮次成员记录提交/统计；业务执行状态仍只由 Run 及领域事实产生。目标明细不复制密码、Token、Cookie或完整凭证。创建批次消费 selection，首轮明细后台幂等分块创建，创建接口不复制整份名单。

轮次摘要可作为 round 的可重建字段/JSONB，批次当前摘要由单独投影维护；查询常用的控制/状态/错误码/排序字段使用有类型列，少量版本化功能结果存 JSONB。不要把全量目标数组、所有失败原因或全部运行结果写进批次的一行 JSON。

新管理批次的现有`_refresh_batch`调用必须明确转入专用计数/dirty分支，不能先按旧root/latest状态重算，再由新projector覆盖；统计写入所有权在代码层唯一化。旧批次继续原汇总，管理模式缺失时不得猜测属于新模式。

账号删除后保留固定 identity 与必要展示快照，记录 account_missing。批次/轮次对 owned Run 的引用必须纳入历史保留约束，不能让现有清理 CASCADE 把还在展示的历史明细删掉；不能为保持 FK 而阻断正常账号删除。

### 7.2 重跑与执行轮次

采用同一批次内新增执行轮次，原因是当前 `retry_runtime_task` 沿用原 task 与 batch_id。若直接新建一个“失败重跑批次”却调用旧 retry，执行配额和归属仍在旧批，会形成统计错误。

新轮固定目标子集与来源 Run，调用现有 retry adapter 并记录其返回的确切新 Run。返回 reused/原活跃 Run/dependency_stale 必须有不同处理，不能算作本轮已创建。重跑规则仍以领域事实为准，不清空检查点、不覆盖旧结果。

重跑轮也需要持久成员快照：selection target 保存原批目标引用、来源target_round/Run，不能仅存“失败”条件后逐块重查。异步准备时显示preparing，冻结成功后才宣布本轮最终目标数。在同一冻结事务中，批量更新所选目标的latest_requested_round归属及初始计数贡献；成员/最新归属不能等task生成后才确定。首轮与重跑轮统计均独立于target_round已物化行数。并发重跑在成员冻结与领取事务中校验目标归属和活动轮次，不能只靠最后创建Run的唯一约束兜底。

重跑接口可先可靠受理准备请求并返回202，成员冻结另由后台完成；只有冻结提交后才切换对应目标的当前轮次。若需要同步确认精确人数，则先调用选择准备接口，再消费ready快照创建轮次，不能把动态筛选与大批量归属更新塞入“固定500毫秒”的响应承诺。

所有入口对新管理任务的人工重跑都经过此轮次适配，包括任务中心、Run详情和旧快捷入口；一个账号手动重跑也产生单成员新轮。内部调用显式区分manual与dependency续接：只有自动依赖续接继承当前轮，不能让`retry_runtime_task`合并旧data时把人工新Run误挂旧round。旧非管理任务继续使用原行为。

首轮和每个重跑轮的结果只依据本轮拥有的执行，后续账号状态与其他轮次不改写它；原 Run 合法补齐回执或修正事实时可修订对应轮次并保留修订记录。“当前结果”是每个固定目标最近已固定成员轮次的投影。例：首轮 100 个失败 10 个；重跑 10 个成功 8 个，则首轮仍失败 10，重跑轮成功 8/失败 2，当前结果失败 2/重跑恢复 8。

同一目标不允许在两个活动重跑轮中同时执行；只对冲突目标等待或复用同一受理请求，不能因少量占用拒绝整批。允许部分失败先重跑、其他账号继续跑，但轮次选择和计数必须明确。

### 7.3 组合补全特别约束

一个 target_round 可有多个父续接 Run 与子 Run。“一轮”不等于“一个父 Run”。在最初提交、子任务提交、依赖完成续接时显式传递 batch/target/round/step 上下文并记录拥有关系。

当前依赖续接会新建父 Run，部分 setup 子任务缺显式 parent/batch 关联。因此实施前要补全关联，不得靠时间戳、同邮箱、当前 last_run_id 或父子树猜历史归属。等待外部既有任务的 blocker 与本轮 owned_child 必须分开。

父任务暂时 partial_success 可能仅表示子任务已提交；只要必需子步骤仍在运行或有待续接，本目标仍是 waiting/running。账号成功必须以本轮必需步骤的真实确认结果为依据，不能以提交成功或父 Run 的临时状态判成功。

## 8. 状态、统计与错误

### 8.1 控制状态和业务结果分开

- 选择：preparing / ready / failed / expired / consumed。
- 批次控制：active / cancel_requested / stop_requested / ended；暂停作为后续独立能力。
- 目标轮次入队：pending_submit / waiting_account / submitted / not_executed / cancelled。
- submitted 的执行状态来自所绑定 Run/依赖，统一投影 queued / running / waiting / success / partial_success / failed / cancelled / attention_required。
- 业务结果由功能适配器给出，不能从状态码或日志关键词猜测。

适配器必须穷举已有原始状态，并保留source_status与原因码：settling属于仍在执行/收口，request_unknown映射待确认；无待续接的interrupted是中断失败；stopped有取消证据才计取消，否则按中断处理；deactivated区分预检已废而未执行与本轮执行确认停用；unsupported记录未执行及原因。增加原始状态时契约测试强制补映射，禁止漏计或统一吞成失败。

名单固定前总数未知；固定后目标集合不再变。共用统计使用互斥分类，使下列恒等式可验算：

```text
目标数 = 待提交 + 等待账号 + 排队 + 执行/等待外部结果
       + 成功 + 部分成功 + 失败 + 未执行 + 取消 + 待确认
```

每个账号在当前视图只落一个类别；组合子步骤数另列。预检阶段“已满足”只有领域服务明确跳过才计未执行/已满足，不能因为有历史套餐结果就跳过主动刷新。

### 8.2 功能统计

查询套餐：执行成功且无优惠属于成功。优惠分布只用本轮成功证据，不能把失败账号旧的无优惠结论冒充本轮无优惠。国家项统计标“国家查询项”，合计可大于账号数；账号分布采用确定规则且一账号只计一次。

部分国家成功时可展示“已发现优惠”，但“所有所选国家均无优惠”必须全部有成功证据。前后变化只比较同产品、同国家范围和可靠基线；没有基线标不可比较，不算新发现或消失。

补密码/2FA：本轮新确认、验证已有值、原本满足、失败分开。Codex：新凭证确认、回执待确认、失败与原资产仍可用分开。组合补全：总账号结果和每能力成功/失败/未执行分开。

“新设置”与“验证已有值”的细分必须有本轮领域证据；旧服务只证明确认成功时显示“已确认，变更方式未记录”，不根据前后是否有密码/secret猜测远端动作。

### 8.3 不在每次刷新扫描整批

Run/依赖更新时，在同一事实事务中将对应 target_round 标记为结果待投影；对已有写入暂不能纳入同事务的适配，必须用持久 outbox 或可证明不漏的补偿游标，不能仅发内存事件。

投影 worker 批量锁取 dirty 行，按 source_revision 计算新贡献与已应用贡献的差值，在一个事务内更新目标结果、计数/结果分布、已应用修订与 summary_revision。重复消息不重复加计数；旧代结果不能覆盖新代。对同批/轮计数合并更新，避免每账号争同一摘要行、每次整批 GROUP BY。

列表读预计算摘要，明细分页读目标结果；允许约 2 秒统计滞后并显示更新时间/同步状态。结束判定要确认本轮展开已完成、无活动目标且计数同步到最终版本，不能看 queued=0 就判结束。全量校验用于修复/验收，失败可重建，不能每 2 秒执行一次全量重算。

新增数据和系统错误分类至少包括筛选非法、快照过期、选择准备失败、配置不可用、账号占用/已废/不存在、凭证代际变化、任务持久化失败、投影滞后、恢复 owner 未确认。继承领域原因码和阶段；历史证据不足明确标缺少哪类证据，不能伪造根因或统一吞成“未知错误”。

## 9. 控制、恢复与资源

第一版提供“取消未开始”和“请求停止”，复用现有安全检查点；展示接受与实际停止完成的区别。“未开始”以账号链首次执行为界：取消尚未启动的目标，包括尚未物化的固定成员；已开始账号的必需子任务和续接继续完成，不能一概取消所有queued Run。“请求停止”才对运行中账号调用已有停止流程。取消与展开/Run首次认领在提交事务内检查同一批次控制修订，不能只在前端或第一次候选查询检查。取消后的名额和已占资源按现有收口规则释放。

暂停建议第二阶段再提供“暂停后续账号”：停止新的账号链启动，已经开始的账号及其必需子任务正常收口，显示正在暂停/已暂停。它不强行冻结线程或远端页面，也不截断组合补全。若实现，门闩只作用于新管理批次 owned 的首次执行；旧任务、注册及 blocker 不能被关联暂停。

选择准备、展开、统计投影都必须有持久 owner、租约/心跳、递增代次和恢复入口。各块可重放并原子推进，宕机不留永久 running；owner 未确认退出时沿用现有许可安全规则，不单凭超时启动重复业务。

沿用全局/类型/批次/平台/账号并发上限。UI 显示“本批上限”和“实际执行数/等待原因”，不把旧 ACCOUNT_BATCH_WORKERS 当全局有效并发。协调和投影任务不占浏览器/业务执行名额，但有自己的受控容量。

## 10. API、分层与性能预算

### 10.1 接口建议

| 接口 | 用途 |
|---|---|
| `GET /api/bulk/catalog` | 功能与共享筛选目录、部署可用性、公开参数/结果schema |
| `POST /api/bulk/selections` | 准备条件/显式ID选择快照，返回202 |
| `GET /api/bulk/selections/:id` | 固定进度、总数、预检摘要、游标分页样本 |
| `POST /api/bulk/batches` | 消费快照、可靠受理新批次；幂等键+摘要 |
| `GET /api/bulk/batches` | 游标分页批次摘要；类型/状态/日期等过滤 |
| `GET /api/bulk/batches/:id` | 公共/功能统计、控制状态、summary_revision |
| `GET /api/bulk/batches/:id/targets` | 当前或指定轮次账号明细；状态/原因/业务结果过滤 |
| `POST /api/bulk/batches/:id/rounds` | 固定失败子集并可靠受理重跑轮次 |
| `POST /api/bulk/batches/:id/control` | 取消未开始或请求停止；期望控制版本 |

正常 GET 不查询外部接口、不触发重投影或重建整个批次。大量显式 ID 用请求体/已选快照，不塞 URL。日志/完整结果继续使用原 Run 详情接口。

### 10.2 代码责任

`core/accounts/query.py`（建议）统一字段与选择语义，`core/storage` 编译并执行 SQL；`core/bulk_operations` 定义目录与受理/轮次/分块编排；各领域 service 负责原有真实行为；`webui/routes/bulk.py` 只校验公开请求与返回结果。前端复用筛选组件和分页，新增 batch-list / batch-create / batch-detail 模块，不复制整个账号页。

SQL 可放专用 repository，但 core 不导入 webui。存储层变更在独立工作区与独立测试库做；业务事实/队列只有 PostgreSQL，不用 JSON 文件或进程内列表作可靠任务源。

### 10.3 必须同时解决的既有性能问题

| 瓶颈 | 对应改造 |
|---|---|
| 500 个入队约10秒、5,001 SQL | 固定选择+快速受理；真正分块/集合提交，减少每项重复读与事务往返 |
| Codex/sub2 每项读全库 | 按 id/filename/email 批量定位，保留原代际与身份校验 |
| 队列满仍重复观察64项 | 配置每轮复用、满载退让、等待原因变化时写；与最终准入分离 |
| 队列多层全候选排序 | 有界候选、公平选择和领取索引；证明原公平/配额语义不变 |
| 任务列表全历史聚合 | 维护当前有效Run、排序时间和次数投影，不能直接拿last_run_id替换活跃优先语义 |
| 每项结束/取消重汇总全批 | 目标贡献增量投影；旧批次分组一次汇总，迁移时明确计数所有权 |
| 大响应与多接口串行刷新 | 摘要/当前页/详情拆分，revision驱动，无变化不重绘 |
| CPA目录重复拉取、串行压包 | 独立后台导出，目录一次匹配，有界下载；后续里程碑 |

新增索引围绕 selection/ordinal、round/status/ordinal、target identity、ready_at、dirty projection 和批次创建排序；有 partial unique 保证每目标轮次、拥有Run和幂等身份唯一。根据 EXPLAIN ANALYZE/BUFFERS 与压力测试定列顺序，不把所有 JSONB 都建 GIN。

### 10.4 性能验收目标

以下是建议门槛，均为待压测目标，不是已达到的承诺。使用明确硬件、空闲/满载两组、冷/暖态分开，至少30次稳定样本报告p50/p95及最大值：

| 环节 | 建议目标与检查 |
|---|---|
| 点击反馈 | 100毫秒内显示提交/准备状态 |
| 新批次/重跑受理 | ready快照前提下p95≤500毫秒；创建事务不随目标数逐项写任务 |
| 条件固定快照 | 500/5,000/10,000目标分别测；10,000目标以≤2秒为初始目标，超时可恢复并真实显示准备中 |
| 后台展开 | 单独测目标/秒、SQL/目标、事务/块；吞吐目标由首个纵向基准确定，明确证明优于当前约48项/秒的空闲入队样本 |
| 批次摘要、50条明细 | 10万账号、100万历史Run压力下p95≤300毫秒；计数和响应不随完整历史线性扫描 |
| 活动进度 | 约2秒刷新；结果投影正常滞后≤2秒，结束状态一致 |
| 满载调度 | 无空位时额外查询/写入有固定预算；不随积压账号数每轮线性增长 |

前端活动摘要约2秒、列表5—10秒，筛选选项低频或按需；隐藏页面和结束批次停止轮询，旧请求不能覆盖新选择。优先普通增量轮询，确有收益再加SSE，不为实时感一次推送全体账号。

## 11. 实施顺序与并行分工

不先逐个大修几十个旧接口再另做新批次平台，避免重复施工。建议五个可验收里程碑：

| 里程碑 | 工作内容 | 完成条件 |
|---|---|---|
| M0 契约与隔离基线 | 筛选同源、现有服务契约、固定范围/轮次模型、前端原型、压力数据 | 设计定稿；列表与选择集合对照、状态与统计口径可测试 |
| M1 公共底座+查套餐 | 选择/批次/轮次/目标关联、恢复、增量统计、三页面、查套餐适配 | 用户10月份无优惠案例完整跑通，500/10,000目标可测，首轮/重跑历史不变 |
| M2 用户必需功能 | 协调下沉core、补密码/2FA/Codex适配与专用结果、消除凭证全量查找 | 三功能共用页面和底座；不新增复制版任务执行器；旧单条与批量行为一致 |
| M3 组合与入口整合 | 组合补全精确上下文、账号快捷按钮迁移、任务中心链接、批次控制 | 父续接/子Run不串轮；取消/重启/交叠批次回归；完整用户需求验收 |
| M4 规模化与其他模块 | 队列/历史读模型优化、提链/巡检概览适配、邮箱资产与导出按风险接入 | 大数据与满载门槛、本地和Oracle分别验收；注册相关变更单独确认 |

M1底座模型定稿后可以并行：A存储/选择/轮次，B批量编排/领域适配，C三页面与筛选组件，D契约测试与性能/恢复测试。先锁定API、状态枚举、结果schema和目录文件所有权，再并行开发，避免多人同时修改巨型store/runtime。

M2四个功能可按领域并行，组合补全须等待owned Run上下文贯通。队列优化只在影响范围与行为验证清楚后合入；跨进程Web/worker拆分作为实测资源争用后的选项，不预先引入Redis/Celery、任意DAG、跨本地/Oracle调度或通用插件市场。

## 12. 关键验证与发布

必须覆盖：

- 相同列条件在账号列表与快照得到相同ID集合，日期边界、多选、搜索、归档、历史优惠/失败语义一致。
- 刚好在预览前后修改账号状态、插入/删除账号，固定范围时间与最终清单一致；查询后优惠变化不让成员消失。
- 同键重发、回执丢失、不同内容复用键、重复点重跑；不丢任务、不误建新轮、不永久拦用户重跑。
- 两批重叠账号、忙账号后续可执行、取消与展开/认领竞态、展开中断/进程重启、旧owner回写。
- Run先结束再收到事件、投影重复/乱序、统计恢复、计数恒等式、重跑后原轮结果不变。
- 密码候选/确认、2FA仅标志/材料、Codex回执/凭证、套餐部分国家成功、旧资产可用但本轮失败。
- 组合父Run临时partial、依赖续接产生新Run、子任务跨轮回调、等待外部既有Run不占本轮成功数。
- 清理与账号删除后历史报告可解释，任务保留不会错误CASCADE；预览TTL不删除已消费目标。
- 桌面和360/390像素手机真实浏览器，键盘、深链接/后退、慢请求、断网重连、条件失效、分页选中与焦点保留。

上线使用新增结构与兼容读写过渡。新批次由独立标记/目录版本识别，旧批次仍走旧投影；同一摘要不能由新旧两个worker同时写。小批量灰度后迁移快捷入口，保留老批历史，不要求一次重建全部任务数据。

回退须先停新受理与展开、排空或明确保留所有新任务，然后切回兼容版本；不能让旧代码忽略新控制和新清理引用而误执行/删除任务。新增表与已受理数据保留，由兼容worker继续处理或等待恢复，不能靠删表回退。

本地与Oracle独立发布、独立配置和数据验收。先代码评审与定向/隔离/恢复/性能检查，再提交、推送并核对远端版本，之后才部署该提交。Oracle现有独立移动端等提交必须保留。发布记录明确区分代码修改、测试、提交、推送、重启和真实业务验收。
