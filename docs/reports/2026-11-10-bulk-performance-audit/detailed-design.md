# 批量任务平台与性能改造：详细设计

日期：2026-11-10。版本：设计 v1。状态：可用于拆分开发与验收，尚未实施业务代码。

## 1. 设计结论

建议建设一级菜单“批量任务”，统一管理选择范围、批次、执行轮次、进度、结果和批量重跑。查询套餐、补密码、补 2FA、补 Codex、组合补全接入同一套底座，各自保留业务参数、资格规则和结果展示。

现有 PostgreSQL、任务/Run、领域服务及并发许可继续使用。需要重构的是批量提交路径、准确归属与统计、恢复控制、列表读模型及部分调度查询，而不是换数据库或简单增加线程。

用户提出的“按 10 月、无优惠筛选账号，创建查询套餐批次”按当前账号列表语义实现：创建日期就是现有列筛选的日期，“无优惠”就是该列原有谓词。账号列表与批量页面使用同一个查询定义和 SQL 编译器；不得新写一份含义相近的筛选。

## 3. 本次收敛的关键决定

| 编号 | 决定 | 原因与边界 |
|---|---|---|
| D01 | 公共批次平台 + 功能适配器 | 公共能力复用，功能结果不硬塞成同一张通用表单 |
| D02 | 列表/预览/固定名单共享 `AccountQuerySpec` | 查询集合一致，含搜索、多选、日期、归档和旧优惠语义 |
| D03 | 第一版保持 `id DESC` 排序 | 当前列表只有该排序；新增排序需两处一起改 |
| D04 | 先准备持久选择快照，再快速受理批次 | 数量准确、目标不漂移，创建请求不遍历全部账号 |
| D05 | 名单全量固定，Run 有界展开 | 目标可很大，内存/待执行队列与实际容量有关 |
| D06 | 同批重跑新增轮次，拥有关系明确到具体 Run | 首轮历史、当前结果与重跑结果分别可解释 |
| D07 | 活跃占用进入等待，不冒领别批 Run | 重叠批次不丢账号、不把其他执行算成本批结果 |
| D08 | 事务事实 + 持久 outbox + 差量投影 | 避免每项完成整批重算；进程重启不丢统计更新 |
| D09 | 新管理任务走统一且可复用连接的事务原语 | 当前单条创建/重跑/claim 锁序不同，不能直接包循环 |
| D10 | 第一版提供取消未开始与请求停止 | 取消按账号整链首次开始判断，不误杀已开始账号的后续步骤 |
| D11 | 生效配置冻结；可覆盖字段由目录白名单决定 | 不出现 UI 能修改但执行器忽略的参数 |
| D12 | 保留旧任务；新旧批次明确不同投影所有权 | 可渐进迁移和回退，不推倒全部历史 |
| D13 | 本地、Oracle 独立受理/执行/统计 | 没有跨部署共享队列，也不复制运营数据 |
| D14 | 首期不引入 Redis/Celery、任意 DAG 或跨机器调度 | 目前瓶颈证据来自 SQL/提交放大；现有持久队列可承接 |

查套餐国家、自动刷新 AT、补密码驱动等当前来源于配置快照，第一版展示为只读生效设置；目录只有在领域实现支持每批覆盖时才发布可编辑字段。Codex 现有独立驱动参数可按契约公开。并发上限是本批约束，实际运行仍受全局资源许可限制。

同批重跑沿用该批功能配置与原执行检查点；需要采用新设置时按同一固定名单创建新批次。预览后若修改参数或生效配置发生变化，先明确展示新设置并重新预览，不静默更改用户已固定的意图。

## 4. 用户流程与页面

1. 进入“批量任务 → 新建批次”，或在账号列表点击“按当前筛选创建批次”。
2. 选择功能，编辑共享列筛选；显式勾选与全部匹配是不同来源，不用当前页冒充全量。
3. 点击“预览并固定范围”。后台只查询本地数据，记录账号身份、顺序和必要证据；ready 后显示最终目标数、固定时点和资格摘要。
4. 点击“创建并运行”，短事务保存用户意图并返回批次 ID。详情立即可访问，显示待提交、等待账号、排队、执行与结果。
5. 后台按容量分块创建 Run，已有领域 handler 执行业务；关闭浏览器不影响进行。
6. 查看公共进度、功能统计和逐账号结果；从失败数量直接筛明细，可打开原 Run 日志。
7. 点击“重跑未成功”创建同批新轮。首轮保留原结果，当前视图逐账号采用最近已固定轮次。

列表、创建、详情是三个稳定页面。任务中心继续查看具体任务和 Run；批次页负责范围和结果汇总。功能面板可以不同，但页面的导航、轮次、明细分页、错误、控制与恢复统一。

例如首轮 100 个账号失败 10 个，重跑这 10 个后成功 8、失败 2：首轮仍显示失败 10；重跑轮显示成功 8/失败 2；当前结果显示目标 100、失败 2。套餐查询失败时，不把旧“无优惠”记录计入本轮成功结果。

## 5. 事实和状态边界

选择快照回答“这批究竟选了谁”；批次回答“用户想执行什么”；轮次回答“这一次重跑包含谁”；task/Run 回答“具体实际做了什么”。结果投影从这些事实计算，不能反向伪造执行成功。

公共底座新增八个职责清晰的关系：选择请求、固定目标、批次控制、执行轮次、目标轮次、Run归属、投影事件、控制命令。task/Run仍使用原表。M4A的旧任务列表另外建立可重建读模型，不是第二份执行事实。

| 对象 | 关键规则 |
|---|---|
| 选择 | 同一 MVCC 语句快照固定，ready 前不承诺最终人数 |
| 批次 | 消费选择、冻结功能/配置/意图键；创建不随目标数逐项建 Run |
| 轮次 | 先固定成员再切当前归属；人工重跑与自动依赖续接显式区分 |
| 目标轮次 | 等待/提交控制事实；执行结果取本轮 owned Run 与领域证据 |
| Run | 保持原执行、许可、检查点、回执和诊断事实；不建第二套执行器 |
| 汇总 | 差量可重建，显示修订和更新时间；不依赖重新筛选当前账号 |

公共桶必须互斥：目标数等于待提交、等待账号、排队、执行/外部等待、成功、部分成功、失败、未执行、取消、待确认之和。一个账号可有多个子步骤，但账号数量只算一次。

未知回执保留事实与原因，支持整批发起新的重跑意图；由领域适配选择原身份恢复、续接或确认回执，不设“必须逐账号人工核对”的通用门槛。仍活动的真实执行不会被当成新 Run，旧 owner 的迟到回写受 fence 限制。

## 6. 需要实际改造的接缝

| 现有位置 | 拟改职责 | 行为边界 |
|---|---|---|
| `core/storage/admin_repository.py`、账号页筛选 | 抽出规范查询与兼容参数映射 | ID 集合与原列表一致 |
| `core/storage/operations/store.py` | managed 创建/重跑/claim/finish 事务原语、汇总路由 | 不将旧锁顺序直接包在新锁里 |
| `core/operations/task_gateway.py` | 传递精确批次/轮次上下文、旧入口适配 | 原 handler 与许可继续有效 |
| `webui/runtime.py` | 密码/2FA/组合领域协调下沉 core | 保持原认证、步骤顺序和恢复规则 |
| 各账号/Codex service | 批量预取、prepare/submit/result/retry adapter | 不通过前端状态猜业务成功 |
| `core/operations/retention.py` | 保护受引用 Run、账号删除保留批次历史 | 不让 CASCADE 悄悄删报告 |
| WebUI 当前现代页面 | 菜单、三个页面、共享筛选和结果组件 | 不增加旧版或第二套页面外壳 |

新存储/领域模块分别落在 `core/storage/operations/` 与 `core/bulk_operations/`，`core` 不导入 `webui`。接口类型、枚举和用例先固定，再并行实施；巨型共享文件由集成人统一处理。

## 7. 性能目标与验收方式

| 环节 | 初始目标 | 证明方式 |
|---|---|---|
| 点击反馈 | ≤100ms | 真实浏览器慢网/满载场景 |
| ready 选择创建批次 | p95≤500ms | 500、1万、10万目标，事务不逐项建任务 |
| 固定1万目标 | 初始p95≤2s | 原筛选 SQL，单快照一致性及失败恢复 |
| 后台展开 | 100目标块≤30 SQL；初始吞吐目标为旧基线4倍 | 独立无外部请求基准，不混入HTTP受理时延 |
| 摘要和50条明细 | p95≤300ms | 10万账号/100万历史Run，检查SQL计划 |
| 活动结果可见 | 正常投影延迟≤2s | 完成事实、outbox、摘要修订链路测量 |
| 满载额外开销 | 固定预算，不随积压目标线性增长 | 100/1万/10万积压对比，含公平与配额回归 |

以上为待验证的发布门槛，不是已实现的速度承诺。已有基线约 48 目标/秒来自无外部执行的旧查套餐入队测量；真实性能需每组至少 30 次样本。本地和 Oracle 分开记录，合成数据库测试与真实账号业务验收分开报告。

## 8. 实施顺序与范围

| 阶段 | 交付 | 依赖 |
|---|---|---|
| M0 | 查询同源、契约样例、隔离夹具、迁移兼容门槛 | 本设计评审 |
| M1 | 选择/批次/轮次/投影/恢复底座、三页面、查套餐 | M0；形成第一条完整纵向链路 |
| M2 | 补密码、2FA、Codex及专用结果，协调下沉 | M1事务与接口稳定；领域可并行 |
| M3 | 组合补全、所有人工重跑归轮、快捷入口整合 | M2与精确依赖上下文 |
| M4A | 必需规模性能、旧任务列表、恢复/浏览器/两端验收 | 完整五功能；达到全部发布门槛 |
| M4B | 其他模块适配、导出等后续扩展 | 独立业务范围与验收 |

M1不是完整交付；M4B不阻塞首期必需范围。计划按验收门槛推进，不用无法证明的固定天数承诺替代测试。数据/编排、领域适配、页面、测试可按分篇契约并行，公共事务接缝必须统一审阅。

受保护注册执行逻辑、全局调度顺序或并发行为如确需改变，仍须单独提供具体行为变化与验证方案并获得确认。本详细设计不把它们隐含授权在通用性能优化中。

## 9. 发布、回退与当前交付状态

新增结构与兼容识别先上线，新受理开关后开；新旧批次的汇总写入归属互斥。回退只回到能识别新控制、轮次和历史引用的兼容版本，先停新受理/展开并明确处理在途 Run，保留所有已受理数据，不靠删表回退。

实施发布顺序：隔离验证、代码评审、提交、推送、核对远端，再部署该提交；本地与 Oracle 各自验收，并保留 Oracle 独立提交。具体版本门槛及带编号的验收矩阵见页面交付篇。

当前交付为文档详细设计。没有创建业务批次、执行 DDL、修改生产配置、修改注册流程、提交推送或重启部署。文档检查不代表 SQL 已执行、性能已达标或真实业务已验收。
