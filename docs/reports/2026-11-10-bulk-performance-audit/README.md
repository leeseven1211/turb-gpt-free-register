# 批量操作性能调查与分阶段改造方案

日期：2026-11-10（北京时间）。范围：本地与 Oracle 的账号、Codex、邮箱池、任务中心和提链批量入口。

本次完成只读代码调查、隔离数据库基准和线上只读采样，没有修改业务代码、数据库结构或运行配置，没有发起真实批量业务、提交、推送、重启或部署。本文是调查结果与待实施方案，不是优化验收报告。

用户进一步提出独立批量任务菜单、共享列筛选、功能专用结果与整体改造计划。先看[实施级详细设计入口](detailed-design.md)，它包含数据事务、API、界面验收和性能四个分篇；[总体方案](design.md)保留产品背景。后续实施以详细设计的完整里程碑和用户评审结果为准。

## 1. 结论

批量操作确实需要针对性改造。首先应解决提交阶段的串行入库、重复全量读取和调度额外读写，再优化任务列表及索引。现有 PostgreSQL 行级存储、连接池、持久化任务、线程池和多维并发许可可以继续使用；目前没有证据要求更换数据库或引入 Redis/Celery。

影响速度的数量有三种，必须分别测量：

- 本次选择数量 B：许多批量接口实际是循环调用单条提交，HTTP 响应时间随 B 增长。
- 全库账号或凭证数量 M：Codex 刷新和 sub2 上传存在每项重新读取全库凭证的路径，工作量接近 B×M。
- 历史任务、Run、事件数量 H：任务列表全历史聚合、重跑读取历史和批次反复汇总会受 H 或批次大小影响。

实际执行耗时还受外部接口、代理、邮箱和浏览器额度约束。增加执行线程不能消除 HTTP 返回前的串行提交，且可能增加数据库锁竞争。

## 2. 实测：仅入队就会等待数秒

使用现有 `POST /api/accounts/check-plan-bulk`，通过 Flask 测试客户端调用真实路由、账号状态更新、任务/Run/事件持久化和日志写入。测试库为独立 `turb_test`，每次创建随机 `test_` schema；准备 2,700 个合成账号，禁用项目 dotenv 和兼容导出，不启动 dispatcher，不执行查套餐或其他外部请求。

仅替换依赖生产配置的功能可用性检查；未替换账号查询、任务提交或 SQL。每个规模取三个样本，使用不同合成账号；下表是中位数，不是 p95。额外的单账号样本用于预热。

| 本次账号数 | HTTP 受理耗时中位数 | 最小—最大 | SQL 次数 |
|---:|---:|---:|---:|
| 10 | 0.202 秒 | 0.188—0.243 秒 | 101 |
| 50 | 1.041 秒 | 1.004—1.130 秒 | 501 |
| 100 | 2.077 秒 | 2.022—2.558 秒 | 1,001 |
| 200 | 4.204 秒 | 4.085—4.358 秒 | 2,001 |

SQL 次数为 `10×B+1`。500 个账号尚未开始外部业务，就已等待约 10 秒，证明提交热路径自身足以造成卡顿。数据库和应用同在本机；结果不能直接替代 Oracle 或带生产并发时的延迟。

测试完成后删除了本次新建 schema。临时测量脚本、合成日志和原始聚合结果位于 `/tmp`，不进入仓库；没有复制生产账号数据。

## 4. 各类批量入口的检查结果

| 入口 | 当前情况与主要成本 | 优先级 |
|---|---|---|

| 补配置、补密码/2FA、组合补全 | 逐项读取账号、生成/归一化执行配置快照及创建任务；组合补全还查询关联注册任务。全局配置快照本身已有缓存 | 高 |
| 邮箱换绑 | 已有原生批次、明确序号和统一唤醒，但仍等逐项提交完成才响应 | 中 |
| 封号邮件扫描 | 普通来源逐项提交；HME 已合并共享扫描，不应按 N 次远端扫描解释 | 中 |

## 5. 数据库、索引和队列

### 5.1 现有基础应继续使用

PostgreSQL 已有关系表、JSONB 扩展字段和生成列；当前账号列表使用 SQL 分页。psycopg 连接池默认每种连接参数组合最多 12 条连接，不是全进程仅 12 条。任务、Run、事件已分表，队列已有状态/计划时间索引，活跃账号任务有唯一约束。

执行器使用非阻塞 `try_submit`，任务持久化后由 Event 唤醒；全局、任务类型、批次、供应商和账号许可与 Run 认领同事务处理。已有租约、心跳和启动恢复。这些正确性能力不应为提速移除。

### 5.2 已确认的额外读写

- 池满且候选不少于 64 时，单轮仍查询一次候选、调用 65 次空位检查、64 次等待原因观察，实际提交 0 项。此数量由原控制流探针验证，尚非生产耗时测量。空位检查重复读并发策略，等待观察读写数据库并使用全局准入锁。
- `list_dispatchable_runs` 对合格队列执行四层窗口排序后才 LIMIT，返回数量有上限不代表中间处理数量有上限。
- `_refresh_batch` 每次都锁批次并计算整批汇总。同批 N 项逐条取消会重复计算 N 次全批，可能接近平方级工作量。
- 任务列表通过全 Run 关系的 `DISTINCT ON` 选择当前运行，再聚合 Run 次数、计算排序后分页。历史增长会增加中间工作。
- 周期恢复与正式派发共用调度线程；恢复逐项核验进程及更新，存在周期性停顿风险，尚未测定线上耗时。

依据：[调度器](../../../core/operations/task_gateway.py)约 1680、1797 行；[执行器](../../../core/operations/executor.py)约 55、221 行；[并发许可](../../../core/storage/operations/permits.py)约 43、186、205、340 行；[任务仓储](../../../core/storage/operations/store.py)约 1932、2966、5057、6481 行。

### 5.3 索引的实施原则

先去掉 B×M 全量读取和重复聚合，再按实际 SQL 的 EXPLAIN 计划补索引。索引不能消除请求中 5,001 次 SQL 往返，也不能修复反复远端下载目录。

重点核验账号/凭证按 ID、filename、规范化邮箱的查询是否使用已有索引；新查询优先使用这些列。评估队列可领取条件与排序的组合/部分索引，以及 `operation_execution_requests` 的活跃请求过滤和排序索引。当前后者只有主键，但是否新增、列顺序如何，应以基数与查询计划决定。

列表使用可索引的当前状态、当前 Run、排序时间和 Run 次数摘要；历史、事件、重 JSON 和完整结果按需读取。已有 `last_run_id` 不一定等于当前读模型所选的“活跃优先”Run，不能直接替换而改变语义。

不建议现在做数据库分库、全面重建 JSONB 数据模型或盲目增加连接池。历史保留是辅助措施，不能代替修复全量扫描。

## 6. 建议实施顺序

### 第一阶段：减少提交与刷新成本

1. 账号/Codex 的批量入口先一次或分块读取目标必要字段，消除重复 `get_account` 和全量凭证列表；配置快照每批捕获一次。
2. 建立共用批量提交服务，复用事务连接、显式批次序号和统一唤醒。保留逐项冲突结果、账号原子占用、凭证代际校验与错误分类。
3. 任务取消/重跑使用动作所需的轻量字段；在写事务中保留条件校验，不能用删除第二次读取的方式丢掉并发保护。整批取消最后统一汇总。
4. 列表默认传摘要，筛选统计合并/缓存，详情按需读取；按钮即时显示“正在提交”，HTTP 完成后明确显示受理、排队、执行三个不同状态。
5. CPA 导出每批只读取一次目录，建立匹配映射；导出任务后台准备文件、提供进度和下载结果。下载可采用受上限控制的并发，保留逐项失败结果。

### 第二阶段：让大批量快速受理且可恢复

HTTP 短事务保存批次请求、确定的目标集合、配置快照与幂等键，提交成功后返回 202 和批次 ID。此时表示“批次已受理”，不能把全部账号虚报成“已入队”。后台按有界分块创建任务并更新逐项结果；页面展示已创建、已跳过、失败和剩余数量。

优先复用现有 `operation_batches`/任务/Run 事实；如现有批次项必须绑定已创建任务，则增加独立受理明细结构，不把尚未建任务的账号伪装成 Run。需要明确保存展开游标、执行归属、租约和状态，重启后继续；一个分块提交后才能推进游标。取消与展开并发时通过同一批次状态校验阻止继续创建。

同一次提交的网络重试复用幂等键；用户明确再次重跑使用新的运行意图。不能因为增加幂等机制就阻断用户的正常批量重跑，也不能以页面内存队列代替持久化。

### 第三阶段：调度与读模型扩展

- 每轮复用线程容量配置；满载时降低候选扫描与等待状态写入频率，状态未变化不反复写。最终准入仍事务内按最新策略检查。
- 每类型、批次、供应商取得有界候选后公平选择，保留续跑与新任务的既有公平规则；分块处理恢复，减少对派发的长时间阻塞。
- 优化任务当前状态和批次计数投影，避免每页聚合全历史、每项重算全批；用事实事务或可恢复的投影机制确保一致性。
- 若页面与任务在实测中仍明显争用 CPU/连接，再分离 Web 与 worker 进程。继续用 PostgreSQL 作事实来源与可靠队列，依据瓶颈决定是否需要其他组件。

公共调度器也可能影响注册。涉及注册步骤、关键分支、重试/超时、状态流转或实际并发执行变化的部分，必须先形成注册专门方案并获得明确确认；各注册驱动分别隔离验证。本报告不授权这些变更。

## 7. 验收方案与当前交付状态

后续实现必须在独立工作区和测试库验证，建议固定以下验收维度：

- 选择规模 10/100/500，分别测提交返回、后台展开、排队、执行及页面显示；不能只测一个总时间。
- 固定选择 100 项，再扩大账号/凭证总量及任务/事件历史，确认消除 B×M 和整历史读取放大。
- 新受理接口可把 500 项 p95 小于 500 毫秒作为初始目标；第一阶段现有同步接口可先设 100 项小于 500 毫秒、500 项小于 2 秒的目标。它们是待验证目标，不是本次已达到或保证的结果。
- 正式 p50/p95 至少采集 30 次稳定样本，区分冷启动/暖态和空闲/满载；记录 SQL 次数、连接等待、事务时长、锁等待与响应大小。
- 满载调度的额外数据库工作应有固定预算，并验证不同类型/批次公平性、取消及时性、重启恢复和旧 worker 写回保护。
