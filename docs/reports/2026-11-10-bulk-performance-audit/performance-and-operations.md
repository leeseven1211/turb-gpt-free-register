# 性能、容量与运行设计

日期：2026-11-10。状态：详细设计，尚未实施；数值预算均需在隔离环境验证。

本文属于[详细设计入口](detailed-design.md)，数据事务见[数据与事务](data-and-transactions.md)，接口见[接口与领域适配](api-and-adapters.md)。已测数据引用[调查报告](README.md)，不将设计目标当成实测结果。

## 1. 性能问题分开治理

| 放大维度 | 已确认现状 | 本次治理 | 不能替代它的措施 |
|---|---|---|---|
| 本次目标数 B | 500 个查套餐请求约 10.36 秒、5,001 SQL，尚未执行远端请求 | 选择快照、短受理、集合持久化、有界展开 | 只加浏览器线程 |
| 全库资产数 M | Codex/sub2 每个目标重新读全库，接近 B×M | 按稳定 ID / filename 批量定位 | 只给全量列表加缓存 |
| 历史 Run 数 H | 50 条任务列表仍全历史选当前 Run 和聚合 | 有索引的当前任务读模型 | 限制 HTTP 返回条数 |
| 批次成员数 N | 每次终结/取消重算全批，可能接近 N² | 每目标贡献差量、每块合并更新 | 只降低页面刷新频率 |
| 外部请求与资源 | 代理、认证、邮箱、浏览器和远端限流影响业务用时 | 保留多维许可、分阶段测时、按故障来源定位 | 宣称入队快就代表业务快 |

两条硬约束：提交/列表性能不能依赖无限加大并发；受保护注册流程不能借共享调度优化改变执行行为。

## 2. 服务结构与容量

首期继续单部署的现有应用进程、PostgreSQL 和业务执行线程池。新增协调线程只做数据库工作，不承载远端认证或浏览器流程。本地和 Oracle 各自读取自己的库、策略与容量。

```text
HTTP / 现有账号快捷入口
    → 持久选择与批次请求
    → 选择准备 worker / 目标展开 worker
    → 原 task/run 队列 → 原准入许可 → 原业务 handler
    → 事实 + 持久 outbox → 结果投影 worker
    → 批次摘要、当前页明细
```

### 2.1 初始内部参数

下列为实现起始值，不作为无证据的最终性能承诺。放在一个 `BulkRuntimePolicy` 中集中校验，不散落 magic number；首期无需把全部内部旋钮暴露给用户。

| 参数 | 初始值 | 含义 |
|---|---:|---|
| 选择准备并行数 | 1 / 部署 | 一次只跑一个大范围快照写入 |
| 展开 worker 数 | 1 / 部署 | 单轮最多处理一个批次的一块，再轮换 |
| 投影 worker 数 | 1 / 部署 | 先按批次合并处理，实测后可增加 |
| 最大块大小 | 100 个目标 | 剩余窗口不足时缩小；只含本地持久化 |
| 每批未结束 Run 窗口 | `min(128, max(8, 2 × C))` | C 为本批与类型、全局上限共同给出的有效并发提示 |
| 所有新批次窗口总和 | 512 个 Run | 只约束新平台，不改变旧队列事实 |
| 单次投影读取 | 最多 200 个 outbox 项 | 按 target 去重、按 batch 合并增量 |
| 空闲协调扫描 | 1 秒 | 内存唤醒只是加速，丢失后仍从库恢复 |
| 账号占用重检 | 2、5、10、30 秒，带抖动 | 释放事件可提前唤醒；不按固定总时长丢弃目标 |
| 单块事务时长 | p95 初始目标 < 200 毫秒 | 超标先缩块，不能在事务内等待外部资源 |

窗口包含本批拥有且未结束的根/子/续接 Run；已经开始账号的必需依赖有优先预留，避免窗口被新账号占满导致老账号无法收口。外部 blocker 不计入本批窗口，仍占已有全局资源许可。临时 partial 父 Run 不代表整个账号已经结束。

活动 Run 数是展开压力提示；真正能执行的数量始终由已有全局/类型/批次/供应商/账号许可事务裁决。配置降低后不驱逐已运行项，只停止补足到较高窗口。等待账号项持久保存，不占业务线程或执行许可。

初版依赖续接预留规则：从 512 总窗口中保留 25% 给已开始账号的必要子步骤；新根 Run 只使用其余空间。每轮先处理已有续接，再给各可展开批次至多一个块。续接仍受真实并发许可约束；不得用“优先”绕过业务限额。

### 2.2 数据库连接预算

当前连接池默认每组连接参数最多 12 条，而不是整个进程只有 12 条。新增服务不得通过随意改变连接参数建立额外无界池。协调任务一条事务占一条连接，计算/等待阶段归还连接。

首期新增三种 worker 总计最多同时占用三条数据库连接；HTTP 与既有业务连接另行监控。出现连接等待时优先减少选择/展开并行与块大小。只有明确观察到连接不足且数据库仍有容量才调整池；不把 `TURB_DB_POOL_MAX` 当默认提速按钮。

租约与 fence 的确切规则以数据篇为准。数据库协调任务失败可重放；真实业务 owner 未确认退出时不能仅因协调租约到期重复执行远端动作。

## 3. 真正降低批量提交成本

### 3.1 块内处理

对 100 个目标，读取固定目标身份、账号必要列、功能所需证据、现有活跃任务和凭证引用，各做集合查询。配置快照在批次受理时固定，块内只读取该版本。不得对每项调用旧路由或打开一个独立事务。

持久化优先使用参数化 `VALUES` / `UNNEST`：预分配 task/run identity，集合插入 task、run、初始 event、精确归属，集合更新账号 queued 投影。需要根 task 自引用的 `root_task_id` 在预分配后直接填值；关系约束在同一事务满足。目标级冲突集合分类，不能捕获一项 SQL 错误后继续使用已经失败的事务。

旧 helper 若仍需要逐项判定，可在一次集合取锁后使用受限保存点；不得把“复用一个连接但仍逐项 10 条 SQL”作为终态方案。批次热路径不得逐目标初始化表、读取全部配置、读取完整事件史或同步写日志文件。

初始预算：100 个独立查套餐目标的正常持久化块不超过 30 次 SQL 往返，事务次数为 1；保存点异常路径单独计量。小块允许固定开销，验收同时报告 SQL/目标与 SQL/块，防止通过拆成许多单项事务掩盖成本。

### 3.2 日志与事务

数据库初始事件随 task/run 同事务提交。文件日志采用提交后最佳努力镜像，路径/标识可提前确定；文件失败归类 `log_mirror_write_failed` 并保留 DB 事件，不回滚已受理任务。不得为优化而删除领域诊断信息。

现有运行日志和领域 handler 行为保持兼容；先只把新 managed 提交的初始日志移出 SQL 事务。若修改公共日志路径会影响注册，单独评审其纯诊断边界。

### 3.3 预取与执行时再校验

预取不是执行资格承诺。原子写入仍需验证账号身份、停用、互斥、原凭证代际以及本轮/控制 fence。事务外准备不得携带能绕过这些检查的“已通过”标志。

稳定凭证 ID 优先于邮箱；filename 仅用于首次解析。若一个邮箱有多份凭证，沿用领域明确的选择规则；缺规则时标为 `credential_selection_ambiguous`，不得任取第一份或最新一份。Token、Cookie 和整个凭证内容不复制到批次/选择表。

## 4. 索引与 SQL 设计

新增批次表索引详见数据篇；本节补充现有账号和任务热路径。索引通过版本化迁移创建，检查实际定义，不能只用同名 `IF NOT EXISTS` 假定列顺序和谓词已正确。

| 查询 | 优先复用 | 候选增量及触发依据 |
|---|---|---|
| 账号日期 + 无优惠 + 归档范围 | `(archived, account_promotion_value, id)` | 表达式索引 `(archived, account_promotion_value, left(created_at,10), id)`；日期范围扫描成本明显时增加 |
| 只有日期 + 归档范围 | `(archived,id)` | `(archived, left(created_at,10), id)`；不得同时盲加所有组合 |
| 凭证 filename / ID | 已有 filename 唯一与 PK | 改为 `filename = ANY(...)` / `id = ANY(...)`，无需再加重复索引 |
| 按邮箱解析凭证 | 已有 email 普通索引 | 只有查询统一采用相同大小写/空白规范后才考虑规范化表达式索引；不能强加未验证唯一性 |
| 活跃执行请求 | execution_key PK | 若活跃集合显著小于历史，候选 `(seen_at, execution_key) WHERE observed_only IS FALSE`；不要把 `now()` 放 partial 谓词 |
| 新任务读模型列表 | 见下一节 | `sort_at DESC, task_id DESC`，高频类型/状态组合按计划追加 |

日期列第一版继续文本的 `left(created_at,10)` 比较，不为建索引擅自转换成时区时间或真实注册时间。若将来迁移类型列，两处筛选同时迁移并做全集合对照。

前缀 `ILIKE '%x%'` 搜索不能保证普通 B-tree 命中；只有该搜索在压测中成为热点才评估 trigram。初版不引入通用全文引擎，不为所有 JSONB 建 GIN。

每个候选索引在隔离合成库上记录 `EXPLAIN (ANALYZE, BUFFERS)`：扫描行数、过滤行数、排序溢出、共享块、执行时间、索引大小与写入开销。生产只执行经评审迁移，不为本设计临时连接生产执行分析。大表并发建索引应单独迁移步骤，失败后的 invalid index 有显式检查/重试，不能放在普通事务内执行。

## 5. 任务中心当前状态读模型

这是 M4 的独立可验收改造，解决现有历史越多列表越慢，不依赖用户改用新菜单才生效。

### 5.1 数据与兼容语义

新增 `operation_task_read_models`，一 task 一行，可重建；业务状态仍由原任务/Run/兼容领域事实决定。

| 字段组 | 字段与类型 |
|---|---|
| 身份 | `task_id bigint primary key`，引用 task；`effective_run_id bigint null` |
| 当前值 | `effective_status text`、`effective_stage text`、`target_status text`、`task_type text`、`source_system text`、`batch_id bigint null` |
| 时间/计数 | `sort_at timestamptz`、`task_created_at timestamptz`、`run_count bigint`、`updated_at timestamptz` |
| 列表检索 | `visible boolean`、`account_id bigint null`、`email_snapshot text`、`error_code text null`、有长度上限的 `result_search_text text` |
| 版本 | `projection_schema_version int`、`projection_revision bigint` |

只保存列表必要摘要，完整 data、结果、日志继续按单条取。字段枚举与 SQL 选当前 Run 的规则完全相同：**优先有效状态为活跃的 Run，然后 run_no DESC、id DESC**。兼容注册/旧账号任务使用原 `_compatibility_run_projection_sql` 的有效状态；不能直接复制原始 r.status，也不能把 task.last_run_id 当作正确结果。

`run_count` 保持原列表现存 Run 计数语义；批次历史永久统计不依赖此数。默认排序保留 `COALESCE(effective_created_at_sort, task.created_at) DESC, task.id DESC`。筛选/搜索效果须与旧接口对照，不能只验证前 50 条看起来一样。

### 5.2 更新算法

复用 `operation_projection_outbox`，使用独立 `consumer_kind='task_read_model'`。影响可见字段的 task/run、兼容注册投影、删除/隐藏和保留清理事务都追加任务 ID；同一业务事件向不同 consumer 发记录必须使用不同 event_key。

消费者先选待处理 outbox ID，再按 task_id 升序取得该任务读模型专用事务 advisory lock；取得锁后，另一个 SQL 语句读取当前已提交事实，按原规则只计算这些 task 的 Run。一次集合 upsert 读模型并标记本次选中的 outbox 已处理。它不锁真实 task/run、不取得 bulk 投影锁、不反写业务事实。

采用 READ COMMITTED，避免先读陈旧快照后等锁再覆盖新值。处理期间新增 outbox 不会被按 task 一锅删除，而是留待下一轮；没有依靠全局 `max(event_id)` 跳过未提交低 ID 事件的游标漏洞。失败整块回滚，不丢脏任务。

高重跑任务可用 `(task_id, run_no DESC, id DESC)` 限定读取；初次和状态切换时只在本 task 内取有效当前 Run。若单任务历史非常大，再以等价性证据增加 active/latest 两个候选优化，不提前引入第二套状态规则。

任务详情/重跑/取消仍读取事实，不依赖最多数秒滞后的读模型作准入决策。数据缺口或版本不匹配时返回同步状态，不能把空读模型当成任务不存在。

### 5.3 查询与切换

普通列表先从读模型完成状态过滤、排序、分页，再批量读取当前页额外字段。分页采用 keyset；旧 page 参数以兼容接口保留，深页性能单独标注，不能靠 offset 宣称固定成本。`total` 和 facets 独立接口/按需请求，不能每 2 秒扫描全历史重新计数。

任意组合筛选的精确 total 仍可能扫描匹配读模型行；承诺不扫描全 Run 历史，不承诺任意组合聚合 O(1)。用规范筛选 hash 缓存短时 facets，并携带 as_of。不对筛选视图维护指数数量的组合计数器。

迁移：先上线事实 outbox，再按 task_id keyset 回填；每块锁对应读模型后读取当前事实，最后处理剩余 outbox。对照旧列表的 ID、顺序、有效状态、run_count；通过后按部署开关切读，旧查询仅作回退与抽样验证，不双跑每次 GET。新版本存在时回填可恢复，旧版本恢复不得删除新表。

## 6. 调度满载与公平性

### 6.1 可先落地的成本优化

每轮只读一次容量提示和配置版本；业务池全满时不再逐个候选重复查询配置和写 observe。对满载原因提供池级摘要，账号明细仅在等待原因变化、订阅该页或周期校验时批量补齐。提示缓存不参与最终许可裁决。

调度唤醒来源：Run 提交、完成释放、配置变更；保留约 0.5 秒的有界扫描作漏信号兜底。纯空闲/全满循环设置独立 query/write 预算，不能每轮随着积压长度增长。

若将恢复扫描移出 dispatcher，它必须沿现有 owner 验证与收口逻辑，只有运行线程隔离和分块调度改变。注册恢复行为受到影响时进入单独评审，不搭便车合入。

### 6.2 多层排序替换门槛

当前四层窗口排序虽然 LIMIT 很小，仍可能扫描全部合格队列。长期改为“活跃分组索引 + 每组有限候选 + 原公平裁决”，但不能全局取最早 K 个后才分组，导致新批次/任务类型饥饿。

分组键保留 task_type / batch / provider / continuation lane；组轮转保留已有持久游标。每组取少量可领取候选，取满后优先轮换其他组。为了避免选组本身扫描全队列，可维护可重建的活跃分组摘要，增减由 queued 转换事务/outbox 驱动；分组摘要滞后仅影响发现速度，不影响许可正确性。

这一替换可能改变与注册共享的真实执行顺序，**不列入首期直接实施范围**。先做只读候选 shadow 对照：相同样本、容量、续接偏好与游标，记录遗漏、饥饿、扫描量；再提交明确调度行为方案确认。当前详细方案批准也不自动授权注册主流程变化。

首期通过有界展开使新批次 queued 数与容量有关，不与十万固定目标成正比；这能减轻现有排序压力，但不是宣称已解决所有旧积压。

## 7. 观测、诊断与降载

每次操作携带 `request_id`、selection/batch/round/target/run ID。指标按功能与部署聚合，不按账号 ID/邮箱建高基数标签。详情可从内部 ID 跳到原 Run 日志。

| 指标 | 必须区分的阶段 |
|---|---|
| `bulk_request_seconds` | HTTP 受理，不含后台执行 |
| `bulk_selection_seconds` | 等待准备、SQL 快照、发布 ready |
| `bulk_expand_targets_total` / `bulk_expand_sql_total` | 目标吞吐、每块 SQL、等待/未执行比例 |
| `bulk_queue_delay_seconds` | 未物化等待、账号占用、queued 等执行名额 |
| `bulk_execution_seconds` | Run 执行与账号整链执行分别计时 |
| `projection_lag_seconds` | 最旧未处理 outbox 年龄、完成事实到可见结果 |
| `db_pool_wait_seconds` / `db_transaction_seconds` | 连接、行锁、advisory 锁等待分别采样 |
| `dispatch_scan_total` / `dispatch_admitted_total` | 满载空转与实际准入，附等待原因变化数 |

投影落后显示“统计同步中 + 最后更新时间”，不得显示全部成功或把差额默认为失败。协调 worker 故障保留已受理请求；恢复后继续，不向用户要求重新点创建来补任务。数据库不可用拒绝新受理并可重试同幂等键，不退回进程内队列。

连续选择准备/展开超时先停止新块、保留待处理，分类显示 `selection_query_timeout` / `bulk_expand_store_unavailable`。系统级故障不伪装成每个账号业务失败。错误已知范围按阶段、异常类型、外部状态与回执确定；证据不足保留诊断引用与缺失证据，不凭空宣称远端根因。

## 8. 性能验收与扩容决策

| 测试 | 数据/并发条件 | 初始门槛 |
|---|---|---|
| 创建批次 | ready 选择分别 500 / 10,000 / 100,000 个目标 | p95 ≤ 500ms；不逐目标写任务 |
| 选择固定 | 10,000 匹配目标、真实筛选表达式 | 初始目标 ≤ 2s；超时可恢复且不会半份 ready |
| 展开 | 无外部请求，500 / 10,000 目标 | 正常100目标块≤30 SQL；吞吐至少为既有约48目标/s的4倍作为初始目标 |
| 摘要/50明细 | 10万账号、100万历史Run；普通状态/错误筛选 | p95 ≤ 300ms；不对全Run或全批反复聚合 |
| 全满调度 | 积压 100 / 10,000 / 100,000 | 同一满载周期额外工作固定预算：容量提示≤2次SQL，逐目标observe写入0次；既有独立心跳另计 |
| 投影 | 持续并发完成、重跑与原Run补证混合 | 正常lag≤2s；最终计数恒等且重建一致 |
| 恢复 | 每个事务提交前后杀进程、旧owner复活 | 无丢失、无重复owned Run；用户可批量重跑 |

30 次稳定样本报告 p50/p95/max，冷暖态、空闲/满载、本地/Oracle分别记录；不得拿三次中位数声称 p95 达标。用 stub 外部 handler 测平台吞吐，用少量授权真实账号测领域行为，两种证据分开。

若展开/投影与 HTTP 出现可复现 CPU/连接争用，才引入独立 `bulk-worker` 进程，继续同一数据库、同一协议与许可。若单库队列已占主要数据库负载且改良查询仍达不到预算，再评估外部消息代理；即使增加消息代理，Run、归属、幂等和结果事实仍在 PostgreSQL。当前没有引入 Redis/Celery 或分库的实测依据。

扩大业务线程必须有外部资源和限流余量，按本地、Oracle分别定标。数据库/页面响应优化完成后，真实查询耗时仍可能主要由远端决定，页面应如实区分已受理、待资源、执行中和统计同步中。
