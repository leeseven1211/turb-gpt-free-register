# 任务失败分类与公开结果核查

## 问题与核查范围

AT 刷新已经返回 `ok=false/status=failed`，仍会因远端 intent 的回执状态被存储层归入 `attention_required`。批量平台再将其投影为 `unconfirmed`，导致验证码超时、密码验证 HTTP 409 和 Session 缺少 AT 都显示成笼统的待确认结果。

2026-11-12 通过鉴权只读 API 拉取了当时全部 4,400 条相关任务：4,310 条 `attention_required`、90 条 `request_unknown`。执行期间任务总量会变化，该数字仅代表本次完整拉取快照。

## 修改后的结果语义

任务中心、批量任务、注册列表与总览、提链工作台和 Butler 导入统一展示明确的执行结果。内部历史回执状态在公开查询中归入失败；持久化 `requested_status=partial_success` 的记录保留部分成功。正在排队、执行或等待真实外部结果的任务继续保持活动状态。

错误优先采用同次执行保存的 HTTP 状态、服务端错误码、邮箱/MFA/回调/Session 诊断和实际失败阶段。失败正文为空也会进行分类。没有历史证据时明确分类为相应阶段的响应、回执或诊断记录缺失，不猜成密码被拒、账号停用或支付失败。

对本次快照逐条应用新规则，得到 4,397 条失败、3 条部分成功；通用 `request_unknown` 和 `unknown.unclassified` 主分类为 0，错误摘要中的笼统待确认占位为 0。部分历史记录本身没有保存失败细项，新的阶段诊断缺失分类只说明证据缺口，不代表重新确认了远端业务结果。

## 一致性与执行边界

- 公开列表 SQL、分页总数、facet、批次与轮次汇总、详情和进度使用相同结果语义。
- 历史批量结果的当前与指定轮次筛选、按错误原因筛选和重跑名单保持一致。按原因筛选时批量读取该批原 Run 的证据，后续账号或其他批次的结果不参与。
- 提链、支付与 Plus 状态分别保留；已出链、已支付、已有有效凭据和已经确认的部分成果不会因后续错误消失。
- 原始数据库状态、intent、回执、注册 Attempt、恢复检查点、邮箱租约和重试能力不变。没有修改注册请求、导航、提交、超时或重试流程。
- 同时修复了注册列表筛选总数查询中既有的 SQL 参数顺序错误，防止出现有数据但总数为 0。

## 验证方式

在独立工作树与非生产 PostgreSQL 测试库中，使用 `tools/test_isolated.py` 和临时 schema 验证。覆盖错误优先级、空正文、历史状态、部分成功、原始记录保留、SQL 筛选及统计、批量重跑成员、活动任务等待、提链独立成果和 Butler 汇总。

前端定向测试、修改脚本的语法检查与桌面/手机隔离浏览器检查同时进行。浏览器使用合成失败场景检查具体中文原因与错误码；未触发真实账号刷新、注册、付款或任务重跑。

代码交付、推送、服务重启和真实业务验收须分别报告；本核查记录不表示服务已部署。

### 合并前复核补充

合并前交叉审查补充修复了以下边界：

- 提链详情历史使用各 Run 自己的摘要、执行模式和 Provider 事实，保留旧成功出链、收款、Plus 和部分成功成果，避免后续 Run 的状态覆盖历史。
- 整体部分成功与具体步骤分别投影。AT、密码或凭据缺少成功回执的步骤保持失败，套餐查询按同次国家查询事实还原；历史公开字段、最新结果与 SQL 筛选采用同一口径。
- 通用请求异常采用请求失败文案并保留原错误，明确的 HTTP 拒绝不会再被写成没有收到响应。
- 提链卡片动态错误摘要按文本转义，覆盖包含 HTML 标签及事件属性的输入。
