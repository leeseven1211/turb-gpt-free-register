# 注册与账号配置重构设计

> 状态：总体设计，暂不改业务代码。
> 范围：只重构配置的信息架构、字段语义和交互；注册、补全、调试的现有执行能力先保持不变。

## 1. 设计结论

配置页新增一个一级菜单 **“注册与账号”**，把目前分散的内容收进同一处，并在页面内使用四个小菜单：

1. **执行方式**
2. **注册主链路**
3. **账号补全**
4. **注册调试**

“浏览器还是协议”统一放到“执行方式”中维护。注册主链路和账号补全只配置“做不做、做哪些”，不再重复摆放同一套驱动选择。

但执行方式不能做成一个粗粒度的“全局全部用浏览器 / 全部用协议”开关。当前各能力并不对称：密码只支持浏览器，套餐查询只支持协议，只有注册、2FA、Codex 等能力支持多种方式。统一的是入口、选项组件和继承规则，不是假设所有步骤都支持相同驱动。

## 2. 信息架构

```text
配置
├─ 注册与账号
│  ├─ 执行方式
│  ├─ 注册主链路
│  ├─ 账号补全
│  └─ 注册调试
├─ 邮箱与验证码
├─ 代理与网络
├─ RoxyBrowser
├─ Codex 服务
├─ 定时任务
└─ 其他现有配置
```

“Codex 服务”继续保留 CPA、sub2api、Token 自动续期等服务端配置；“Codex OAuth 用浏览器还是协议”属于执行策略，迁入“注册与账号 → 执行方式”。

“RoxyBrowser”继续保留 API 地址、Profile、窗口、代理注入等浏览器基础设施配置；它不再承担业务链路选择。

## 3. 执行方式

### 3.1 页面目标

集中回答每个业务能力“由谁执行”，让注册主链路和账号补全共同引用。页面只提供下拉选择，不允许用户手填 `roxy`、`protocol` 等内部值。

### 3.2 当前能力矩阵

| 能力 | 浏览器（RoxyBrowser） | 协议（Protocol） | 建议默认 | 页面表现 |
| --- | --- | --- | --- | --- |
| 注册基础流程 | 已实现 | 已实现 | 浏览器 | 可选择 |
| 设置/补充账号密码 | 已实现 | 未实现 | 浏览器 | 固定值，只读 |
| 查询套餐 | 未作为浏览器能力开放 | 已实现 | 协议 | 固定值，只读 |
| 开通 Authenticator 2FA | 已实现 | 已实现 | 协议 | 可选择 |
| Codex OAuth | 已实现 | 已实现 | 跟随注册 | 可选择“跟随注册 / 浏览器 / 协议” |
| 刷新账号 AT | 浏览器兜底已存在 | 协议主路径已存在 | 自动策略 | 显示“协议优先，浏览器兜底”，首版只读 |

### 3.3 配置规则

- 每种能力只定义一个通用默认执行方式，注册和补全默认共用。
- 兼容期如果两个旧键当前值不同，页面必须同时展示“注册使用值”和“补全使用值”，提示用户显式统一；首次重排 UI 不得静默覆盖现有行为。
- 只有实际存在两种实现的能力才显示下拉框。
- 当前只有一种实现的能力显示状态标签，例如“浏览器（当前唯一实现）”，不显示伪下拉框。
- Codex 的“跟随注册”表示解析当前注册基础流程驱动，不复制一份值。
- 以后确实出现链路差异时，再增加“单独覆盖”高级项；首版不展示重复配置。
- 页面同时展示“保存值”和“本次实际值”。若能力不可用或被兼容规则覆盖，要明确显示原因，不能静默换驱动。

### 3.4 推荐配置模型

概念模型如下，首版可继续映射现有配置键，不要求立即改名：

```yaml
execution_methods:
  registration: browser | protocol
  password_setup: browser
  plan_check: protocol
  twofa_setup: auto | browser | protocol
  codex_oauth: follow_registration | browser | protocol
  token_refresh: protocol_with_browser_fallback
```

现有键的映射建议：

| 概念项 | 首版沿用键 | 处理方式 |
| --- | --- | --- |
| 注册基础流程 | `REGISTRATION_DRIVER` | 直接沿用 |
| 密码设置 | `ACCOUNT_PASSWORD_DRIVER` | 后端兼容保留，UI 只读 |
| 套餐查询 | `ACCOUNT_PLAN_CHECK_DRIVER` | 后端兼容保留，UI 只读 |
| 2FA 设置 | `TWOFA_DRIVER`、`ACCOUNT_2FA_DRIVER`、`ACCOUNT_2FA_BROWSER_FALLBACK_ENABLED`、`ACCOUNT_2FA_PROTOCOL_REAUTH_ENABLED` | 注册与账号补全分开选择；公开值为 auto/protocol/browser，自动模式按已有 AT、协议重认证、浏览器会话选择上下文，并独立控制浏览器兜底 |
| Codex OAuth | `CODEX_OAUTH_DRIVER`、`ACCOUNT_CODEX_DRIVER` | 兼容期集中展示但不静默改值；新配置默认让补全跟随通用值 |
| 刷新 AT | 当前固定策略 | 首版只展示，不新增无效选择 |

## 4. 注册主链路

### 4.1 页面目标

只回答“注册任务包含哪些步骤”。基础账号注册永远是主链路，不提供总开关；用户点击“开始注册”本身就是启动主链路的明确动作。

页面按用户理解的逻辑链路展示步骤卡；第一阶段只调整配置表达，不据此改变现有后台执行时序：

```text
基础账号注册（必选）
  -> 设置账号密码（可选）
  -> 查询套餐（可选）
  -> 开通 2FA（可选）
  -> Codex OAuth（可选）
  -> Flow 触发（高级，可选）
```

### 4.2 步骤卡设计

每张可选步骤卡统一采用：

```text
[开关] 功能名称
       一句话说明
       开启后：执行方式  协议 / 浏览器 / 跟随注册   [去修改]
```

具体配置：

| 步骤 | 页面开关 | 当前键 | 说明 |
| --- | --- | --- | --- |
| 设置账号密码 | “注册时设置密码” | `REGISTRATION_AUTH_MODE=password/otp` | UI 改为开关，不再让用户理解内部枚举 |
| 查询套餐 | “注册后查询套餐” | `REGISTRATION_PLAN_CHECK_ENABLED` | 失败不回滚已保存账号 |
| 开通 2FA | “注册后开通 2FA” | `ENABLE_2FA` | 执行方式读取通用 2FA 设置 |
| Codex OAuth | “注册后开通 Codex” | `ENABLE_CODEX_AUTO` | 执行方式读取通用 Codex 设置 |
| Flow 触发 | “注册后触发 Flow” | `ENABLE_FLOW_TRIGGER` | 放入高级设置，不与核心能力同权展示 |

`REGISTRATION_PASSWORD_TRANSITION_TIMEOUT_SECONDS` 放到“密码步骤 → 高级设置”，仅在密码开关开启时显示。关闭密码时保留保存值，但不生效、不重置。

### 4.3 页面摘要

顶部显示一行可读摘要，例如：

```text
主流程：浏览器 · 密码：开 · 套餐：开 · 2FA：协议 · Codex：关
```

保存前展示固定顺序预览，不允许首版拖拽调整步骤顺序，避免形成未经验证的组合。

## 5. 账号补全

### 5.1 是否需要“启用账号补全”总开关

首版**不增加总开关**。

原因是“补全账号”是账号页的手动操作，用户点击按钮已经是明确授权。这里真正需要配置的是“补全时检查并处理哪些缺失项”。再加一个总开关会出现“按钮存在、步骤也开启、但总开关关闭”的三层状态，反而更难理解。

处理规则：

- 四个主要步骤全部关闭时，等价于停用组合“补全账号”。
- 账号页的“补全账号”按钮置灰，并提示“尚未配置补全项目”。
- 单独的“补密码、补 2FA、补 Codex、查套餐、刷新 AT”仍然可用，不受组合补全配置影响。
- 如果未来增加“注册后自动补全”或定时补全，再为自动触发单独增加总开关，不复用手动动作的开关。

### 5.2 补全范围

| 补全项 | 当前键 | 默认 | 行为 |
| --- | --- | --- | --- |
| 账号密码 | `ACCOUNT_COMPLETION_PASSWORD_ENABLED` | 开 | 仅在本地未保存密码时执行 |
| 套餐状态 | `ACCOUNT_COMPLETION_PLAN_CHECK_ENABLED` | 开 | 仅在套餐未成功确认时执行 |
| Authenticator 2FA | `ACCOUNT_COMPLETION_2FA_ENABLED` | 开 | 仅在没有已确认 TOTP 时执行 |
| Codex OAuth | `ACCOUNT_COMPLETION_CODEX_ENABLED` | 开 | 仅在 Codex 凭证未成功时执行 |
| 必要时刷新 AT | `ACCOUNT_COMPLETION_REFRESH_AT_ENABLED` | 关 | 仅在 AT 缺失或不可用且后续步骤需要 AT 时执行 |

“必要时刷新 AT”放到“依赖处理 / 高级设置”，用风险色提示它会触发重新认证和邮箱 OTP。它不是普通补全项，也不能被解释为每次补全都刷新。

### 5.3 执行方式与执行顺序

补全菜单不再重复显示可编辑的驱动下拉框，只显示从“执行方式”继承的结果和跳转入口。

规划顺序保持固定：

```text
检查账号状态
  -> 必要时刷新 AT
  -> 补密码
  -> 查套餐
  -> 补 2FA
  -> 补 Codex
```

任务创建时保存本次配置快照。任务已经入队后再修改配置，只影响新任务，不改变正在运行的任务。

## 6. 注册调试

### 6.1 页面目标

把“普通失败诊断”和“主动调试任务”分开，避免用户误以为打开配置后所有注册都会持续抓完整网络包。

### 6.2 小菜单结构

#### 失败诊断

- “普通注册失败时保存脱敏诊断”：映射 `REGISTRATION_FAILURE_DIAGNOSTICS_ENABLED`，建议默认开启。
- 资源记录上限、页面文本上限收进该卡片的高级设置。
- 成功任务不生成失败诊断文件。

#### 调试任务

- 完整抓包仍由“开始注册”旁的“调试模式”按批次开启，不做全局常开。
- 配置页只维护调试任务的默认资源策略：失败现场保留时间、最大保留现场数。
- 页面明确提示“只有提交任务时勾选调试模式才生效”。

#### 存储与清理

- 单正文上限。
- 单任务正文预算。
- 全局抓包预算。
- 保留天数。
- 事件队列上限。

这些字段默认折叠到“高级设置”，顶部只显示预计占用策略和保留天数。

## 7. 通用交互规则

### 7.1 开关与执行方式

- 先显示功能开关，执行方式显示在开关后面。
- 功能关闭时隐藏其详细配置，但保留保存值。
- 重新开启时恢复上次选择。
- 只有一个实现时显示只读标签，不展示可点击但无选择意义的下拉框。
- 所有枚举都使用中文选项，内部值不让用户填写。

### 7.2 保存

- 每个小菜单单独保存，避免改注册主链路时顺带覆盖调试预算。
- 保存按钮旁显示“新任务生效”；需要重启的字段单独标注。
- 保存前做组合校验，整组失败时不保存任何字段。
- 切换小菜单时如有未保存内容，显示“未保存”标记。

### 7.3 校验与提示

- 选择的执行方式必须在能力矩阵中可用。
- 当前实现下，“协议注册 + 注册时设置密码”不兼容，保存或提交前必须直接拦截；不能显示为可运行后再静默跳过密码。
- 当前实现下，协议注册的注册内 2FA 只支持协议；若选择浏览器 2FA，要么切换为浏览器注册，要么明确作为后续独立账号操作实现后再开放该组合。
- 密码关闭时，密码跳转超时不参与校验。
- 2FA/Codex 关闭时，其执行方式可以保留但不生效。
- 补全项全关允许保存，但账号页禁用组合“补全账号”。
- 开启“补全时刷新 AT”时显示一次明确风险提示。
- 驱动或链路配置不可用时，任务提交前失败并指出具体字段，不允许执行一半后才发现配置错误。

## 8. 配置 API 建议

UI 不应继续靠字段名猜测如何渲染。配置 API 应逐步返回结构化元数据：

```json
{
  "key": "TWOFA_DRIVER",
  "group": "注册与账号",
  "section": "执行方式",
  "capability": "twofa_setup",
  "control": "select",
  "choices": [
    {"value": "auto", "label": "自动选择（协议优先）"},
    {"value": "protocol", "label": "协议"},
    {"value": "browser", "label": "浏览器（RoxyBrowser）"}
  ],
  "requested_value": "auto",
  "effective_value": "protocol",
  "restart_required": false
}
```

这样现代 UI、旧 UI 和后续 CLI 可以共用同一份选项与校验规则，不再各自维护别名。

## 9. 分阶段实施建议

### 阶段一：只重排 UI，不改执行语义

- 新增“注册与账号”一级菜单及四个小菜单。
- 沿用现有配置键。
- 把手填驱动改成受限下拉或只读标签。
- 注册主链路和账号补全去掉重复驱动编辑，只引用“执行方式”；旧键值不一致时在执行方式页明确展示兼容差异。
- 保持现有任务执行和配置热加载逻辑。

### 阶段二：收敛重复配置键

- 合并注册与补全的 2FA 驱动语义。
- 账号补全 Codex 默认直接读取统一 Codex OAuth 驱动。
- 固定实现的密码、套餐驱动退出用户配置面，只保留兼容读取。
- 配置 API 增加 requested/effective/capability/choices。

### 阶段三：补充能力后再开放选项

- Protocol 密码设置经过真实验证后，才在密码执行方式中开放协议。
- 刷新 AT 具有稳定的可选策略后，才开放驱动选择。
- 如确有业务需要，再增加注册与补全的单独覆盖，不提前制造重复配置。

## 10. 验收标准

1. 左侧配置导航只出现一个“注册与账号”入口，内部有四个小菜单。
2. 用户无需填写 `roxy`、`protocol`、`same_as_registration` 等内部值。
3. 注册主链路只配置步骤开关；所有执行方式集中在一个位置。
4. 账号补全清楚展示“补哪些”，不会与单独操作按钮混淆。
5. 账号补全不增加多余总开关；全关时组合按钮明确禁用。
6. 密码、套餐等单实现能力不会展示假选择。
7. 关闭功能不会清空其配置，重新开启可恢复。
8. 正在运行的任务使用入队时快照，不受后续保存影响。
9. 调试完整抓包仍按任务开启，普通失败诊断与其语义分离。
10. 第一阶段重构后，现有注册、补全和调试行为不发生变化。
