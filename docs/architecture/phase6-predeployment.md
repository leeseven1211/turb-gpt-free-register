## 总停止预算

Web 和 Worker 都增加 `--shutdown-timeout`。首次停止信号建立一个单调时钟截止时间，HTTP 排空与 runtime 收尾共用剩余预算，重复信号不重置时间；异常清理同样只建立一次截止时间。默认 Web 总预算 80 秒，Worker 60 秒，runtime 单阶段仍最多 60 秒。

本机实际 launchd 将原模板声明的 90 秒显示为 60 秒，因此两个本机示例模板显式声明 60 秒，并向应用传入 55 秒，为退出回执、解锁及解释器退出留出余量。HTTP 若耗满 20 秒，runtime 仅得到剩余的最多 35 秒。超时必须返回失败，不能宣称完整排空；这也不保证不可中断的系统调用会被 Python 截止时间强制打断。

改动范围为两个入口、两个 launchd 模板、部署文档和三个测试文件。41 项定向测试通过，独立边界审查通过；真实可丢弃 launchd 标签完成正常收尾和超时非零退出验证。未安装生产标签。

## 数据库重启验证未通过

最初共用测试容器重启会重新分配 Docker 随机端口，和执行上下文正确冻结的数据库地址冲突；这些夹具失败保留，之后改用全新、固定端口、独立身份的故障专用容器，未修改执行上下文或生产连接配置。

固定端口最终轮已确认真实暂停/恢复/服务器重启、相同 cluster/database/schema/marker、postmaster 启动时间改变、owner 保持失效且本地文件栅栏保留。数据库恢复后的旧池连接返回 `AdminShutdown`；原生 handler 的事件记录明确遇到该异常，随后出现清理异常链。截断日志不足以逐条证明后继 DELETE/finish 的具体 SQLSTATE。保存的观察中，执行许可随后为 0，但原 Run 仍 running、账号 lease 仍有效，因此终态及资源收尾断言失败，Worker 需夹具兜底回收。不能把恢复连接或许可为 0 称为完整恢复通过。

源码显示 `OperationLease.release()` 在数据库删除成功前设置本地 `_released=True`，之后同一对象再次 release 不会重试；原生方法最小复现已经确认这项契约失败。后续只读分析还确认：finish 提交结果不确定时缺少精确回执、部分 catch 会覆盖原结果、permit 的 finally/future/recovery 可早于收尾释放。因此只修租约布尔标记不足以构成完整恢复。

## 目标管理器与部署边界

受限 Linux 容器安装了 systemd 257，但实际用户管理器因系统并非由 systemd 启动而退出 1；没有增加权限、伪造启动标记或挂载主机管理器。因此 Linux 原生管理器的启停、重启和实际 90 秒停止等待仍是目标环境切换前门槛，模板解析不能替代。

本批只准备经审查的源码清单与操作步骤，不把脏工作树复制品称为已提交发布包。真实部署仍需精确提交/推送版本、可恢复备份、目标权限和依赖、紧邻停止时的队列与资源核验，再分别执行本机或 Oracle 的切换和业务验收。具体步骤见[独立运行部署文档](../deployment/split-runtime.md)。
