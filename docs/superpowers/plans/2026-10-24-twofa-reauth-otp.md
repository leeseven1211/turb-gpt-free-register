# 补 2FA 重认证发码修复计划

目标：修复协议补 2FA 未确认认证页面和发码就等待邮件的问题，并验收原有四个失败任务。

范围：沿用已有 AT 优先、协议重认证及 Roxy 兜底，不修改全局配置、存储结构和账号重跑入口。

方案：确认 HTTPS 认证域的邮箱验证码页后，调用现有 `send_email_otp`，以本次发码前时间取新邮件。
密码页、错误页和未知落点保留脱敏原因并进入已有兜底；发码失败不进入收码，显式传入的验证码不因重发失效。

## 执行与验证

- [x] 在 `tests/test_twofa_otp_retry.py` 增加页面判定、发码先于收码、失败不收码和显式验证码不重发的行为测试，先观察失败。
- [x] 修改 `core/account_export.py`，保留页面类型及发码错误的安全诊断，不记录完整 URL、凭据或验证码。
- [x] 更新 README 中的补 2FA 重认证说明。
- [x] 通过独立测试库的隔离入口运行相关与相邻回归：173 项测试、43 个子用例通过，静态检查和独立代码评审通过。

## 运行验收步骤

1. 在 `main` 提交本次文件，通过现有 launchd 重启 8000 端口服务，核对进程、工作目录、健康与就绪状态。
2. 先重跑任务 `257162` 验证，再运行 `257163`、`257164`、`257165`，逐个核对最终状态和 2FA 是否启用。

## 评审重点

- HTTP 200 但实际落在密码页、错误页或其他域时，不得当作已发码。
- 显式发码返回拒绝、未知网络结果时，本次调用不自动重放发码请求。
- 邮件时间锚点在发码前更新，避免误收旧验证码或漏掉快速送达的新邮件。
- 用户已提供验证码时不重发；手动输入模式仍先发码。
- 新增异常与日志只包含固定页面类型、阶段和异常类型。
