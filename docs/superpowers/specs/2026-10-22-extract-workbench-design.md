# 提链工作台与多平台接入设计

## 目标

新增一个独立一级菜单“提链工作台”，以任务卡片集中管理提链、支付和 Plus 权益核验；在保留当前提链服务和账号页入口的基础上，接入 Lumen Flow 与幻光，并为后续平台留出统一适配接口。

首个真实验收仅执行 Lumen Flow 提链，不调用支付接口。验收账号从 2026-10-14 前后创建的账号中选择一个符合条件的样本，使用用户提供的 Lumen CDK；账号身份和 CDK 不写入文档、日志或代码提交。

## 已确认的现状

- 当前 `core/extract_link_service.py` 已使用 PostgreSQL durable operation、Run 事件、账号操作租约和公共账号操作并发预算。
- 提链 worker 已在远端提交前在线查活；只有明确 Token 失效（包括 HTTP 401、已过期标记）才调用现有强制刷新流程，并在刷新成功后从数据库重读 AT。废号、网络错误、未知查活结果和刷新失败都会停止远端提链。
- 单账号和批量提链入口在入队前检查 Plus 免费试用资格、账号停用状态和 Token 是否存在，但执行时尚需再次校验资格，以覆盖排队期间账号状态变化。
- 当前 UI 的统一任务中心是通用表格；账号记录仅保存最近一次提链业务字段，未拆分远端提链、支付和本地 Plus 到账三类状态。
- 提链并发目前共用 `ACCOUNT_BATCH_WORKERS`，`EXTRACT_LINK_QUEUE_LIMIT` 在模块导入时读取。新增平台并发上限不能替代公共并发预算，也不应让超出平台上限的任务占住公共 worker。
- Huanguang 文档描述的 checkout 创建需要入口和出口代理，并返回 `job_id`、`job_secret`；进度查询与 Plus 到账核验是不同状态。其创建接口没有文档化的幂等键。
- Lumen Flow 把 checkout 创建、支付、支付同步和 Plus 核验分成不同接口/状态；checkout 成功不代表已付款，付款成功也不直接证明 Plus 已到账。自动支付能力受支付渠道限制。

参考资料：[Lumen Flow Checkout API](https://int31.space/public/checkout-api)、[幻光 API 文档](https://chongyun-link.xiaoliai.shop/static/api-docs.html)。

## 设计

### 1. 独立提链工作台

- 在主侧栏添加一级“提链工作台”，不嵌入账号页或任务中心子菜单。沿用当前 tab 导航、浏览器历史和移动端侧栏行为。
- 主视图采用响应式任务卡片，保留页面原型的紧凑信息密度：顶部按任务状态统计和筛选，主体卡片展示账号、平台、模式、Run/重试次数、进度与时间。
- 每张卡片分别展示账号/AT 预检、提链、支付、Plus 到账核验四段状态，不能用一个“完成”覆盖相互独立的结果。主要筛选包括全部、处理中、成功出链、成功支付、Plus 已确认、失败/待确认；另外支持平台、运行模式和账号搜索。
- 卡片操作包括查看提链结果、复制/打开支付链接、同步支付状态和重跑。敏感值只在用户明确点击对应操作后通过现有受控接口读取；列表、事件和默认任务详情不包含 AT、CDK 或 `job_secret`。
- 工作台提供批量选择账号、选择平台和运行模式后提交任务。账号页既有单个/批量提链入口继续保留，并打开工作台且带入已选账号，避免已有操作路径突然消失。

### 2. 平台适配器与运行模式

使用 provider registry 统一平台标识、能力声明、配置解析、请求/状态归一化和错误分类。初始适配器为现有提链 API、Lumen Flow、幻光；运行任务快照保存 `provider_id`、`mode`、提链类型和非敏感选项，重跑沿用同一平台与模式。

运行模式明确区分；工作台只允许选择在全局和对应平台配置中同时启用的模式：

- `extract_only`：创建 checkout/提链并返回链接；不得请求任何支付接口。该模式是新建任务默认值。
- `manual_payment`：只提供已创建的支付链接与状态同步，不触发平台自动扣款。
- `auto_payment`：仅当对应平台的自动支付配置开关已开启、适配器声明支持所选渠道，且用户在本次任务提交时明确选择，才允许进入自动支付阶段；每次批量提交只做一次整体确认，不要求逐账号核对。

适配器统一归一化提链结果、远端 checkout 状态、付款状态、错误/未知结果、状态查询能力、取消能力和幂等能力。provider-specific 字段仅保留在适配器内部，不扩散到 WebUI 与共用 worker。

### 3. 账号预检、AT 与权益确认

任务执行时重新读取 PostgreSQL 账号记录并确认：账号存在、未标记停用、仍符合已确认的 Plus 免费试用条件、没有冲突中的账号操作、具备可用于预检的账号凭据。批量入队时的筛选不能替代执行时检查。

预检复用现有 `_ensure_extract_token` 和 `run_account_live_check_inline` 路径：有效 AT 直接使用数据库中的最新值；明确失效时才调用现有 AT 刷新/重登流程；停用账号、网络故障、`request_unknown`、其他非 Token 错误或刷新失败都不创建远端任务。不要为省一步预检而盲目提交旧 AT。

付款状态确认为成功后，系统执行一次账号在线检查；AT 仍有效时不做无意义的强制重登，只有检查明确判定 AT 失效时才走已有刷新流程。随后复用现有套餐查询能力确认 Plus 状态。支付成功与 Plus 确认分开保存和展示；权益仍未出现时进入“支付成功，Plus 待确认”，而不是失败或已到账。

### 4. 远端任务、状态和恢复

- 提链操作继续作为统一任务中心可识别的 durable operation；运行事件按 `preflight`、`refresh_token`（按需）、`extract_link`、`payment`、`plan_check` 分阶段记录。
- 保存归一化的平台、模式、远端任务 ID、四段状态及安全摘要，以便卡片筛选、重跑和审计。可复制的提链/支付链接只由授权后的任务详情操作读取，不进入公开列表摘要或日志。
- 幻光的 `job_secret` 等远端查询凭据需要跨进程重启恢复；为远端每个 Run 提供隔离的私有存储接口，私有字段不进入 `operation_tasks`/`operation_runs` 的公开投影。只允许内部适配器读取，不复用会清洗掉 secret 字段的 `operation_resources.detail`。
- 对已有远端 job ID 的中断任务，启动恢复只继续查询/收口该 job，不再创建新 checkout。新的恢复逻辑必须覆盖进程重启，避免永久 `running`。
- 超过某平台并发上限的 durable Run 留在 queued，由 dispatcher 在有该平台容量时领取；不得先占公共 executor 线程再阻塞等待 provider semaphore。总并发仍受现有 `ACCOUNT_BATCH_WORKERS` 限制。

### 5. 重跑与未知结果

遵守项目现有批量任务约定：可重跑的失败/中断任务不因远端没有返回正文而一律禁止重跑，重跑创建同一逻辑任务下的新 Run，并保留原 Run 事件和平台/模式快照。

重跑前先利用已保存的远端任务凭据查询原任务：已成功则补写本地状态或继续 Plus 核验；仍运行则继续监控；明确失败才按平台能力重试对应阶段。若远端创建响应完全未知且平台不支持幂等查询/创建（当前幻光文档未提供幂等键），重跑仍允许创建新任务，但把“可能重复创建/支付”作为批次级风险提示，并完整保留前一次 `request_unknown` 证据。支付仅在 `auto_payment` 模式执行；支付成功或状态未知时不能在后续 Run 中盲目再触发扣款，必须先查到可判定的旧订单状态。此限制作用于支付阶段，不阻断提链任务按项目约定重跑。

### 6. 配置与并发

所有工作流开关都在“配置 → 服务集成 → 提链”中维护，工作台不提供绕过配置的开关。至少包括：

- 全局提链总开关、默认平台和默认运行模式。
- 每个平台的启用开关、提链能力开关、手动支付能力开关、自动支付能力开关、默认提链类型和独立并发上限。
- 支付成功后的自动查活开关、AT 明确失效时自动刷新开关、套餐/Plus 复核开关。
- 每个平台独立的 API Base、CDK/凭证、请求超时、事件/轮询间隔与超时。

自动支付能力默认关闭；未配置启用的平台不能出现在任务选择器中，未开启的支付/复核动作不能被 API 请求参数强制打开。每个平台的自动支付配置仍需与平台适配器支持的支付渠道取交集。密钥使用 `secret=True` 和 `.env` 存储，不进入普通配置快照、任务数据、README 示例值或日志。保留现有 `EXTRACT_LINK_*` 字段作为现有平台的兼容配置，不能因新增 provider 让旧任务切换平台。

平台并发按 provider 单独配置，默认保守值由实现阶段依据当前 worker/队列边界确定；实际并发同时受全局 `ACCOUNT_BATCH_WORKERS` 上限约束。队列上限与并发上限分开。配置变更需通过当前配置 schema 与环境快照机制生效；不再以模块 import 时的静态 semaphore 作为唯一并发事实。

幻光请求使用现有代理池中的合格入口/出口线路并绑定到任务 Run。远端任务未终止或结果待确认时不得提前释放线路；无法取得所需线路时，在远端创建请求之前明确失败。

### 7. 持久化与向后兼容

- 保留目前账号页提链字段作为最近一次结果的兼容投影，工作台历史以 durable operation task/Run 为准，不把账号表当作任务历史。
- 任务数据只保存 provider、运行模式、类型、可公开的配置版本标识和非敏感选项；CDK、AT、代理认证、`job_secret` 及远端完整响应不写入普通 task data、Run event 或日志。
- 若需新增 PostgreSQL 表/字段，沿用项目 storage 层、显式白名单读模型与私有字段分离；迁移和测试必须使用项目隔离 schema，存储测试继承 `tests.support_pg.PostgresTestCase`。
- 已有 `extract_link` 任务和重跑仍按旧 provider 兼容执行；老记录缺少 provider 时固定解释为现有平台，不能读取新默认平台覆盖历史行为。

## 验收计划

### 自动化验证

- provider adapter 的请求契约、状态映射、支付阶段 gating、未知响应分类与敏感字段脱敏测试。
- 提链前查活成功、明确 AT 失效后刷新并重读、非 Token 错误停止、废号跳过、排队后资格变化的流程测试。
- 同任务重跑保留 provider/mode；未知远端创建仍能重跑且保留历史；已支付/付款未知状态不重复调用支付接口。
- provider 并发上限、共享账号操作预算、排队不占公共线程、进程重启后继续查询远端任务的验证。
- PostgreSQL storage tests 使用隔离测试 schema；不连接生产 `turb_console`。
- 当前 WebUI 真实浏览器验收桌面与移动布局、卡片筛选/分页、创建与重跑、阶段状态和错误反馈。

### Lumen Flow 无支付冒烟测试

1. 只读筛选 2026-10-14 前后创建、仍为活跃账号、免费 Plus 试用资格已确认、没有现存提链/支付任务且没有已支付状态的候选账号；选择一个样本，不输出账号身份。
2. 提交前执行一次现有在线查活流程；如 AT 明确失效，才允许复用既有刷新路径。若账号已停用、刷新失败、查活结果未知或资格不再成立，则不向 Lumen 提交。
3. 使用用户提供并仅保存在配置 secret 中的 Lumen CDK，以 `extract_only` 提交单账号任务。测试断言并观测调用路径没有访问 `/momo-payment` 或其他支付接口。
4. 观察持久化 Run、远端提链状态、出链结果及 CDK 扣次；确认工作台卡片显示“成功出链 / 未支付 / Plus 未确认”。不打开支付链接，不触发付款。

如果没有满足条件的账号、配置无法安全写入 secret、或平台尚未接受任务，保留为未完成的外部验收，不改用其他账号或支付方式扩大测试。

## 非目标

- 首个 Lumen 冒烟不测试或触发支付。
- 不把远端 payment/checkout 成功推断为 Plus 已到账。
- 不引入 SQLite、文件队列或替代 PostgreSQL 的本地状态源。
- 不改造注册主链路、账号查活本身、全局账号操作预算或无关 UI 页面。
- 不在界面默认展示或复制 Token、CDK、代理完整地址、远端私有查询凭据。
