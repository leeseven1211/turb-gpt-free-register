# Team 管理菜单与业务流程设计

日期：2026-11-27。版本：v1。状态：业务规则及 HTTP 契约已收口，后端已在独立工作区实现并进入交付验证；前端由 Antigravity 独立开发，服务尚未部署。实际验收范围见[后端验收记录](../reviews/2026-11-27-team-backend-acceptance.md)。

已确认的账号菜单为「活跃账号」「Team 账号」「归档账号」，保留现有「活跃账号」名称。后续由 Codex 负责后端、Antigravity 负责前端，共用 [Team HTTP API 契约 v1](2026-11-27-team-management-api-contract.md)，在各自工作区按同一契约开发。

本次修订收口：本地单账号单 Team、已购席位优先及明确的本地人数上限、异步绑定探测、更换管理母号、双路径选人与本地预检、窄字段及物化计数、精确 Team 任务过滤。单 Team 约束替换旧稿允许同一账号主动加入多个 Team 的规则；远端已有的多 Team 事实仍完整保留，涉及多个本地 Team 时标记归属冲突。

## 1. 目标与第一版范围

管理已经开通的多个 Team，从 Turb 现有账号中批量选人，自动完成邀请、接受邀请和成员关系核验，减少逐个切换账号的操作。

第一版包括：

- 绑定已有账号管理的 Team，读取工作区身份、套餐、角色和成员。
- 从 Team 详情或账号页选择已有账号，批量邀请并自动加入指定 Team。
- 同步成员、邀请及订阅状态，保留最近一次成功读取的数据和时间。
- 展示逐账号结果，支持停止、失败重跑和进程重启后恢复。

第一版以用户明确选择的一个目标 Team 为一次批次的范围。跨 Team 自动分配、自动补位、定时轮换成员、自动购买套餐和修改订阅另行设计。加入后的 Codex 授权不属于本轮范围。

同一本地账号默认只允许一个 Team 的成员或管理归属，已受理的加入意图也固定目标 Team。本版不提供强制加入第二个 Team 的开关。

## 2. 菜单结构与取舍

推荐在侧栏「账号」之后增加一个一级入口「Team 管理」，直接进入 Team 列表。

```text
总览
注册
账号
  活跃账号
  Team 账号
  归档账号
Team 管理
Codex 授权
批量任务
任务中心
……
```

模块内的层级：

```text
Team 管理
  Team 列表
    Team 详情
      成员
      邀请
      查看相关任务 → 统一任务中心
```

「成员」「邀请」是 Team 详情的页内标签，不是侧栏二级菜单。第一版不增加跨 Team 成员总览或独立邀请记录菜单；几个 Team 的日常操作先在同一个工作区上下文中完成。

考虑过的其他方案：

| 方案 | 优点 | 取舍 |
| --- | --- | --- |
| 独立 Team 入口，详情内管理成员与邀请 | 团队身份和操作上下文集中，导航短 | 推荐作为第一版 |
| Team 列表、成员总览、邀请记录三个子菜单 | 便于跨 Team 检索 | 当前会分散同一个 Team 的操作，待出现明确需求再增加 |
| 所有动作放进账号页 | 少一个菜单 | 缺少工作区、成员和席位的管理入口，不适合作为主入口 |

账号页保留「加入 Team」快捷入口，与 Team 模块提交同一种业务请求。

### 2.1 账号视图与自动归类

账号仍使用同一份账号记录，通过成员关系和归档状态形成不同视图。

| 账号子菜单 | 范围与职责 |
| --- | --- |
| 活跃账号 | 未归档、尚无已确认 Team 成员关系的账号，作为默认账号视图；沿用现有菜单名称 |
| Team 账号 | 已确认加入 Team 的母号与成员，展示所属 Team、角色和加入状态；默认包含归档账号并提供归档标记与筛选 |
| 归档账号 | 所有已归档账号，包含已归档的 Team 母号与成员 |

自动归类规则：

- 核验加入成功后，从「活跃账号」视图转入「Team 账号」视图，不自动归档，不复制或迁移账号记录。
- 邀请中、接受待确认或加入失败，不凭执行进度提前改变账号归类，仍显示在原视图并标记进度。
- 已确认成员关系的 Team 母号同样归入「Team 账号」；仅建立管理绑定、存在 Team 优惠资格或单次套餐字段，不能单独代替成员关系证据。
- 新加入动作遵守单 Team 归属；同步发现历史或人工造成的多个本地 Team 关系时，保留所有事实并标记「归属冲突」，不自动选择一个 Team、不自动退出或移除成员。尚未绑定本地的其他远端工作区作为观察证据保留。
- 账号视图、数量、筛选和批量选择按本地 account ID 去重；历史冲突账号仍只显示一行，在详情展示全部已确认关系。
- 明确不再属于任何 Team 且不存在未决加入占用后，未归档账号回到「活跃账号」，已归档账号继续留在「归档账号」。同步失败、名单未读完整或暂时不可见不等于已离开。
- 归档状态独立保存。归档母号仍能出现在「Team 管理」中，不要求恢复归档才能继续管理。

「活跃账号」是保留的菜单名称，不等同于账号刚刚完成查活；账号可用性继续由现有状态和筛选表达。「Team 账号」与「归档账号」可以重叠，三个视图的数量不能直接相加作为账号总数。

### 2.2 单账号单 Team 归属与候选限制

以下状态均构成账号对某个 Team 的业务占用：本地管理母号绑定、已确认成员、有效待接受邀请、已受理的加入意图，以及尚待核对的远端提交结果。个人工作区不属于 Team 占用；归档不解除占用。

候选默认聚焦未被任何 Team 占用的账号。需要查看其他候选或粘贴明确目标时，已被其他 Team 占用的账号置灰，标注「已归属其他 Team」；批量预检及受理返回 `skipped`、原因码 `already_in_another_team`，并提供占用的本地 Team 引用。历史多 Team 冲突使用同一禁止新增规则，保留冲突详情。

同一 Team 的已有成员属于 `already_member`，已有邀请正常续接，已有活跃加入意图复用当前执行；不能把它们错误归为「其他 Team」。其他 Team 的申请直接跳过，不按普通账号忙排队等待跨 Team 加入。

受理时原子检查账号 Team 占用并绑定加入意图；并发请求不能分别把同一账号分给两个 Team。检查不是只在前端执行，Worker 在远端副作用前仍核对当前业务占用。

## 3. 页面职责

| 页面或入口 | 负责什么 |
| --- | --- |
| 账号 · 活跃账号 | 管理未归档且尚未确认加入 Team 的账号，保留加入中的进度 |
| 账号 · Team 账号 | 按账号查看母号与成员的凭据、所属 Team 和角色，复用现有账号操作 |
| 账号 · 归档账号 | 按独立归档状态查询，保留 Team 关联 |
| Team 列表 | 找到目标 Team，查看管理身份与最近同步摘要，进入详情 |
| 绑定已有 Team | 选择现有母账号，识别其工作区并建立本地管理关联 |
| Team 详情 · 成员 | 查看远端已确认的成员，关联已有 Turb 账号，发起批量加入 |
| Team 详情 · 邀请 | 查看邀请及加入成果，继续接受、重跑和追踪具体任务 |
| 加入 Team 表单 | 确定目标 Team 与固定账号名单，一次提交完整流程 |
| 统一任务中心 | 查看执行阶段、错误证据、历史 Run、停止与重跑 |

Team 模块回答「谁在这个 Team、谁还没进来」；任务中心回答「这次执行到了哪一步、为什么失败」。

## 4. Team 列表

主操作为「绑定已有 Team」。其他操作为「同步选中」及进入对应 Team；保持现有列表的工具栏、数据、分页结构。

| 字段 | 展示规则 |
| --- | --- |
| Team | 工作区名称；可附本地备注名，实际 workspace ID 在详情中提供 |
| 母账号 | 现有账号的邮箱与本地 ID，标记账号是否归档 |
| 管理角色 | 最近一次确认的角色；无证据时显示「待核验」 |
| 成员 | 已确认成员数，包含母号；尚未同步显示「待同步」 |
| 待接受 | 远端仍有效且待接受的邀请数，独立于成员数 |
| 处理中 | 本系统正在邀请或接受的目标数，独立于远端成员与邀请统计 |
| 订阅 | 最近一次成功读取的套餐状态及到期时间 |
| 最近同步 | 时间及本次同步结果；失败时保留旧数据并标记其时间 |
| 操作 | 查看、加入账号、同步；相关任务放在更多操作中 |

不凭本地账号数量推算工作区成员数。远端成员可能包含 Turb 未导入的账号。

列表统计是各自含义的快照，「成员」「待接受」「处理中」可能存在交集，界面不得直接相加解释为占用席位。

列表从 `team_workspaces` 的窄字段读取 `confirmed_member_count`、`pending_invite_count`、`last_synced_at`、`last_sync_status`。尚未完成一次完整同步的计数为 `null`，不显示为零。`processing_count` 仅对活跃状态部分索引覆盖的加入意图聚合，按目标账号去重，不按父子 Task 或 Run 数量计数。

列表不实时遍历全量成员和邀请历史，不解析 `progress_steps`、完整 Session 或大 JSONB。同步成功时由持有执行围栏的事务更新事实与相应计数；同步失败保留最近成功数据及其时间。成员和邀请不是同一时刻读取时，保留各自完整性和时间证据。

## 5. 绑定已有 Team

一次绑定的操作路径：

1. 从现有账号中选择母账号，支持搜索邮箱、本地账号 ID，并能选择归档账号。
2. 提交持久的绑定探测 Task/Run，读取该账号能够访问的工作区及其角色、订阅、实际管理能力；需要刷新会话时由后台执行，HTTP 请求不等待远端完成。
3. 弹窗轮询探测摘要和阶段。工作区始终单选；仅识别出一个非个人 Team 工作区时默认预选，仍由用户确认，不自动绑定。
4. 确认时使用探测引用、目标 workspace 及管理账号在事务内建立本地关联，立即返回，后台自动入队首次 `team_sync`。绑定成功与首次同步成功分别展示。

「母账号」表示执行 Team 管理动作的身份。套餐为 Team、存在 Team 优惠、拥有个人工作区，都不能单独证明它具备目标 Team 的管理能力；是否能邀请及读取成员，以实际权限证据为准。

归档只影响账号列表归属，不要求先恢复归档才能绑定或继续管理 Team。母号凭据与认证能力继续引用现有账号，不另外输入一份密码、AT 或邮箱配置。

同一个远端 workspace 在一个部署内只建立一份 Team 事实。重复绑定时打开或更新已有管理关联，不产生重复 Team。

探测不产生 Team 业务占用，成功结果有明确的证据版本和有效期。确认绑定必须核对探测账号、所选工作区和成功证据；已被其他本地 Team 作为母号、成员或未决加入目标占用的账号，在选择器中标明归属，提交返回 `409 already_in_another_team`。绑定确认只校验本地持久证据，不在请求内重新登录或请求远端。

探测出现多个远端候选工作区，本身不构成禁止绑定的条件；用户明确单选一个目标。若已取得成员关系证据且工作区映射到其他本地 Team，则纳入本地归属检查，不能因尚未完成手工绑定而漏掉该关系。其他未绑定本地的远端关系继续保存，不自动退出或删除。

绑定写入与首次同步任务采用同一持久事务或现有持久 outbox 保证：重启后仍能恢复首轮同步，不留下永远没有初次同步任务的工作区。

## 6. Team 详情

详情提供可直接定位的地址，刷新后仍能回到同一 Team 和标签。返回列表时保留筛选、分页与滚动位置。

头部显示工作区名称、母账号、角色、订阅、最近同步时间。主操作为「加入账号」「同步」；更多操作为「查看相关任务」「更换管理母号」「重新核验权限」。

### 6.1 成员标签

成员表以远端已确认的工作区成员为范围。

| 字段 | 规则 |
| --- | --- |
| 成员 | 邮箱或远端可读身份；远端未返回的字段不补造 |
| 本地账号 | 匹配已有 Turb account ID；未匹配显示「未入库」 |
| 角色 | 该成员在此工作区的实际角色 |
| 成员状态 | 已加入、已离开或待确认；附最近核验时间 |
| 加入时间 | 仅显示远端或本系统确实记录的时间，不能拿首次同步时间代替 |
| 最近任务 | 本系统与该成员相关的最近一次操作和结果 |
| 操作 | 查看本地账号、查看相关任务 |

远端成员未入库时保留在成员表，不自动创建一个缺少凭据的本地账号。

某成员在一次同步中没有出现，不能立即判定其已离开；必须确认读取成功且名单完整，或取得明确的成员关系变更证据。

移除成员、修改角色、自动退出 Team 不放入第一版动作。

### 6.2 邀请标签

邀请表同时保留本系统提交的加入目标与已同步到的远端邀请。本地 `invitation_id` 标识加入记录，在尚未发送远端邀请时也可存在；远端邀请标识单独保存，允许为 `null`。列表按目标聚合最近进度，历史发送、撤回和接受记录在详情中保留。

| 六列字段 | 规则 |
| --- | --- |
| 目标账号 | 本地账号 ID 与邮箱；外部邀请可显示「未入库」 |
| 业务事实 | 两行分别展示邀请事实与加入事实，不把邀请发出当作已加入 |
| 执行与阶段 | 两行分别展示最近执行结果与当前阶段 |
| 结果摘要 | 具体原因短语，详细证据进入任务详情 |
| 时间 | 最近操作与最近核验时间 |
| 操作 | 继续加入、重跑、查看任务，按实际状态提供 |

「继续加入」复用完整加入流程：已经存在邀请时续接接受步骤，已经是成员时确认成果，不要求用户判断应该重发还是继续。

外部目标缺少本地账号时可以查看远端邀请，但自动登录和接受仍需要有效的本地账号关联。该状态直接说明缺少什么，不把整批其他账号阻断。

成员表与邀请表维护 `last_task_id`、`last_run_id`、业务状态、执行状态、阶段和结果码等窄字段。列表不逐行读取任务完整步骤或历史日志；详情按引用进入统一任务中心。

### 6.3 更换管理母号与重新核验权限

新母号先通过异步探测确认它已经属于目标 workspace，并具备所需管理能力；同时遵守单 Team 占用约束。校验通过后通过带 `expected_revision` 的本地配置更新，原子切换管理身份；失败保留原母号绑定及已有成员事实。

这项操作只变更 Turb 使用哪个账号管理工作区，不自动邀请新母号、不转移远端所有权、不移除旧母号。旧母号没有明确离开前继续占用原 Team 归属。

重新核验权限生成独立后台任务，返回任务引用。原母号掉权限时保留 Team 与历史数据，显示具体限制；不把权限失败伪装成工作区已不存在。

已经发送的远端请求保留其原管理账号和版本，不在请求中途换身份。其真实回执按原请求身份、目标 workspace 和执行围栏保存，不能仅因母号已更换而丢弃。更换完成后的后续远端动作，在步骤边界重新取得当前管理版本；旧执行不能覆盖新管理配置或较新的远端快照。

## 7. 批量加入的两条入口

### 7.1 从 Team 详情发起

点击「加入账号」，目标 Team 已固定，提供轻量候选选择器：搜索、粘贴邮箱或本地 ID、排除已归属其他 Team 和已确认废号，以及高频快捷筛选。粘贴目标通过本地集合解析得到账号引用，不触发登录或远端请求；无法匹配的输入逐项说明。

复杂多维筛选通过 `?target_team_id=<id>` 联动现有账号页，沿用该页筛选与跨页选择能力，返回时保留目标 Team 和来源上下文。

### 7.2 从账号页发起

在现有账号列表跨页勾选后，点击「加入 Team」，选择一个已绑定 Team。沿用本次账号 ID、邮箱快照和选择范围，不要求重新筛选。

两条入口统一支持显式 `account_ids`，或已固定的 `selection_id` 加 `selection_revision`，二选一；写入提交使用同一个幂等键契约。跨页复杂查询复用现有名单快照能力，但需要新增 `team_join` 操作目录及目标 Team 参数校验，不能直接拿其他操作的名单充当 Team 加入名单。

两条入口使用同一个表单和同一种提交规则：

- 目标 Team 与成员名单在提交时固定，后续列表筛选变化不改变这批目标。
- 成员角色默认为普通成员，不在邀请流程中自动赋予管理员或所有者权限。
- 默认自动接受邀请，保留个人工作区；不自动合并个人数据。
- 对本系统已知的重复目标去重；远端已存在邀请或成员时，执行时核对并续接。
- 其他 Team 的母号、成员、有效邀请和未决加入占用归入 `skipped / already_in_another_team`；同 Team 的邀请续接、成员跳过和运行复用分别统计。
- 提交只表示任务已受理，显示回执和「查看任务」「查看 Team」入口，不显示「已加入」。
- 受理后保留当前页面上下文；用户可主动查看进度，不强制跳走。
- 部分目标无法受理时显示逐项原因；成功受理与未受理的数量分别展示。
- 账号忙时按既有调度规则等待，不把短暂占用当作永久失败。

表单显示本批选择人数、已确认成员、待接受邀请、拟新增目标，以及数据最近同步时间。远端事实尚未读取时显示「执行时核对」，不伪造精确人数。

### 7.3 提交前本地预检

新增只读 `POST /api/teams/{team_id}/join-preview`，只做本地集合查询，不创建选择快照、任务、业务占用或席位预留，不刷新 AT、不读取远端。

返回去重后的净新增目标、本 Team 待续接邀请、同 Team 活跃执行、已有成员跳过、其他 Team 跳过、缺少认证材料及目标不可用数量，同时返回席位和人数上限余量、依据与快照时间。互斥分类用于统计，附加说明不重复计数；缺少资料不能伪装为已在线验证失败。

预检的性能验收目标为服务端 P95 小于 50ms，按名单规模分别测量并包含本地校验和序列化；这不是已完成的性能结论。不得为达到目标而截断名单或仅统计当前页面。

预检不是容量预留或执行许可。正式受理必须在事务中重新核对归属与容量，实际执行仍核验远端现状；并发变化不能沿用旧预检结果硬写。参数与返回字段以 [HTTP 契约](2026-11-27-team-management-api-contract.md) 为准。

## 8. 人数、席位与费用

必须区分三类数据：

| 名称 | 含义 |
| --- | --- |
| 成员数 | 远端确认已属于该工作区的人员，含母号 |
| 已购席位 | 远端明确返回的订阅或计费席位事实 |
| 计划人数上限 | 用户为自动拉人配置的本地执行上限，含母号 |

已购席位不是本地人数上限，成员数也不是已购席位数。读取失败显示「未返回」，不能把缺失当作零。

默认开启「仅使用已购剩余席位」，第一版不提供超出有效上限继续拉人的开关，不单独购买套餐或修改订阅。字段固定为 `purchased_seats` 与 `planned_member_limit`，本地计划人数上限包含母号。

| 已购席位证据 | 本地计划人数上限 | 有效上限与提交规则 |
| --- | --- | --- |
| 已返回非负整数 | 未设置 | 使用已购席位数作为上限 |
| 已返回非负整数 | 已设置正整数 | 使用两者较小值 |
| `null`，未返回 | 未设置 | 新批量拉人提交返回 `409 team_limit_required`，先配置本地上限 |
| `null`，未返回 | 已设置正整数 | 使用本地上限，容量依据明确标记为 `planned_member_limit` |

`purchased_seats=0` 是已确认零容量，不能当成 `null` 走本地上限回退。上限下降不移除成员，已超上限时暂停新增并保留待办。

占用容量为已确认成员、有效邀请、已预留名额及结果未确认目标的去重并集，包含未入库的远端成员和外部邀请；母号只计一次。邀请变成员、同 Team 重跑或更换 Run 都不重复占位。因名额不足而等待的已受理目标固定 Team 归属，但只有获得容量后才能发送新邀请。

容量按净新增预留判断：同一目标已有有效预留时沿用原位，不能因当前占用等于上限而再次拒绝它；上限已下调到实际占用以下时，暂停新的远端邀请，接受和核验仍可继续。

成员或邀请名单尚未完整同步时，`occupied_count`、`available_count` 为 `null`，不把缺失视为零、不授予新增容量。符合本地上限配置规则的目标可以受理后等待同步；首次同步、母号更换及重启恢复使用相同规则。

未知已购席位时，本地上限是用户明确配置的总人数边界，不能反填 `purchased_seats` 或承诺已证明不增费。UI 同时显示默认策略和当前依据：按已购席位，或已购数未返回、按本地上限。远端人工操作、另一部署及邀请本身的计费规则仍须真实验证。

已存在的本 Team 邀请只继续接受或核验、不新增邀请及占位时，可以续接已确认阶段；重跑若需要新发邀请，重新遵守上限要求。缺回执不会永久关闭重跑入口。

## 9. 执行流程与完成标准

一次加入流程按账号记录进度：

```text
核对母号与目标工作区
  → 核对现有成员和邀请
  → 需要时发送邀请
  → 使用目标账号认证
  → 发现并接受对应工作区邀请
  → 核验成员关系
  → 保存成员事实与工作区认证上下文
```

成功标准为：目标账号在指定 workspace 的成员关系已确认，并且本次要求的本地结果已经保存。发信成功、邀请列表出现目标、点击接受按钮，都只是阶段成果。

母号发送邀请和成员接受邀请使用不同身份，设计为独立子任务，由父任务协调。任务中心既能看整批结果，也能定位某个成员的具体步骤。

如果已确认远端加入、但本地保存或后续会话核验失败，保留「已加入」事实，执行结果为部分成功或对应阶段失败；重跑只补未完成事项。

接受邀请的具体实现仍需验证：优先调查已登录成员能否直接读取待接受工作区；确实需要邮件链接时，再增加独立邀请邮件读取能力。现有统一取码入口不能直接当作邀请邮件读取接口。

## 10. 状态、错误与重跑

业务成果与任务执行分别保存：

| 情况 | 业务事实 | 执行展示 |
| --- | --- | --- |
| 邀请明确发出，成员尚未接受 | 待接受 | 继续执行或等待接受 |
| 邀请回执丢失 | 邀请待确认 | 失败，说明回执缺失阶段，允许重跑 |
| 已接受但成员核验未完成 | 已接受、加入待确认 | 核验中或核验失败 |
| 成员核验成功且保存成功 | 已加入 | 成功 |
| 远端已加入，本地保存失败 | 已加入 | 部分成功或保存失败 |
| 用户停止 | 已确认成果保留 | 已停止，未执行目标保留 |
| 历史已加入，后来明确退出 | 历史接受事实保留、当前已离开 | 原历史任务结果不改写 |

重跑先读取远端现状，由系统决定跳过已完成步骤、续接已有邀请或重新发起邀请。远端未返回内容不构成永久禁止重跑的条件，也不要求用户逐个手工核对。

网络重试沿用原请求幂等键并返回原受理回执。同账号同 Team 的同一加入意图若仍有活跃执行，返回当前引用；已有终态的人工重跑创建新 Run，保留原运行结果。同账号申请其他 Team 按 `already_in_another_team` 跳过；刷新 AT、改密等认证互斥按既有规则排队，不能复用其他操作的任务。

重启后根据持久检查点恢复并核对远端，不让记录永久停在进行中。

账号 Team 占用及名额属于持久加入意图，不属于某次 Run 或 Worker 租约。失败、停止、`request_unknown` 和租约到期不会自动释放；同 Team 重跑复用原占用。确认未产生远端效果，或取得无成员及无有效邀请的完整证据并确认原执行已停止后，才由系统释放，无需用户逐个核对。

错误至少明确到以下阶段和原因：

- 母号认证：会话过期、凭据缺失、具体认证挑战失败。
- 工作区与权限：目标不可见、管理权限不足、订阅或工作区被远端明确限制。
- 邀请：目标被拒绝、人数上限、限流、传输失败、回执缺失。有效邀请已存在属于正常续接事实；无法继续时，按实际权限、目标身份或邀请失效等原因分类。
- 成员认证：账号身份不匹配、密码被明确拒绝、缺少所需 OTP 或 TOTP。
- 接受：目标邀请不可见、过期、已撤回、目标工作区不匹配、页面或响应无法解析。
- 核验与保存：成员事实未确认、本地写回失败、执行租约失效、运行中断。

程序异常保留发生阶段、异常类型和必要诊断证据，不统一落成「未知错误」。HTTP 401/403 只作为响应证据，不能单凭状态码认定密码错误或账号停用。

新增错误码与短语统一登记到 `core/operations/error_labels.py` 及既有分类器，生成前端错误目录；默认短语不超过 10 个 Unicode 字符。固定码、阶段和重跑语义在 HTTP 契约中列明，不依赖前端解析错误原文。

## 11. 账号、工作区与任务的数据边界

| 对象 | 负责保存的事实 |
| --- | --- |
| 现有账号 | 用户身份、邮箱、密码与认证材料、归档状态 |
| Team 工作区 | workspace ID、名称、订阅快照、当前管理账号与权限证据 |
| 成员关系 | 工作区与远端用户的关系、本地账号关联、角色和核验时间 |
| 邀请与加入意图 | 目标邮箱快照、远端邀请身份、邀请成果、加入成果、执行关联 |
| 账号 Team 占用 | 单账号有效业务归属、待接受及未决目标占用、历史冲突状态 |
| 工作区认证上下文 | 某个账号访问指定 workspace 的会话和身份依据 |
| 现有 Task/Run | 执行、步骤、错误、取消、重跑、租约和恢复 |

个人工作区与 Team 工作区可以同时存在，但本系统的新操作只允许单个本地 Team 业务归属。远端历史多 Team 事实完整保留；多个已管理本地 Team 之间的冲突单独记录，不用唯一约束覆盖或删除真实关系。同一个 Team 中不同成员仍是不同用户，不能仅凭 workspace ID 把不同成员当成同一个账号或同一份凭据。

成员加入后不能简单覆盖账号的个人工作区会话；应记录明确的目标 workspace，保持用户身份、工作区身份和认证上下文一致。现有单账号会话缓存及 AT 刷新中的身份检查，需要在业务开发阶段单独设计兼容。

Team 数据存 PostgreSQL，引用现有账号，不另建一套账号库。执行复用现有任务中心、共享调度、账号认证互斥及启动恢复；工作区另有成员去重与人数占位协调。

容量与账号 Team 占用的预留在同一事务协调；未取得容量的目标不伪装为已经预留。有效账号业务占用、同 Team 同目标有效加入意图由唯一约束兜底。管理配置更新核对当前管理版本；请求回执、成员和邀请成果核对原请求、workspace 与执行围栏，历史回执不覆盖较新的快照，计数投影随实际采用的当前事实更新。

只读性能约束：

- 工作区列表读取物化计数与窄状态，处理中数量只聚合部分索引覆盖的活跃意图。
- 成员、邀请按 `(team_id, 状态, 排序键)` 索引分页，最近 Task/Run、执行阶段及错误码直接读取窄字段。
- 团队相关父子 Task 写入可索引的 `team_id`，`GET /api/operations?team_id=<id>` 精确过滤列表、total 与 facets，不能用标题或邮箱模糊匹配替代。
- 账号视图及候选过滤读取关系和占用索引，归属、废号及认证材料能力由集合查询产生，不逐账号解密凭据。
- GET 和本地预检不做远端同步、不写投影，也不解析完整历史步骤或大结果 JSONB。

本地与 Oracle 继续分别部署和保存事实。若两端管理同一远端 Team，单端数据库锁不能协调另一端，远端现状仍是最终核验依据；本轮不引入跨部署调度系统。

## 12. 交给 UI 设计模型的说明

前后端对照 [HTTP API 契约 v1](2026-11-27-team-management-api-contract.md) 开发；该契约定义请求、响应、分页、筛选、枚举、异步任务及幂等行为。接口状态以服务端字段为准。

需要表达的界面和状态如下：

1. 账号子菜单：沿用「活跃账号」，增加「Team 账号」，保留「归档账号」；按第 2.1 节表达成员归类与归档状态。
2. Team 列表：有数据、空列表、同步中、同步失败但有旧数据。
3. 绑定已有 Team：选择账号、多个工作区、已绑定、权限不足、归档母号。
4. Team 详情 · 成员：本地已关联、未入库、角色、最近核验、当前已离开。
5. Team 详情 · 邀请：邀请与加入事实、最近任务结果、继续加入和重跑入口。
6. 加入 Team 表单：固定 Team 或选择 Team、账号范围、人数与席位摘要、部分受理回执。
7. 与任务中心衔接：任务详情、整批筛选、返回来源页面的上下文。
8. 更换管理母号与重新核验权限：异步探测、旧绑定保留、单选目标及版本冲突反馈。
9. 仅使用已购剩余席位的默认策略、已购数为 `null` 时配置本地上限的明确反馈。

列表沿用现有中文文案、列头筛选、跨页选择、两行单元格及分页规范。状态同时有文字，不只依赖颜色；进行中更新不打断查看，不自动打开第一条任务。

未验证的成员数、席位、权限、时间显示待同步或未返回，不用示例数字冒充当前真实数据。设计阶段如使用示例，必须明确标记为示例。

UI 可据此安排布局、组件和视觉细节；工作区身份、人数含义、完成标准与重跑语义由本设计约束。

挂载约定固定为侧栏 `data-tab="teams"`、容器 `#tab-teams > #teams-page-root`，构建入口 `frontend/src/teams.ts` 输出 `task-center/teams.js`。沿用现有导航外壳及按需挂载，页面拥有自身查询、选择、弹窗、轮询和可见性状态。

前后端分别在独立工作区开发。Codex 负责领域逻辑、存储、运行恢复、HTTP 实现及契约变更；Antigravity 负责导航、前端入口、页面和 API 客户端。共享契约发生变化时先更新版本与说明，不能由任一侧自行改变字段含义。

## 13. 后续验收场景

业务开发时至少验证：

- 归档母号绑定及同账号多个工作区的准确选择。
- 「活跃账号」「Team 账号」「归档账号」的筛选范围、成功加入后的归类、加入待确认时保留原视图，以及历史多 Team 冲突的账号去重。
- 归档 Team 母号的查询与管理、成员关系及未决占用明确解除后按原归档状态归类。
- 跨 Team 母号、成员、待接受邀请与未决任务的候选置灰、预检跳过、并发受理唯一约束。
- 单选工作区及唯一候选预选、异步探测、确认绑定后首次同步恢复。
- 更换母号失败保留旧绑定、更换成功保留旧母号成员关系、旧执行不能覆盖新管理版本。
- 同一个 Team 重复绑定、成员已加入、邀请已存在时的去重与续接。
- 从两条入口提交同一组账号，受理与执行规则一致。
- 小批次邀请、自动接受和指定工作区的真实成员核验。
- 邀请成功但接受失败、接受成功但核验失败、远端加入但本地保存失败。
- 回执丢失后整批重跑、进程重启恢复、停止后再次继续。
- 同 Team 两批并发、同账号操作冲突、人数与席位统计去重。
- 已购席位为 `null`、零及正整数；本地上限缺失、调整及下降后的容量行为。
- join-preview 无远端调用、无数据库写入、无隐式占位，按名单规模记录 P95 是否小于 50ms。
- 工作区物化计数、活跃部分索引查询、成员及邀请窄字段分页、任务中心精确 `team_id` 过滤的一致性。
- 同 Team 两个成员的认证材料互不覆盖；个人与 Team 工作区不混淆。
- 邮箱源只能取 OTP、需要读取邀请链接时的明确能力反馈。
- 界面保留历史成功事实、同步时间、原列表上下文及失败项重跑入口。

本轮只检查设计文档，不运行注册、邀请、接受、支付或成员移除动作。
