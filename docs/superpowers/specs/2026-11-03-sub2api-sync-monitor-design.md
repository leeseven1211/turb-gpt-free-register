# Sub2API 同步、上传配置与异常巡检

用户已确认实施对比分析中的第 1、2、3 项。本次仅扩展 Sub2API 管理与 Codex 任务编排，不改变任何注册驱动、认证请求、页面操作或注册重试策略。

## 目标与边界

1. OAuth 授权、Token 刷新后统一完成凭据上传、清错、恢复调度；失败保留有效凭据，持久记录阶段并仅补传。
2. 配置分组、代理、并发、优先级、负载因子和允许模型；留空保留既有远端设置，新账号采用后端默认值。
3. 可选巡检远端 OpenAI OAuth 异常账号，按邮箱归并，先补传，再依据明确认证错误刷新或通过现有 Codex 入口重授权。

自动补传与巡检默认关闭，现有手工入口保持可用。本地与 Oracle 分别使用自己的配置、数据库和账号，只共享代码。本次不操作真实远端账号，不自动启用线上开关。

## 实现选择

采用现有 PostgreSQL 存储、durable gateway 与账号租约。相比在控制台增加内存队列，这样能够沿用任务中心、取消、失败重跑、并发限制和进程恢复；相比把同步塞回注册执行器，独立任务能够只重传而不重复认证。

### 管理客户端

单次操作捕获后端、鉴权、超时与上传选项，使用不含凭据的后端摘要绑定持久任务。更新原账号前核验 ID、平台、类型和邮箱。已有账号定向 PUT 合并凭据，保留模型映射及未显式填写的配置；新增才走既有导入接口。清错、启用分别报告阶段。多个同邮箱远端账号由巡检逐个记录 ID，不以任意搜索结果覆盖。

### 持久补传

新领域表保存凭证名称、后端摘要、目标 ID、凭证代际摘要、失败阶段、重试时间和关联 Run，不复制 Token 或管理员密钥。按后端、凭证、目标去重；新代际覆盖待同步目标，旧执行不得回写覆盖新结果。任务使用 `openai_interactive` 账号租约，与刷新、授权互斥。账号忙碌时保留待处理状态，失败退避最高 300 秒。重启恢复队列并核对原 Run，避免永久 running。更换后端后旧 ID 不得流向新后端。

### 异常巡检

默认每 300 秒检查一次，先调度已有补传，分页读取远端 error 账号并按邮箱归并。归档、明确停用、账号忙碌和冷却中的记录单独计数。已有新凭据优先同步；明确 Token 失效先调用现有刷新任务，明确需要重新授权时检查自动登录资料后调用现有 Codex 任务。持久记录修复阶段、原目标 ID 和凭证代际，等待原任务完成后补传，不重复启动登录。网络故障、429、5xx 与无法识别的错误分别分类，不凭通用错误推断停用，也不以任意错误触发重登。

## 配置与界面

上传参数放在现有 Codex 的 sub2api 配置小节；自动补传和异常巡检放在定时任务小节。提供安全状态摘要、立即巡检入口，任务中心识别同步任务和触发来源。所有配置同步更新 schema、模块、示例环境文件及 README。

## 验证

使用独立工作区与 `turb_test` 数据库、`test_` schema；数据库测试继承 `PostgresTestCase`。测试覆盖参数保留、身份/后端绑定、分阶段故障、补传不登录、同邮箱多目标、旧代际隔离、跨进程去重、重启恢复、错误分类和冷却。所有外部请求 mock，真实浏览器验收使用隔离服务及测试配置，不调用真实 Sub2API 或 OpenAI。完成后进行独立代码审查，明确区分测试通过、提交、推送和部署状态。
