# 注册进度、认证与资源恢复改进设计

日期：2026-10-13。状态：本地实现与隔离验证完成；代理部分按用户确认的独立池方案实施。生产运行验收另行记录。

## 1. 目标与范围

解决本次注册批次暴露的四组问题：步骤状态与计时跨线路混合；认证等待、提交和响应确认边界不完整；代理重试重复且实际耗时不受完整约束；Remail 订单未知后缺少精确恢复依据。

目标是提高成功率和可恢复性，同时让界面准确解释实际执行。不能靠把未知结果标成功、缩短正常等待、重复提交或更换邮箱来改善统计。保留原邮箱、原密码、原 Attempt；注册与续跑、CLI 与 WebUI 使用一致的业务边界。Remail 的订单改进也覆盖邮箱换绑的相同调用路径。

本次实施覆盖代码、配置 schema、现代 WebUI 和隔离测试。历史任务数据只读适配，不能用新推测改写过去的结果；不自动重跑历史任务、改写生产数据或重启服务。

## 2. 已证实的问题与证据边界

### 2.1 进度投影把不同线路当成同一次步骤

截图任务分别为原任务链 `4560 → 4610 → 4625`、`4562 → 4612 → 4626`，批次为 `20261013-103900-7975b5aa`。这些编号用于定位历史证据，不是后续测试的生产数据依赖。

- `db.begin_job_route_attempt()` 已清空当前 `progress_steps` 并保存线路历史。
- 统一事件保存了 `route_attempt_no`，但 `core/task_progress.py` 的步骤归并没有保留、隔离这个维度。
- 同一步骤使用最早开始与后续完成时间；跨线路的旧失败又通过 `_unrecovered_failures()` 覆盖当前状态。
- 注册卡片只要发现一个失败步骤，就覆盖任务结果为“部分失败”，没有区分正在重试与最终业务结果。

回放任务 4625 的事件到北京时间 13:44:45，可以精确复现“网络失败 601 秒、邮箱成功 310 秒、浏览器成功 327 秒、登录仍执行”。真实活动是第七次线路尝试分配网络，登录活动来自第三次线路。任务 4626 的 128/122/129/472 秒也可精确复现；最后线路实际分别为 20/不足 1/7/354 秒。其整次执行 491 秒正确，没有混入前两次人工重跑。

关联提交：`1fb58ef`，2026-10-09 的统一步骤与日志改造。属于展示回归，不能将它当作真实注册失败的原因。

### 2.2 线路关联字段自身也可能漂移

`_acquire_registration_proxy_with_retries()` 调用 `begin_job_route_attempt()` 后，没有同步更新下一次传给供应商的线路编号；浏览器关联又使用 `initial_route_attempt_no + retry_attempt`，没有包含此前代理申请失败造成的编号推进。

因此仅在展示层增加线路过滤还不够：事件、租约、浏览器流量必须引用同一个实际线路编号，不能各自计算。

### 2.3 认证预算和请求边界耦合

`8e6200e` 引入页面接管检测：邮箱表单最多等待约 30 秒，然后 NextAuth 兜底继续消费原来的 60 秒总预算。这批首次执行的 27 次兜底中，20 次记录 `nextauth_budget_exhausted`。日志证明等待挤占了后续时间，但不能证明 React 事件检测一定误判。

还有三个独立缺口：

1. NextAuth 的 CSRF 读取与 signin POST 共用超时，失败结果没有稳定区分“POST 未调用”“已开始调用”“收到响应”“完成跳转”。因此不能仅凭预算耗尽判断允许换线重试。
2. 密码的异步点击回执不等于 HTTP 请求已经派发。Roxy 的密码保存时机、`login_password/running` 到业务检查点的映射，需要与 Protocol 已有的 `prepared/started/confirmed` 契约对齐。
3. OTP 提交后 30 秒仍留在原页且没有错误标记，会被当作卡页并重发。重发函数把点击与后续页面读取放在同一异常重试范围内，存在点击成功、读取失败后再次点击的风险。

图二实际先收到并提交了验证码，随后停页；后续两轮又出现 Remail 网络连接失败。不能据此认定第一次验证码错误，也不能认定保存的密码错误。

### 2.4 代理申请不是完整的有界操作

当前浏览器换线和代理申请各有额外重试；每次供应商申请内部又有多次提取。任务 4625 记录 42 次重复代理、3 次 SSL 错误，真正得到的租约只有 3 条。

- 同一 job 重新进入提取函数时，从相同会话参数序列重新开始，容易再次命中刚使用或仍在隔离期的端点。
- 单次 60 秒只在部分循环位置检查；锁等待、节流、HTTP 请求、出口检测没有完全受剩余时间约束。
- 批量提取没有同等的总截止时间；等待另一 worker 补充批次池时也没有完整取消、截止约束。
- 批量预取最多取整批 64 个候选，不能简单套一个单任务预算后直接截断，否则会引入新的失败。
- 批量补取与外层补充池各自维护序号，存在再次使用已尝试参数的风险。

这是原有策略在本批网络条件下放大的问题。最新套餐查询允许复用 IP 的修改不等于注册也允许复用；注册继续保留独占租约和隔离期。

### 2.5 Remail 保护了重复购买，却没有完整保存原订单意图

客户端每次领取临时生成幂等键，收到的订单号、服务凭据先留在内存，注册前失败或进程退出会丢失精确恢复关联。注册与换绑的 `except RemailOrderUncertain` 又丢弃异常对象，把安全原因统一覆盖成“订单结果待核验”。

现有恢复还会在同邮箱多个订单中选择较新的候选；订单的供应商账号、项目、服务模式和原订单身份不能用更新时间代替。

本批 33 条只保存了 `remail_order_request_unknown`。上一轮只读查询得到本批时段 17 笔已交付订单，与本地 17 个已领取邮箱数量相符，但不足以证明其余 33 次都未创建或未扣费。原始 HTTP 原因无法凭空补回。

当前 Remail 异常分支没有调用注册账号的 `_mark_registration_request_unknown()`，不能断言其污染了 OpenAI 远端账号状态。设计仍需增加未知范围以避免界面与恢复动作混淆。

### 2.6 与本次故障不能直接建立因果的改动

当前公共静态资源缓存为 `off`，相关旧执行没有启用记录；密码进度文案修改本身不改变提交动作。少量投影 deadlock 有重试记录，没有证据证明它造成此次认证或收件失败。最近 Protocol 的邮箱预算上下文也不能直接解释未传该上下文的 Roxy 执行。

早上成功批次与本批同时存在邮箱来源、并发差异，不能以两批成功率比较证明某一个修改的因果。

## 3. 方案选择

| 方案 | 收益 | 局限 |
| --- | --- | --- |
| 只修 UI 并增加超时 | 变更少 | 未知请求和订单恢复缺口仍存在，重试浪费没有解决 |
| 在现有模块补齐身份、请求事实、预算和恢复，分批交付 | 每项可独立验证，保持现有调用分层 | 需要覆盖存储、驱动和 UI 的交叉回归 |
| 重写统一注册执行框架 | 理论上可统一全部流程 | 范围过大，迁移风险高，不适合本次问题 |

采用第二种。新增代码只承担缺失的职责，不另建一套任务中心或注册状态机。

## 4. 统一身份、状态与时间语义

### 4.1 执行身份与动作关联

1. `Attempt`：同一账号注册意图，拥有原邮箱、密码、远端事实和恢复边界。
2. `Run`：一次实际执行，人工重跑产生新的 Run；注册 Run ID 与 operation Run ID 显式区分。
3. `route_attempt_no`：本 Run 内一次线路申请/使用的生命周期，由协调器调用存储接口取得，禁止本地加减推算。
4. `submission_id` / `step_instance_id`：同一线路内一次业务提交或阶段出现，供重入、去重及耗时配对。

存储的线路开始接口返回实际线路号；服务层固定绑定当前 Run、线路与步骤实例上下文，供进度、代理租约和浏览器流量共用。供应商后台补货独立于任务线路号，不自行推进任务线路。上一条线路结束后，协调器才创建下一条线路；后台获取候选不计任务“自动换线”。

新进度转换带原 job、operation Run、线路和阶段实例，业务提交事实另保留注册 Run/execution_id。转换 UUID 用于幂等，同实例终态后的迟到 running 只作为审计，不倒退当前状态；同阶段再次执行需要新的实例号。本版没有新增通用源顺序号，数据库事件 ID 仍用于读取游标。

切换线路时先结束旧线路并记录原因，再开始新线路。旧回调保留原线路身份；晚到事件可以补历史证据，不能将当前活动切回旧线路。进度序号校验与业务执行令牌校验分别处理，不能为了修展示拒绝合法的远端晚到回执。

### 4.2 展示规则

主步骤显示当前 Run 的当前线路；终态显示最后线路。历史线路和历史 Run 分层展开，分别标明“曾失败后换线”“已中断”“结果待确认”。旧失败不会覆盖当前线路 `running`；旧登录步骤不会在新线路分配网络时继续计时。

卡片总体结果读取后端本 Run/逻辑任务结果。运行期间显示“正在申请线路”“换线重试中”等当前活动；`partial_success` 仅用于已确认核心注册成功、后处理未完成的业务事实，不由任一步骤颜色推导。

后端快照升级版本并增加 `selected_route_attempt_no`、`routes`、`time_basis` 等可选字段；注册页、任务详情与日志定位共用同一快照。非注册任务没有线路信息时保持既有路径。快照修订号必须包含版本和线路选择，防止前端沿用旧缓存。

### 4.3 三种时间分别呈现

| 时间 | 定义 | 展示 |
| --- | --- | --- |
| 本次执行耗时 | 本 Run 开始到结束/当前时刻的墙钟时间 | 卡片总耗时，保持现有含义 |
| 当前线路步骤耗时 | 同一线路、同一阶段实例的开始到结束 | 主步骤 |
| 历史尝试耗时 | 每条历史线路内各自的步骤边界 | 分线路展示，本版不新增跨尝试累计值 |

登录主组包含其子步骤间的必要等待；不得把其他线路、前一次人工运行或排队时间夹进来。并行子步骤不能简单相加造成双重计数。排队等待与运行耗时分开。

认证和代理等待预算使用 monotonic 时钟；步骤展示仍依据已持久化的开始、结束时间计算，本版不迁移历史时间字段。旧秒级事件无法提供亚秒精度；缺少边界则显示“记录不足”，不编造精确值。切线可以结束旧活动的展示，但不能把未知远端结果推导为业务失败或成功。

### 4.4 兼容历史

优先级：显式线路/实例事件 → 源任务已保存的线路历史和转换 → 可证明的单线路历史 → 未知。历史 `route_attempts` 是嵌套的 `progress_steps`，适配器必须展开而不是把外层直接当阶段。

没有线路号的事件不依据日志文案、页面顺序或相近时间强行归属。保留“未归属线路的历史记录”，不足以算当前步骤的耗时。人工 Run 边界始终先于线路归并。旧数据库事件不做批量重写。

## 5. 认证提交与预算

### 5.1 请求事实优先于展示进度

新增小型浏览器提交回执模块，提供邮箱 UI、NextAuth、密码、OTP 校验与 OTP 重发共用的事实结构；不接管各驱动的页面业务逻辑。

事实至少区分：

- `prepared`：输入与恢复资料已准备。
- `dispatch_intent`：已持久化进入可能执行动作的窗口，此后崩溃不能当作未提交。
- `ui_queued`、`ui_dispatched`：本地定时器排队、点击已调用，均不等于 HTTP 成功。
- `request_observed`：观察到与操作匹配的请求元数据。
- `response_observed`：收到响应，记录状态码和白名单结果枚举。
- `confirmed`、`rejected`、`not_dispatched`、`unknown`：业务确认结果。

证据采用追加事实，允许网络事件先到、本地回调后到；不能依赖理想化的严格事件到达顺序。缺少网络观测不证明没发请求。只有同一原文档的原回执可原子取消、且确认点击尚未发生，才能认定 `not_dispatched`。

复用现有 CDP 采集连接增加白名单观察分发，不引入多个会抢日志的 `get_log` 消费者。成功路径也记录轻量请求事实；完整抓包仍是可选功能。观察器不可用时记录可观测性状态，继续依靠保守回执和页面证据，不伪造 HTTP 结果。

白名单只包含操作类别、阶段、关联 ID、HTTP 方法/状态、枚举化端点类别、时长和错误类型；不保存 URL 查询串、请求体、密码、Token、Cookie、OTP 或邮件正文。

### 5.2 邮箱准备与认证请求分开预算

第一版建议值为**准备最多 30 秒，单次提交链路与落点确认最多 60 秒，整个邮箱阶段最多 90 秒**，这是待验证设计参数，不是已证实最优值。

准备阶段包含 DOM 定位、填写校验、页面接管等待，不能每个函数各等 30 秒。正常页面就绪即继续。提交阶段只在进入 UI 提交或唯一一次 NextAuth 兜底时启动一次；NextAuth 的 CSRF、signin 和跳转共同消费这 60 秒。所有阶段仍受从邮箱操作开始计算的 90 秒外层截止时间约束。

这为慢页面准备和后续认证分配独立上限，而不是在每次循环、每次回退时重新获得 60 秒。NextAuth 内部现有 25 秒请求上限保持为子预算并受剩余时间约束；需要在日志分别记录 CSRF、POST、跳转耗时，后续再依据数据决定是否调整。

页面就绪检查保留“不向未接管的表单发送原生 GET”的限制。React 私有属性只作一种信号，补充表单连接、输入有效性、按钮可用性、页面正在导航及前端错误摘要。当前没有证据支持直接移除接管检查或固定缩短到几秒。

允许唯一兜底的条件：尚未进入可能派发窗口，或已证明排队动作未执行且完成取消。UI 点击、NextAuth POST 已可能发生时，不再次导航或重发；在原阶段等待确认，超时保留同 Attempt 的可恢复未知状态。

### 5.3 密码先保存，再进入可能提交窗口

复用已有 `save_password_checkpoint()` 和 Attempt 私有恢复上下文，不新增密码状态表：

1. 原密码或新生成密码先持久化为 `prepared`，写失败不执行点击。
2. 在可能触发异步点击之前记录 `dispatch_intent` 和保守的请求开始围栏。
3. 浏览器回执与网络观察补充实际派发证据；原有 `started` 不能被解释成已观察到 HTTP POST。
4. 只有确认响应或稳定下一步才记录确认；密码未知时保留原值，下一次仍继续同账号。

新版本驱动不再通过 `login_password/running` 推进请求已发出的业务事实，改由显式提交事件驱动。旧驱动保留兼容适配并标明证据来源，不能全局删除映射后破坏其他注册入口。

续跑直接到验证码页时只标“沿用已保存密码”，不创建本次密码提交记录。页面资料保存、账号成功和 Token 获取的现有事实仍分别确认，不能因一个回执把后续全部标成功。

### 5.4 OTP 校验与重发分开处理

不再把“提交后 30 秒无跳转、无错误”等同于验证码错误。30 秒作为诊断检查点：

- 明确无效/过期响应或可靠错误标记：允许一次受控重发。
- 请求可能已派发但结果未确认：继续原请求的有界确认，不清空输入、不再次点击；到确认截止仍未知则保留恢复上下文。
- 确认通过但页面慢：等待下一步，不再取码。
- 明确尚未点击：同一阶段内允许修复控件状态后提交原候选。

现有 Roxy 代码已将整个 OTP 阶段设为 `OTP_MAX_WAIT`，默认 240 秒，最多 3 轮共同消费，并非每轮 240 秒。首版保持这个总上限和轮数上限；将同一截止时间传入邮箱上下文恢复、HTTP、轮询、填写、确认与重发，不只在循环入口检查。一次停页确认建议从 30 秒扩展到最多 60 秒，实际等待取 `min(60 秒, 阶段剩余时间)`；30 秒处只记录诊断。轮数是上限，不承诺预算耗尽后仍补足 3 轮。任何整段预算调整都须作为单独的策略变更验证，不能暗中延长或缩短。

重发动作一旦点击即设置围栏；后续读取状态失败只能再次读取，不能再次点击。`resend unconfirmed` 与“验证码未收到”“邮箱读取失败”分别记录。未确认重发时允许在该轮原有期限内只读等待新邮件，但不得不断重置邮件时间窗口；只有新邮件的可靠时间/消息身份符合当前操作才能使用。已用候选用不含 OTP 的消息身份去重。

本版保持取码接口和本 Run 内已有候选去重，将剩余时间传入邮箱轮询；验证码只交给内部提交路径，不进入公共提交事实。统一消息身份封装未在本版引入，来源缺少可靠消息身份时不能据此证明跨 Run 邮件身份。

### 5.5 重试分类

将普通“邮箱认证总预算耗尽”从无条件代理错误识别中移出。只有结构化传输错误、明确的线路拒绝以及原 Attempt 的远端安全边界共同允许时，才自动换线。

页面未就绪、未派发请求可以在同账号内做有限恢复；派发未知不据字符串自动从头执行。该规则不把原任务永久锁死：人工重跑仍走已验证的原邮箱、原密码与检查点继续路径。

未决 `submission_id` 归属于 Attempt，新 Run 不能清空它的未知围栏。续跑先核对原动作与远端检查点；尚无新事实时只观察、读取和核验。若已有证据允许进入原账号登录恢复，则建立明确的 `resume_login` 动作，与原注册提交分开关联；不能借新 Run 重放原未知 POST、密码创建或 OTP 提交。

## 6. 独立代理池

### 6.1 职责与容量

用户确认注册、注册续跑、套餐查询及其他账号任务统一接入。选路配置仍决定代理或直连；需要代理时只向池申请租约。供应商提取、检测、复检、补货和退役不再嵌入注册批次或业务任务重试。

借鉴连接池的最小保有量、容量上限、后台维护和空闲回收，但库存对象是有供应商有效期的线路。`proxy_pool_resources` 保存库存，`proxy_leases` 保存去重锚点和每个任务的独立租约。PostgreSQL advisory lock 和行锁负责跨进程容量与领取，不依赖 WebUI 内存计数。

| 配置 | 默认 | 语义 |
| --- | --- | --- |
| `PROXY_POOL_MIN_READY` | 2 | 每个活跃供给配置的最小可用库存目标 |
| `PROXY_POOL_MAX_SIZE` | 20 | 所有配置合计的提取中、检查中、可用、使用中库存上限 |
| `PROXY_POOL_WAIT_TIMEOUT` | 60 秒 | 单次任务申请的等待期限 |
| `PROXY_POOL_MIN_TTL` | 300 秒 | 领取时要求的最短剩余寿命 |
| `PROXY_POOL_CHECK_INTERVAL` | 60 秒 | 可用库存的检查有效期，过时先复检 |
| `PROXY_POOL_MAX_IDLE` | 300 秒 | 超过最小目标的空闲库存回收时间 |
| `PROXY_POOL_WORKERS` | 2 | 每个进程的后台维护并发 |

最大值不能小于最小目标；1024Proxy 会话时长必须大于最短剩余寿命，并留出检测时间，否则在提取前报告配置错误。最大容量是全池硬约束，多个配置的最小目标不保证同时满足。有等待任务的配置可退役其他配置的空闲库存，但不能抢占使用中线路。调小最大值只退役空闲库存；在用租约完成或到期后收敛。

### 6.2 生命周期与共享边界

后台先占槽位，再提取和检测，合格后 `ready`。领取事务检查供给配置、检测新鲜度、剩余寿命和占用状态；此过程不访问供应商或出口检测服务。静态代理和 1024Proxy 候选遵守相同准入规则。

注册与认证任务使用独占子租约 `pool_leased`；套餐查询仅在 `PLAN_CHECK_PROXY_ALLOW_REUSE` 开启时领取 `shared_leased`。共享查询有各自的任务身份和释放记录。锚点持续保护端点/出口去重，子租约结束不能改写其他任务历史。

正常独占归还进入配置的冷却期，静态线路无额外冷却；冷却结束且仍有容量和寿命时重新进入待复检库存。共享租约全部归还后才恢复可用。已报告的传输故障进入 `quarantine`，不再发放，到期收口。冷却、隔离和历史记录不占可分配容量，仍保留去重或审计依据。

重启不恢复失联任务的使用中资源为可用，只等待其租约到期。提取、检查各有持久截止时间和 owner token；旧 worker 晚到结果不能填充已回收的槽位。数据库不可用时领取失败，不回退到进程内去重或直连。终态与锚点收口在同一事务完成；无活跃关联的库存终态保留 7 天后分批清理，任务子租约历史不随库存删除。

### 6.3 供应商适配与预算

1024Proxy 每轮先预留小窗口槽位，一次请求不超过最大容量、最多 64 条的候选列表；跳过数据库已占用/冷却的候选，只检测所需数量，逐条交付后停止。这样供应商重复返回粘性列表前缀时，仍可使用列表中其余候选。重复端点、出口和地区不符的候选不入池；补货失败按指数退避，由池自行维护，任务的等待期限不被后台重试重置。WebUI 启动预热注册来源，CLI 在首次申请时启动维护。

`PROXY_1024_ACQUIRE_TIMEOUT` 约束每轮后台补货；锁、节流、HTTP 与出口检测读取同一剩余时间。同步 HTTP 在途请求仍受底层 connect/read 超时约束，不宣称绝对墙钟硬中断；晚到或寿命不足的候选释放且不交给已超时任务。任务停止不清空其他任务共享的池。

官方 API 的 `region/time/num` 分别用于地区、粘性时长和提取数量。正常池使用固定配置的 `time`，不按 job 派生时长、不将改变时长等同于强制换新 IP。当前文档不足以确认白名单提取模式有独立强制换 IP 接口，因此不臆造参数；增加 num 也不保证新 IP，候选全重复会明确记录并退避，供应商可用能力与线路检查留在适配器内。过期时间按配置窗口保守估算，并不代表供应商作出的存活保证。

配置诊断仍可显式调用旧单条提取器；原 `PROXY_1024_ROTATE_SESSION_TIME/MAX_ATTEMPTS` 不参与正常池补货。旧批次提取函数保留兼容，但注册入口不再调用。

参考：[Psycopg 连接池生命周期](https://www.psycopg.org/psycopg3/docs/advanced/pool.html)、[1024Proxy 官方 API](https://help.1024proxy.com/1024/1024proxy/dynamic-residential-traffic/api)、[1024Proxy 会话管理](https://help.1024proxy.com/1024/1024proxy/dynamic-residential-traffic/session-management)。连接池文档是设计参考，不引入新的业务依赖。

### 6.4 任务显示与重试

领取超时明确返回 `proxy_pool_wait_timeout`，不触发注册服务再次嵌套提取。只有真正发生浏览器线路传输失败、且原 Attempt 没有未知提交或已创建账号围栏时，才按现有注册重试上限申请下一条线路。

代理池页面独立显示容量策略、库存状态和脱敏线路；本进程等待者/worker 明确标记为 local。任务显示只记录申请和领取过程，供应商补货不算作任务执行或自动换线次数。线路编号以存储返回值为准，进度、租约与流量使用同一个编号。

## 7. Remail 订单意图与恢复

### 7.1 三层职责

- `core/remail_client.py`：HTTP 协议、响应解析、结构化安全异常，不隐式创建本地任务。
- 新订单协调器：创建/读取原意图，安排唯一提交、订单查询和凭据交付。
- 新 `core/storage/remail_orders.py` 与 PostgreSQL `remail_order_intents`：并发领取、状态条件更新和私有恢复数据。

注册、换绑和 CLI 共用协调器。仅往注册 Attempt 加字段不能覆盖 CLI：现 CLI 在取得邮箱后才建立按邮箱识别的注册上下文。CLI 必须在付费领取前生成并持久化领取意图，提供明确的继续原意图入口，再绑定后续注册 Attempt。

### 7.2 必要持久事实

| 分类 | 内容 |
| --- | --- |
| 身份 | 稳定 acquisition_id、供应商连接身份引用、owner_kind/owner_id、当前执行令牌 |
| 请求 | 原项目、后缀、服务模式、供货策略、参数指纹、原幂等键 |
| 订单 | 原订单号、创建/提交/响应/核验时间、订单状态与安全原因码 |
| 私有恢复 | 交付邮箱、service token；仅内部读取 |
| 公开摘要 | 是否有订单号/取件凭据、脱敏邮箱、原因、unknown_scope、允许动作 |

一个 owner 的一次领取意图有唯一约束和条件抢占。供应商身份引用不存明文 API Key；连接凭据变化时需要确认仍属于同一供应商账号，不能用当前配置覆盖原请求参数。已知原订单号优先且唯一，读取失败不能自动替换成同邮箱新订单。

owner 不能直接使用每次新建的重试 job 或 Run：注册在取得邮箱前以逻辑根任务绑定原 `acquisition_id`，取得邮箱后再绑定 Attempt，所有后继任务沿用；换绑使用同一逻辑操作任务；CLI 在购买前保存领取标识并通过该标识继续。新的 Run、worker 接管或进程重启都不自动生成新的购买意图。

### 7.3 提交与崩溃边界

`prepared → submitting → order_created → delivered`；异常分为 `request_unknown`、`rejected`、`read_blocked`。

1. 事务保存原参数和幂等键；提交失败则不发 POST。
2. 条件更新为 `submitting` 并提交事务，取得执行令牌后才允许唯一 POST；HTTP 不占用长数据库事务。
3. 得到订单号立即落库，再查询交付。凭据一到立即私有保存，成功后才把邮箱交给调用方。
4. 重启发现 `prepared` 可继续未提交意图；发现 `submitting` 必须当作结果未知，不能因租约过期重发。
5. 原请求晚到响应按原意图和参数身份补记事实，不覆盖新执行状态，不倒退已交付状态。

已有 `Idempotency-Key` 请求头并不能证明供应商允许安全重放。本轮未取得可验证的幂等保留期、按键查询及并发语义；第一版不开放未知 POST 自动重发。恢复以查询已知原订单为主，无定位依据时保持待核验。

### 7.4 错误保留与恢复动作

`RemailOrderUncertain.safe_details()` 保存固定字段：`unknown_scope=mailbox_order`、`operation_phase`、`cause_code`、HTTP 状态、允许的供应商错误枚举、缺失的已知字段名称、耗时、是否已有订单号。注册/换绑异常处理捕获 `exc`，事件、Run、任务中心投影同步保留白名单。

不持久化原始响应体、完整异常、URL、认证头或 OTP。POST 的 409/5xx 仍可能代表未知，不能仅按状态码断言未扣费。GET 的 401/403 是读取受阻，不能覆盖原订单事实为下单失败。

提供受 WebUI 认证保护的核验清单与“核验原订单”API，执行有界同步 GET 并保存核验事实，不购买新邮箱。没有新增常驻 worker 或核验 Run；进程中断后原 intent 保留，可再次查询相同订单或由同一领取意图继续。本版未新增核验清单前端页面。

旧订单缺少 intent 时仅邮箱相同或更新时间较新不足以恢复原购买身份。上述 33 条缺少关联资料的历史记录继续待人工核验；本版不导入、改写生产历史，也不声称已自动生成它们的清单。不得自动绑定那 17 笔已交付订单，或解除未知围栏后重新购买。

## 8. 配置、验证和交付顺序

### 8.1 配置与版本

代理领取启动时固定本次等待策略；认证阶段创建一次预算并沿调用链传递，重试或兜底不重置截止时间。旧 Run 不用当前配置推断历史策略。本版未新增完整 Run 策略快照或 policy_version；后续如增加，应只保存脱敏执行参数。

代理策略以第 6 节独立池配置为准，不继续派生 Run 累计供应商提取次数。如将新认证预算做成可编辑配置，必须同步 `config/schema.py`、对应配置模块、`.env.example`、现代配置页和 README。密钥仍只进入私有配置，不进入 Run 快照。

### 8.2 建议实施包

| 顺序 | 可独立验收的交付 | 主要文件 |
| --- | --- | --- |
| 1 | 线路编号唯一、进度按 Run/线路隔离、计时与卡片状态修复 | `core/storage/db_legacy.py`、`core/storage/operation.py`、`core/task_progress.py`、`core/registration_service.py`、`webui/static/js/modern/jobs.js` 与公共步骤组件 |
| 2 | Remail 安全错误和浏览器提交回执可观测，暂保留原超时策略 | `core/remail_client.py`、注册/换绑服务、`core/task_errors.py`、浏览器采集和认证模块 |
| 3 | Remail 持久意图、原订单核验、CLI/换绑接入 | 新订单存储与协调器、`core/email_provider.py`、`main.py`、对应路由/UI |
| 4 | 独立代理库存、统一领取、后台补货、容量与恢复 | `core/proxy_pool.py`、`core/proxy_pool_store.py`、`core/proxy_supply.py`、统一代理入口、配置与测试 |
| 5 | 认证阶段预算、密码先保存、OTP确认与重发边界 | `core/registration/email_otp.py`、`password_auth.py`、`roxy.py`、检查点适配与测试 |

包 3 和包 4 在接口约定后并行开发；包 5 依赖包 2 的回执证据。共享 `registration_service.py` 的改动按函数范围分工，再统一审查、集成回归和提交。

### 8.3 必须覆盖的验收

- **进度**：用不含生产数据的合成事件复现两张截图；两个 Run、多线路、同线路重复步骤、晚到事件、缺线路历史、终态、续跑复用事实；确认步骤不跨线路累计、总 Run 耗时不变。桌面/移动现代页面展开历史、键盘查看、日志定位均验收。
- **代理**：并发容量上限、独占与共享领取、冷却/过期/中断恢复、跨配置空闲回收、最小库存补货与退避、固定会话参数和逐条交付；任务等待超时不直接访问供应商；旧晚到释放不影响新租约。
- **认证**：准备缓慢仍有提交链路预算；UI排队取消、点击后读失败、NextAuth POST超时、回执乱序、CDP不可用；不重复发送。密码保存失败零点击；保存后崩溃恢复原密码；直接OTP不伪造密码提交。
- **OTP**：30秒停页无错误不自动认定验证码错误；明确拒绝才重发；点击成功后读状态失败不二次点击；重发未确认可有界只读取码；旧邮件/已用候选不重复使用；收件网络失败与校验失败分开。
- **Remail**：POST前数据库失败时请求数为0；并发只产生一个意图；提交窗口崩溃后不自动POST；订单号已返回但凭据未到可跨重启GET恢复；多候选/错误项目不认领；旧33条不自动购买；公开API/日志无私有数据。
- **全链路**：静态与隔离数据库测试完成后，在单任务、2并发、5并发逐级验证；比较同来源、同并发、同配置的样本，统计逻辑根任务成功率、P50/P95、真实线路数、供应商请求数、未知结果比例及是否发生重复提交。小样本只作冒烟，不声称统计显著改善。

沿用 `python tools/test_isolated.py --profile all -- <相关测试文件> -q`；存储测试使用独立数据库和 `test_` schema。重点扩展 `test_task_progress.py`、`test_job_progress.py`、`test_proxy_provider.py`、`test_registration_retry_driver.py`、`test_browser_auth_initialization.py`、`test_email_submission_receipt.py`、`test_registration_password_flow.py`、`test_remail_client.py`，新增订单意图并发/崩溃测试。

存储变更必须在独立 worktree 与测试数据库实施。生产目录保持现状，测试不设置生产放行。新增字段与表采用增量兼容迁移；历史事件只读适配，不批量改状态。

### 8.4 发布与回退

用户已授权实施。交付分别记录文件修改、隔离测试、提交、推送、进程加载版本、健康检查、浏览器验收和真实流程结果。现有未知订单不会因代码上线自动重新购买。

部署应等待当前 Run 收口，避免进程重启打断正在进行的远端动作。展示回退不能修改业务数据；引入 Remail 订单意图后，任何行为回退也必须继续识别 `submitting/request_unknown` 并保留其阻止重复购买的边界。不能简单回退到不认识新意图记录的旧版本。失败和未知记录、私有恢复上下文、原订单事实始终保留。

- 最后补漏后分别补跑：认证 360 项测试、75 项子断言；CLI/查活 72 项测试、7 项子断言；代理故障分类与 CLI 68 项测试、5 项子断言。以上存在覆盖重叠，不相加作为唯一用例数。

## 9. 设计验收标准

1. 当前线路申请代理时，界面不再显示旧线路仍在登录；步骤耗时能解释到同线路事件。
2. 日志能区分未提交、本地点击、请求可能发出、HTTP响应和业务确认，超时不会触发重复远端操作。
3. 同账号的邮箱、密码和恢复身份跨换线、人工重跑、进程重启保持一致。
4. 代理库存独立维护；任务不重复嵌套提取，等待、后台补货和在用租约边界清楚。
5. 每次 Remail 付费请求之前都有持久意图；已知订单可精确恢复，未知订单不会自动重购。
6. 没有足够证据的历史失败仍明确标记原因缺失，不用新方案伪造过去的确定性。
