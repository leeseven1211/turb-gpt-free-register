# 浏览器、协议与 Rust 三类内核结构规划

## 状态与目标

用户确认按“浏览器 / 协议 / Rust 三种内核，各内核拥有各自实现”规划代码结构。
本文件记录已确认结构设计；当前已实施静态内核目录、懒绑定和首批真实执行迁移，
交付进度与验证见迁移计划。Rust 注册尚未接入。

上一阶段已经完成七类操作的驱动目录与入口整理，见
[操作驱动设计](2026-11-20-operation-driver-catalog-design.md)。
原有领域入口保留兼容委托，真实执行按下述内核与实现归组。领域生命周期和混合业务编排
不因目录迁移而整块搬动。

目标是让新增内核、同内核新增实现、同实现新增操作都有明确位置，同时保留原有配置、
任务快照、认证行为和失败重跑语义。

## 内核与实现

内核固定采用以下产品分类：

| 标识 | 名称 | 定义 |
| --- | --- | --- |
| `browser` | 浏览器内核 | 以浏览器自动化为主要认证执行方式 |
| `protocol` | 协议内核 | 现有 Python 协议流程及其独立实现 |
| `rust` | Rust 内核 | 未来由独立 Rust 注册或认证程序执行的流程 |

Rust 与协议作为并列内核登记。实现内部使用的语言或网络库不改变其所属内核：
当前 `protocol_oss_2` 的流程由 Python 编排，使用 wreq 传输，仍属于协议内核。
`BrowserSession` 实际封装 HTTP 会话，不能因类名含 Browser 就归入浏览器内核。

每个内核可以有多个实现：

- 浏览器内核：现有 `roxy`，将来可以增加其它浏览器实现。
- 协议内核：`local` 表示本地协议实现，`protocol_oss_2` 表示独立上游注册实现。
- Rust 内核：预期接入 `sentinel_rs`；当前没有可执行的 Rust 操作。

注册、刷新 AT、补密码、2FA、Codex OAuth、普通查活和套餐查询是操作。
某实现必须逐项声明操作能力，不能因为属于同一内核就自动获得其它实现的能力。

## 结构方案选择

| 方案 | 改动 | 适用性 |
| --- | --- | --- |
| 只给现有驱动增加内核标签 | 最小，但执行边界仍分散 | 可以作为第一步 |
| 三类内核目录加独立实现，业务服务保留 | 可逐操作迁移，依赖和状态有明确拥有者 | 采用 |
| 一次搬迁所有认证代码并合并通用状态机 | 同时影响注册、账号和 Codex 的执行与恢复 | 超出本轮目标 |

采用第二种结构，先完成第一种的身份映射，再渐进迁移实际执行实现。

## 目标目录

下面是职责结构；只在对应迁移阶段创建实际需要的文件，不预造空操作或占位执行器。

```text
contracts/
  kernel_catalog.py                 # 无初始化副作用的内核、实现与操作绑定
  operation_drivers.py              # 现有配置值、操作别名与选择策略兼容

config/
  operation_drivers.py              # 配置侧兼容出口
  schema.py                         # 配置字段、默认值、校验与选项投影

core/
  kernels/
    registry.py                     # 按操作绑定懒加载执行适配器
    browser/
      roxy/
        registration/               # Roxy 注册执行
        refresh_at.py               # Roxy 登录刷新
        live_check.py               # 只验证旧 AT 的浏览器 probe
        password_setup.py
        twofa.py
        codex_oauth.py
    protocol/
      local/
        refresh_at/
          v1.py
          v2.py
          v3.py
        live_check.py
        password_setup/
        twofa.py
        codex_oauth.py
        plan_check.py
      protocol_oss_2/
        registration/               # 上游注册执行与本地执行适配
        upstream/                   # 独立上游源码、许可证和来源记录
    rust/
      sentinel_rs/
        registration.py             # Python 侧操作适配，未来接入时增加
        process.py                  # Rust 子进程生命周期
        messages.py                 # 版本化输入、事件、结果通信

  registration/                     # 批次、Attempt/Run、资源归属与注册收口
  accounts/                         # 账号操作任务、业务规则、保存与后置关联
  codex/                            # OAuth任务、回调、凭据保存及上传
  auth/                             # 认证结果契约与认证上下文
  browser/                          # 既有浏览器资源能力，逐项明确归属
  email/  proxy/  operations/        # 既有邮箱、代理、任务与并发服务
  storage/                          # 既有 PostgreSQL 仓储
```

Rust 源码接入时，原生工程独立放在 `native/sentinel-rs/`，Python 桥接位于
`core/kernels/rust/sentinel_rs/`。本机与 Oracle 分别构建匹配平台和架构的产物。
此次只记录未来位置与[桥接契约](../../architecture/rust-kernel-bridge.md)，
不下载、集成、编译该 Rust 程序，也不提前开放 Rust 配置选项。

## 标识与选择模型

代码内部区分以下身份：

| 身份 | 示例 | 拥有者 |
| --- | --- | --- |
| 操作 `operation` | `registration`、`refresh_at` | 业务模块 |
| 内核 `kernel` | `browser`、`protocol`、`rust` | 纯契约目录 |
| 实现 `implementation` | `roxy`、`local`、`protocol_oss_2` | 所属内核 |
| 操作内变体 `variant` | 本地刷新 AT 的 `v1/v2/v3` | 具体操作实现 |
| 选择策略 `policy` | `fixed`、`auto`、`same_as_registration` | 操作自己的选择入口 |

一个明确的执行绑定由 `(operation, kernel, implementation, variant)` 标识；
没有多个变体的操作不需要人为增加版本。`protocol_oss_2` 中的 `2` 不等于刷新 AT 的 `v2`。

目录只声明静态能力和现有配置值到执行绑定的对应关系，不读取账号、数据库或环境配置。
执行入口按绑定查找适配器，按需导入；不能把选择策略当成可执行实现。

各业务模块继续提供其明确的操作契约：

- 注册：身份资料、原密码、OTP 和检查点上下文，返回注册与会话事实。
- AT 刷新：现有账号认证输入，返回新凭据和本次认证结果。
- 查活：现有 AT 的探测输入和结果，不含登录或自动刷新。
- 密码、2FA、Codex、套餐：分别保留本操作的输入、结果与持久化边界。

共用取消、进度、OTP、提交前检查点等显式上下文能力。不同操作不统一成一个
`run(operation, **kwargs)` 来掩盖真实契约差异。

## 现有能力映射

| 操作 | 现有选择 | 内核 / 实现 / 变体 |
| --- | --- | --- |
| 注册 | `roxy` | `browser / roxy` |
| 注册 | `protocol_oss_2` | `protocol / protocol_oss_2` |
| 刷新 AT | `protocol` 与 v1 | `protocol / local / v1`，保持内部 `legacy` |
| 刷新 AT | `protocol` 与 v2 | `protocol / local / v2`，保持内部 `protocol_v2` |
| 刷新 AT | `protocol` 与 v3 | `protocol / local / v3`，保持内部 `protocol_v3` |
| 刷新 AT | `browser_roxy` | `browser / roxy` |
| 补密码 | `protocol` | `protocol / local` |
| 补密码 | `roxy` | `browser / roxy` |
| 2FA | `protocol` | `protocol / local` |
| 2FA | `browser` | `browser / roxy` |
| 2FA | `auto` | 保留原策略，初选协议及原认证上下文规划 |
| Codex OAuth | `protocol` | `protocol / local` |
| Codex OAuth | `roxy` | `browser / roxy` |
| Codex OAuth | `same_as_registration` | 保留原配置快照到 Codex 实现的映射 |
| 普通查活 | `protocol_current` | `protocol / local` |
| 普通查活 | `browser_roxy` | `browser / roxy`，保留原开放开关 |
| 套餐查询 | `protocol` | `protocol / local` |
| Rust | 尚无 | 三类内核中的预留类型，不登记可执行绑定 |

这张表描述主要操作执行器，不把操作中所有辅助步骤强行归为单一内核。
强制改密码、更换 2FA 等动作仍按原业务规则选择浏览器；本轮不新增可选实现。
邮箱换绑和 Codex Token 刷新继续由原服务提供固定实现，不人为添加配置开关。

## 跨内核组合

一次业务操作可以使用多种执行能力，保留“主选择”和“实际阶段”两个概念：

- Roxy 注册成功后的协议 2FA、套餐查询和 Codex 是各自的后置操作。
- 协议 2FA 可能复用浏览器取得的认证上下文；2FA 本身仍由协议执行器执行。
- Roxy Codex 的浏览器认证可以配合协议换取 Token。
- 协议刷新失败进入现有 Roxy fallback 时，保留原选择并记录实际目标、触发原因和结果。

新模型首先投影既有行为，不新增跨内核 fallback、不收紧原先的部署能力检查，
也不为了提前生成完整计划而提早读取账号状态或固定执行阶段。

`same_as_registration` 继续按本次入队配置快照中的注册选择解析；只有原有历史兼容路径
才读取当前配置。它不改成“跟随该账号当年的注册来源”。
未来 Rust 如何映射到 Codex 必须单独声明，不能仅按“同内核”或“同属协议通信”自动推导。

## 依赖与隔离规则

业务编排调用操作契约，registry 将已选择的绑定交给对应适配器。执行内核负责其
页面、请求、Cookie、指纹、连接或子进程；业务服务拥有任务、租约、凭据保存及终态。

目标是执行器通过显式上下文回调报告事实，不直接导入 `registration.service`、
账号业务 service 或 WebUI。现有注册模块含有这些依赖时，先保留旧边界，不能整目录搬迁
后声称已经完成隔离。

- 实现之间不导入对方的私有 helper。
- 共同能力只在职责清晰时提取，不能变成统一远端认证状态机。
- 原本的纯入口保持无配置初始化、数据库或可选执行器导入副作用。
- Rust 使用独立程序及通信版本；浏览器与协议实现按需加载自己的依赖。
- 各实现持有独立会话、执行上下文和恢复资料；子进程事件绑定当前执行身份。
- 数据库、代理池、邮箱服务和机器资源仍是共同依赖，三类内核不承诺绝对故障隔离。

## 配置、快照与恢复兼容

第一步不改变现有配置键、选项、默认值和字段顺序；从既有解析结果推导内核绑定。
“内核 + 实现”的两级配置界面属于后续展示方案，当前不实现。

历史别名按操作和输入边界解释，新 API 严格值、历史配置和恢复快照继续保持各自规则。
同一 Run 恢复沿用原快照；手动重跑新建 Run 和批量任务重跑分别保留原有配置捕获、
冻结与显式覆盖规则。注册的普通原任务重跑、AT 手动重跑和 Codex 手动重跑不能被
统一成一种配置规则。既有任务和历史 Run 不批量改写。
需要增加持久绑定时，另行定义快照版本、选择依据和缺字段兼容，不把旧配置直接废弃。

每阶段保持原请求顺序、参数、调用次数、超时、重试、账号写回和资源归还时机。
远端回执不明保留原事实和凭据，维持现有手动批量重跑入口。
代码目录迁移不新增人工核对或重复预检，也不把一种内核的私有恢复资料交给另一种解释。

## 迁移顺序

1. **身份与能力目录。** 增加三类内核、现有实现和操作绑定的纯定义；
   对既有选择结果建立等价投影。现有执行代码不移动。
2. **执行入口绑定。** 操作 registry 根据已解析绑定懒加载适配器；
   适配器先调用原函数，旧导入路径、patch 点和任务入口保留。
   此时只是过渡绑定，不能据此声称纯执行实现已经完成内核隔离。
3. **按操作迁移纯执行实现。** 优先迁移普通查活、明确的刷新变体，
   再迁移密码、2FA、Codex 与套餐中职责可拆清的部分。
   业务服务、凭据保存与资源收口留在原领域。
4. **注册执行边界。** 分别梳理 Roxy 与 protocol-2，把生命周期里的业务职责留在
   `registration`，纯认证执行再进入对应内核目录；两条链路分别审查和验证。
5. **Rust 独立接入。** 另行确认来源许可、通信和恢复契约、目标平台构建，
   再增加真实能力与配置选项。本规划不代表已经批准或完成上游接入。

## 验收

- 配置 metadata、默认值、历史别名、现有参数和任务快照与迁移前等价。
- 两种内核的实现或操作不会因名称相同而混用；Rust 没有占位可用能力。
- 改变 AT 协议版本不会切换注册、查活、密码或 2FA 的固定实现。
- 实现缺少可选依赖只影响对应选择，纯入口不初始化配置或数据库。
- 复用取消、进度、OTP、凭据保存及重跑的既有直接相关契约测试。
- 涉及存储使用独立测试库与 schema；涉及实际流程的迁移按影响制定验证，不以
  目录移动或测试替身通过替代真实流程验收。
- 每阶段独立审查、提交与部署分别记账，保留可恢复旧入口。

具体阶段文件与实际迁移边界见[迁移计划](../plans/2026-11-20-kernel-layout-migration.md)。
