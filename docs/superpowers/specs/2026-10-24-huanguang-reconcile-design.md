# 幻光原单持续同步设计

用户已确认网站实现对照并授权优化。目标是让现有幻光订单持续收敛，区分本地执行、等待同步和远端结果；扫码完成与独立 Plus 核验保持分开。

## 方案与取舍

- 不采用无限占用执行线程的轮询：慢单会占满批次与共享预算。
- 不单独新增常驻同步 worker 或数据库表：复用现有 durable Run、私有 provider JSONB 和 `next_attempt_at`。
- 采用同 Run 延迟续查。初次监控沿用现有时间预算；预算结束后保存原单，释放执行容量，下次仅查询一次，再按平台轮询间隔延期。续查不重复预检、登录、创建提链或提交支付。

## 执行与公平性

新增 context.defer 契约，携带安全的 continuation 标记和原 provider Run 引用；转为 queued 而不产生终态或新 attempt。调度分别取得初次执行与到期续查候选，交错排列并轮换首选车道。幻光续查最多占本地平台预算的两个执行槽，仍受平台、批次和共享总预算约束；并发为一时轮换两类候选，避免饥饿。执行中的续查有 lease/fence，排队等待不占线程。进程恢复包括 queued 续查和查询中断的已知原单。

## 平台引用与回执

- 原任务 ID 稳定。自动重提的子任务沿原 secret 读取，父子状态独立，禁止把父单退款或推断到账直接复制给子单。私有链有去重、循环检测和有限长度。
- 平台声明支持 batch receipts 时，单账号使用带随机私有批次凭据的批次提交。凭据必须在发送前持久化，失败则不发送。提交响应不确定后只查原批次回执，不重放提交。未支持该能力时兼容原接口。
- 旧的无回执创建未知和 AT 认证未知不能假装已失败或自动重新付款；新回执恢复可以在没有 job ID 时查询原提交。

## 展示与安全

运行中仅统计本地实际执行；停止查询的旧快照不计运行中。新队列不因 Plus 尚未知而全部计入失败/待确认。续查显示等待平台同步。私有 batch secret、job secret、链内材料不进入普通 API、事件、日志或配置快照。

严格的 `entitlement_inferred` 规则及独立套餐核验不放宽；用户的 `retry_count=3` 原样保留。本次不引入 SSE 客户端、新配置键或数据库 migration。已有 JSONB 结构承担恢复信息。

## 验收

覆盖监控到期后继续、网络恢复、无重复 POST、回执丢失和进程恢复、父子链、过期 fence、取消优先、公平调度及统计一致性。通过隔离 PostgreSQL 测试与完整回归，真实浏览器验证当前界面；合并 main 后重启实际托管服务，确认健康与已有原单同步。
