# 任务步骤条：按真实执行流程展示

状态：设计稿，待评审；本次仅形成设计，未实施。

日期：2026-09-07。依据：当前工作区源码（包含已有未提交改动）、用户提供的任务 #44430 截图及此前本会话的只读诊断。本文中的示例是目标展示，不是新运行结果。本轮未重新执行账号任务。

## 1. 目标与范围

用户要求：“正常顺序是什么就显示什么，不能显示得乱七八糟。”

顶部要能回答三个问题：这次任务准备做什么、现在进行到哪一步、哪些事情已经得到确认。步骤条必须跟随本次运行的实际驱动、请求步骤与分支，不能把所有日志阶段平铺成一条流程。

覆盖统一任务详情中的全部现有任务类型：注册、继续注册、Codex 补跑、账号配置补跑、补密码、补 2FA、账号补全、查活、刷新 AT、刷新 Codex Token、查询套餐、封号邮件扫描。注册的其他进度入口需复用相同展示定义或完成一致性校验。

本次设计调整流程展示与必要的结构化上报，不改变认证策略、验证码重发、密码重置策略、任务调度、失败重跑或业务数据写回规则。不把账号补全改成自动等待/自动续跑的工作流系统。

## 2. 当前实现与确认的问题

| 位置 | 已确认的现状 | 展示后果 |
| --- | --- | --- |
| `core/task_stages.py::TASK_FLOWS / flow_for` | 仅根据 task_type 返回固定列表 | 同一任务类型的驱动差异、分支、所请求步骤无法表达 |
| `webui/static/js/modern/accounts.js::renderAccountTaskStageProgress` | 先渲染固定 flow，再把未知 observed stage 追加到数组尾部 | 登录、验证码、Token 等出现在“完成”之后 |
| 同一前端函数 | 每个 stage 保存最后一次状态；ERROR 日志也可能被当成失败 | 包裹整个操作的 browser 与内部认证阶段同时处于 running；普通日志污染进度 |
| `core/codex_retry_service.py::run_twofa_worker` | browser.running 在账号配置浏览器流程前，browser.success 在整个操作返回后 | 名称叫“启动浏览器”，实际覆盖登录、密码和 2FA 操作 |
| `core/roxy_codex_oauth.py::_fill_email_and_otp` | login.success 表示“已提交 OpenAI 登录邮箱” | 登录尚未验证通过，步骤名称却看起来已经完成登录 |
| `core/task_stages.py::ALIASES` | account_setup 被统一映射为 twofa；login_password 也被多个上下文复用 | 补全协调器开始账号配置可被误读为正在设置 2FA；登录密码与设置密码混淆 |
| `core/codex_retry_service.py::run_twofa_worker` | 若请求套餐查询，实际先分配网络、查询套餐，再进入浏览器/2FA 分支 | account_setup_retry 的静态套餐顺序与执行不符 |
| `_run_protocol_direct_twofa` | 协议 2FA 可直接结束，也可先重认证，失败后按配置回退浏览器 | 静态 browser 节点可能一直显示未开始；协议失败与后续成功被同名阶段覆盖 |
| `core/registration/roxy.py`、`protocol.py`、`browser_use.py` | Roxy 后置顺序为 Codex→2FA；协议和 Browser Use 为 2FA→Codex；协议用 browser 阶段表示协议会话初始化 | 统一静态列表无法准确表达各驱动，协议任务不应标作启动浏览器 |
| `webui/runtime.py::_run_account_completion_worker` | 刷新 AT 入队后返回 partial_success；Codex 入队后父任务可以结束 | 提交成功不能解释为 Token 刷新/授权业务完成 |
| `core/registration/protocol.py` | 注册后的套餐查询独立入队 | 主注册任务不能把独立查询标成已查完 |
| `core/roxy_codex_oauth.py`、`core/codex_operation_service.py` | 本地授权路径先 credential_persist，返回后外层再 credential_confirm；远端来源另有 callback 提交/确认路径 | 不能统一硬编码“确认凭证→保存凭证” |
| `accounts.js::pollAccountTaskLog / pollAccountTaskEvents` | 详情用 include_events=0；首次事件请求仅取最近 500 条 | 用浏览器事件缓存计算阶段状态会丢失较早状态 |
| `core/storage/operation.py::get_task` | runs 已有 progress_steps、progress_stage，但 flow 是 task 级静态数据 | 切换历史运行时无法得到独立的分支流程；快照信息没有被充分利用 |

现有 `docs/task-log-unification-design.md` 已规定：阶段、事件、技术日志分层，串行 Run 最多一个主阶段执行中。本文补齐其流程顺序、层级、分支和运行快照约定。

### #44430 的直接解释

静态流程只有 network→browser→login_password→complete。截图中新增 login 事件被追加到 complete 后，而 browser 仍在包裹内部操作。另一个独立问题是 login.success 只确认邮箱已提交。因此只把“登录 OpenAI”挪到“完成”之前仍不能保证进度真实。

## 3. 方案比较与选择

| 方案 | 优点 | 局限 |
| --- | --- | --- |
| 只删除未知步骤追加并修改固定数组 | 范围小，可直接消除完成后的节点 | 登录阶段状态、分支、分页丢状态仍未解决；容易隐藏用户关心的当前动作 |
| 按事件首次出现顺序生成步骤条 | 能看到已经发生的事件顺序 | 开始时没有完整预期；包裹阶段、重试、异步提交仍混排；刷新可能重排 |
| 每次运行的流程定义＋后端进度快照＋主/子步骤 | 预期顺序明确，分支与状态有依据，可脱离日志分页 | 需要补充关键上报边界及兼容适配 |

推荐第三种，采用有限模板及分支规则，不引入通用 DAG 引擎。原有执行器仍决定执行顺序；展示定义与执行器通过契约测试保持一致。

## 4. 用户看到什么

### 4.1 补密码

常规浏览器路径：

```text
分配网络 → 启动浏览器 → 登录验证 → 设置密码 → 结果
 已完成      已完成       执行中      未开始    待结束

当前：登录验证 · 等待邮箱验证码
  已提交邮箱 → 验证邮箱 → 确认登录会话
```

登录验证中，提交邮箱成功只结束“提交邮箱”子步骤；父步骤在登录会话确认可用时结束。Token 若只是建立登录会话的产物，归在登录验证下，不额外占一个主步骤。

设置密码在远端结果确认且必要写回完成后才能成功。密码已提交、仅保存本地检查点而未确认远端结果时，继续显示处理中或待确认。

开启密码重置且实际进入该路径时，在登录验证下显示“重置密码验证→提交新密码→重新登录确认”；此路径可能已经完成密码设置，后面的“设置密码”负责确认并显示“已通过重置完成”，不能暗示又执行了一遍。密码检查点事件带明确所属步骤，不能把登录密码输入映射为“设置密码”成功。

### 4.2 补 2FA 与回退

```text
分配网络 → 设置 2FA → 结果
             ├─ 协议尝试：失败（已转浏览器）
             └─ 浏览器回退：启动 → 登录验证 → 设置并确认
```

协议直达成功时没有浏览器节点。需要重认证时在设置 2FA 下显示认证子步骤。回退过程中主步骤仍是设置 2FA，协议失败保留在尝试记录中，当前子步骤转向浏览器回退。

这样保留失败→回退的真实历史，也不会让顶部看起来先失败、突然跳回左侧启动浏览器，再跳向右侧。明确选择浏览器驱动时，浏览器初始化与登录同样属于设置 2FA 的执行路径。

### 4.3 账号配置与账号补全

- 同步账号配置按“分配网络→查询套餐（若请求）→准备浏览器及登录（若需要）→设置密码（若请求）→设置 2FA（若请求）→结果”。只有套餐查询时，查完即结束。
- 账号补全先显示“生成补全计划”，之后仅展示计划中本次会执行的工作。
- 若本次先提交刷新 AT，就展示“生成计划→提交刷新 AT→本次结果”，附“已提交，结果见关联任务；其他步骤待刷新后再次发起”。延后步骤列在结果说明，不能写成已跳过或已完成。
- 提交 Codex 是“提交授权任务”，附独立任务链接。父任务提交成功与子任务授权成功分别展示；不自动合并两个 Run 的进度。
- 如果 busy 返回时没有可靠关联任务 ID，显示“已有任务执行中，关联信息暂不可用”；不得凭邮箱、最新任务或日志文本猜测关联对象。

### 4.4 通用布局

主步骤保持稳定，从左到右。当前动作始终可见；当前阶段下面显示有序子步骤，已完成主步骤可展开查看尝试和细节。长流程使用可横向滚动的步骤条，窄屏使用单列顺序布局，不通过压小文字容纳十几个节点。

结果节点固定在最后，名称用“结果”。成功时显示已完成，失败/取消/部分成功/待确认各用对应文案和颜色，避免“完成 · 失败”这种互相矛盾的标签。连线只连通已确认通过的相邻步骤，不能因为右边一个步骤成功就画出穿越未执行步骤的绿色线。

## 5. 各任务类型的流程基线

下表是拟采用的业务主步骤；括号说明条件和待补充的上报边界，不代表所有节点永远出现。表中合并后的业务阶段不会替换原始事件名。

| 类型 | 主流程与分支约定 |
| --- | --- |
| registration | 网络→邮箱→执行环境→注册认证（页面/提交邮箱/密码/验证码/资料子步骤）→取得会话→后置配置→结果；后置配置子步骤严格沿驱动顺序：Roxy 为 Codex→2FA，协议/Browser Use 为 2FA→Codex；套餐独立提交与同步查询分开命名 |
| registration_resume | 从已保存的恢复位置生成本次路径；资源准备按本次需要执行，已完成身份步骤显示“沿用检查点”说明，不伪装成本次重新完成；确需重新走页面/邮箱/认证的路径必须出现 |
| codex_retry | 配置预检→网络→准备授权→身份验证→授权确认→回调→凭证处理→结果；准备授权包含驱动初始化与获取地址，按驱动真实边界排序；手机号及短信位于身份验证的条件子路径；凭证处理按来源展开，本地路径保存后才有外层成功确认，远端路径显示提交/确认及实际存在的保存动作 |
| twofa_retry / account_setup_retry | 使用 requested_steps，而非类型名称推断仅处理 2FA；现有默认工作包括密码、套餐、2FA；网络→套餐（若请求）→登录/密码/2FA 对应路径→结果 |
| password_setup | 网络→浏览器→登录验证→设置密码→结果；重置路径在登录验证下展示并在密码确认步骤复用结果 |
| twofa_setup | 网络→设置 2FA→结果；协议/重认证/浏览器回退为实际子路径 |
| account_completion | 生成计划→本次同步步骤或提交刷新路径→提交 Codex（若本次执行）→结果；提交后延迟处理的工作不进入已完成清单 |
| live_check | 网络→校验现有 Token→结果；当前普通查活不自动展示刷新 AT；历史曾发生重认证的任务按历史证据归组 |
| token_refresh | 网络→重新认证→取得并保存 Token→结果；密码/TOTP/邮箱验证码/浏览器回退属于认证路径，未被要求的验证方式不显示成必经步骤 |
| codex_token_refresh | 刷新 OAuth Token→结果；Token 保存、下游同步作为子步骤，刷新成功但同步失败分别保留 |
| plan_check | 网络→查询套餐→结果 |
| deactivation_mail | 扫描邮件→结果 |

已直接核对账号配置、密码、2FA、补全协调器，三种注册驱动的后置顺序，当前查活/刷新路由，以及 Codex 本地保存与外层确认、套餐和邮件扫描的上报入口。恢复注册的全部检查点组合、Codex 的全部驱动/远端来源组合仍须在实施时通过对应执行器的完整上报序列验证后接入，不把静态数组视作运行证据。

## 6. 数据与模块设计

### 6.1 保留三个不同概念

- 原始阶段 `stage`：兼容既有任务事件、检索与诊断。
- 展示步骤 `step_id`：某类流程中的明确业务含义，如 authenticate、set_password；可与多个原始阶段对应。
- 尝试实例 `instance_id`：同一步骤的第几次执行、所属父步骤和分支。失败的协议尝试与成功的浏览器尝试不得压成同一条最后状态。

新增展示模型不全局修改 account_setup→twofa 等旧别名。兼容适配按 task_type、原始来源、结构化 detail 区分含义；已有投影丢失原始含义时，只能借助可靠 source_id 读取源事件恢复，或明确标注未知。

### 6.2 每次运行的计划

执行器解析好本次请求、驱动和恢复位置后，写一次结构化 `flow.planned` 事件。其 detail 只包含：

- 展示契约版本 `flow_version`；
- 本次 `requested_steps`、实际选择的驱动/路径、恢复阶段标识；
- 已知有序主步骤与预定义分支槽位；
- 可用的关联任务标识。

不得把整个账号对象或 settings 直接塞入计划，字段使用白名单，不含密码、Token、OTP、Cookie 和代理凭据。排队中尚未解析的分支显示“路径待确定”；启动时冻结本次实际使用的选择，不用今天的全局配置解释过去的 Run。

分支变化使用结构化 `flow.branch_selected`，记录父步骤和路径。已执行节点不换位置、不删除；未选中的候选子路径不作为必经未开始节点。顶层按已确定计划排列；待确定分支只在预留槽位内展开。重试发生在步骤内部的尝试列表，新的业务重跑属于新的 Run。

### 6.3 关键上报边界

继续复用 `TaskReporter` / 现有 gateway，在 detail 增加 `step_id`、`parent_step_id`、`instance_id`、`branch_id` 等可选展示元数据，保持原 stage.* 五态契约兼容。明确四个边界：

1. 浏览器创建并可操作后完成“启动浏览器”；整个浏览器 action 的结束事件是执行范围/资源生命周期说明，不能再覆盖初始化步骤。
2. 提交登录邮箱完成的是 submit_login_email 子步骤；authenticate 在会话确认时完成。
3. 设置密码与登录时输入已有密码使用不同 step_id；账号配置协调器属于 scope，不映射为设置 2FA。
4. 提交独立任务使用 dispatch 步骤并携带可靠 child task/run ID；业务完成由子任务自己报告。

密码重置的“写入检查点”与“远端确认”需要分别记录，2FA 的 secret 检查点与启用确认亦如此。此处只补上报边界，不改变原执行/写回顺序。

### 6.4 后端进度快照

建议新增纯函数模块 `core/task_progress.py`，接收运行信息、计划、完整结构化进度事件和现有 progress_steps，返回展示快照。流程定义仍集中于 `core/task_stages.py`，避免维护前后端两份顺序表。

建议新增只读接口：`GET /api/operations/<task_id>/runs/<run_id>/progress`。必须校验 Run 属于该任务，并沿用现有鉴权。旧详情 API 的 flow 字段暂时保留兼容；新版步骤条仅消费这个按 Run 返回的快照。

快照至少包含以下字段：

| 字段 | 含义 |
| --- | --- |
| task_id / run_id / flow_version | 明确运行和契约版本 |
| revision | 快照内容指纹，用于避免重复渲染，不用于比较新旧大小 |
| source | explicit、legacy_derived 或 insufficient_evidence |
| main_steps | 顺序已确定的主步骤，包含 id、label、state、display_status、active、reason、children、attempts |
| current | 当前主步骤和子步骤；无法确认时返回空值并给出说明 |
| outcome | 本 Run 的实际状态、结果文案及关联任务，单独于业务步骤状态 |
| evidence | 步骤证据引用、是否推断及简短原因；不返回敏感 detail 全量数据 |

原始 stage 五态保持不变；展示字段另行表达 unknown、not_executed、deferred、awaiting_confirmation 等情况，不塞回旧的 STEP_STATES。父步骤可由子步骤聚合为 running，主步骤条只高亮当前父步骤，其详情只高亮当前活动子步骤；不会在同一层级同时高亮多个串行步骤。

存储读取只拉该 Run 的计划、分支、stage 及必要生命周期/关联事件，结合 progress_steps 和 result_summary，不依赖时间线分页。初版按需计算，不新建流程引擎表或持久化快照表；若事件规模使读取不达标，依据实测再做缓存或索引调整。

一次快照的 Run 状态和事件须来自一致性读取，避免拿到“Run 已结束但结束前事件尚未读取”的混合视图。历史兼容投影可能原地更新事件，同一个最大 event_id 并不保证内容没变，因此 revision 计算需覆盖参与推导的实际状态、事件字段与计划内容，不能只用最大 ID。

### 6.5 前端请求规则

详情、进度快照、时间线、技术日志各司其职。选中 Run 后独立读取进度；时间线仍按原分页方式读取，缺少早期日志不影响顶部。

切换任务或 Run 时增加请求代数；响应必须匹配当前 task_id、run_id 和请求代数才可写入 UI，防止旧请求回包污染新运行。终态先取得最终进度快照再停止轮询；是否继续轮询按 Run 状态和实际关联任务需求处理，不把父任务 success 当成子任务 success。

快照加载失败时保留同一 Run 的最后一次成功快照并显示“进度更新失败”；首次失败则显示不可用。不能回退到用当前一页日志猜进度。

## 7. 状态规则

| 情况 | 展示规则 |
| --- | --- |
| 串行主步骤开始 | 当前主步骤高亮；先前缺完成证据的阶段不得自动刷绿，标“未确认”，以显式当前阶段确定活动位置 |
| 普通 INFO/WARNING/ERROR 日志 | 留在时间线，不推进、不结束步骤；状态只消费明确契约事件 |
| 子步骤成功 | 不自动让父步骤成功；父步骤需其成功条件满足或明确结束事件 |
| 下一步已开始，但旧 browser scope 还 running | scope 不占主流程；真实启动已确认则初始化步骤成功，无法确认则注明历史证据不足 |
| 未请求/配置关闭的步骤 | 不进入本次计划；与运行中明确决定跳过的步骤区分 |
| 计划内明确跳过 | 保留 skipped 和原因，例如已有 2FA 无需重复设置 |
| 因前置失败未到达 | 显示“未执行（前置步骤失败）”，不写成主动跳过 |
| 协议失败后浏览器回退 | 保留失败尝试；主步骤 running；最终按最后有效业务确认结束 |
| 同一步骤重试 | 新实例另记，旧尝试状态不覆盖；“正在重试，第 N 次”出现在当前详情 |
| 任务结束仍有 running | 不继续动画；有失败/取消证据则按证据结束，没有证据显示“结束时未确认”，不补造成功 |
| 后到的清理、资源释放、诊断事件 | 时间线可继续追加，不在结果后增加主步骤，也不重新开启已结束流程 |
| partial_success / cancelled / interrupted / attention_required 等 | 结果使用实际语义；已确认成功的前序步骤保留，未确认或未执行项分别说明 |
| 独立任务 accepted / busy | 只表示提交/已有执行；附关联结果入口，不能代表业务完成 |
| 新 Run 或历史 Run | 分开计算，当前结果不能覆盖过去的步骤状态 |

未知阶段保留在时间线并计入内部契约诊断，不自动出现在主流程。若未知阶段恰是当前动作且无法归属，显示“当前动作暂未归类，详见时间线”，不得假装已准确知道进度。

## 8. 旧记录兼容

历史数据不重写。已存在的 progress_steps 能弥补分页遗漏，但只能作为阶段状态证据，不能独自区分同名步骤、父子层级或失败后的回退。

兼容优先级：显式展示元数据→结构化原事件与本 Run 结果/驱动/计划→已验证的类型适配规则→未知。对于无版本的旧事件，保留现有兼容事件类型，但根据原始 detail 判断证据强弱，避免把旧投影对中文消息的推断当成新版明确上报。

特定可证明的推断需列入白名单并显示说明：例如截图场景已经发出浏览器中的登录页操作，足以说明该次浏览器已可操作，但“已提交邮箱”不足以证明登录验证完成。不能用一条任意下游事件把所有前置业务步骤补成成功，不推造耗时。

若历史驱动无法恢复且关系顺序证据不足，显示“历史记录，部分顺序无法确认”，只显示已可靠识别的业务组和当前证据；不能用当前默认驱动生成一条看似确定的历史路线。恢复注册的已完成检查点标为历史沿用，保留其来源，不统计成本次运行完成步骤。

4. **前端展示与回归**：接入新快照，移除未知节点追加和事件缓存推状态，完成主子步骤、结果态、请求竞态和窄屏展示。

## 10. 验收场景

验收以脱敏事件夹具、模拟上报和隔离 PostgreSQL 集成为主；UI 用测试数据回放，不通过批量真实注册/密码重置/2FA 操作验证布局。

1. #44430 截图时刻：结果最后，浏览器初始化已确认，登录验证仍未完成；不会出现“完成→登录”。
2. 密码常规路径和重置路径：提交/检查点不算最终密码确认；登录密码输入与设置密码不混淆。
3. 套餐+密码+2FA 配置：套餐在浏览器之前；套餐失败但密码/2FA 成功时保留各自结果与待处理原因。
4. 2FA：已有密钥跳过、协议直达、协议重认证、协议失败不回退、允许浏览器回退五种路径均有准确展示。
5. Roxy/协议/Browser Use 注册：后置顺序分别符合执行器；协议会话不叫浏览器；套餐独立提交不显示查询成功。
6. 恢复注册：同一账号从不同检查点恢复，展示本 Run 真正执行的路径。
7. 补全刷新 AT 入队后返回 partial_success、Codex accepted/busy、入队失败：父子结果分别准确，延后步骤不被刷绿。
8. 事件超过 500 条，第一次打开与持续打开的顶部状态一致；随机打乱分页/重复事件/原地更新兼容事件都不丢状态。
9. 快速切换 Run/任务并让请求反序返回：只显示当前选中运行。
10. 失败、取消、中断、部分成功、待确认：均无伪成功和永久 running；结果后没有新主节点。
11. 普通 ERROR 日志、scope 事件、未知诊断阶段、清理事件：不污染主流程；必要的不确定性明确可见。
12. 其余类型逐一运行投影及 API 夹具；对应驱动契约断言实际主阶段序列是其计划的一条合法路径，重试仅改变实例。
13. 桌面与窄屏检查步骤顺序、当前子步骤、键盘展开、非颜色状态文案及结果标签；检查事件/进度响应均无敏感字段。
14. Codex 本地路径先保存再外层确认、远端 callback 后待确认、凭证确认失败：按真实顺序展示，callback 到达不表示凭证已可用。

完成标准：用户能看出实际执行路径和当前动作；没有凭日志补出的成功，没有完成后的新步骤，没有跨 Run 混状态。仅修改数组或让截图顺序看起来正常不算完成。
